## 3. 用户、组织范围与访问模型

### 3.1 用户类型

- **商城消费者/企业员工**：浏览商城，使用福利账户、餐补、卡券或微信完成购买，管理订单、售后、通知、地址和安全设置。
- **平台运营人员**：管理平台层级、全局商品池、卡号库、渠道和跨组织治理能力。
- **分销运营人员**：查看分销层，管理分销设置、推广商品、推广员资格和佣金信息。
- **企业运营人员**：经营驾驶舱、商城应用、商品、订单、卡券、渠道、财务、报表、客服和成员权限。
- **商城运营人员**：在单商城范围内执行与企业运营相同类型、但受商城数据范围约束的操作。
- **财务、客服、风控、复核人、目录管理员等专业人员**：通过动态角色、权限、Capability 和范围授权获得对应能力；代码没有把这些专业角色硬编码成固定前端角色。

### 3.2 范围模型

代码定义的完整范围类型为：`platform`、`distributor`、`tenant`、`enterprise`、`mall`、`department`、`supplier`、`brand`、`store`、`owner`、`self`。

Console 当前可直接切换和导航的范围为：

- `platform`：平台。
- `distributor`：分销层。
- `enterprise`：企业/集团。
- `mall`：商城。

Storefront 的个人业务在 `mall`、`owner`、`self` 等服务端范围规则内执行；服务端同时校验当前 Membership、资源所属关系和授权范围。

### 3.3 动态导航

- 导航树由 `navigation.tree.read` 按当前 Membership、Scope、Permission 和 Capability 动态生成。
- 无权限、无 Capability 或没有可见数据的节点可被隐藏，前端不自行推测菜单权限。
- 导航 Catalog、健康状态和客户端 Catalog Hash 参与一致性校验。
- Console 根路径根据服务端返回的可用 Scope 和导航节点选择落地页，不固定假设某个页面必然存在。

## 4. 统一认证与账号安全

### 4.1 Auth 页面

| 路径           | 页面已接通功能                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/` 及默认路径 | 在 Console/Storefront 目标间切换；账号/手机号 + 密码登录；账号/手机号 + 短信验证码登录；邀请码登录；动态展示可用联合登录方式；阅读并接受用户协议和隐私政策。 |
| `/callback`    | 展示联合身份提供方回调处理状态；实际签名回调和身份交换由 Commerce 服务完成。                                                                                 |
| `/membership`  | 一次性身份选择；当同一身份有多个 Membership 时选择本次进入的企业/商城身份。                                                                                  |
| `/link`        | 身份绑定冲突提示；明确禁止自动合并账号，要求管理员强验证和人工确认。                                                                                         |

### 4.2 登录与入职能力

- 密码登录。
- 短信验证码登录，包含 6 位验证码校验、发送冷却和过期控制。
- 邀请码登录；可处理无效、过期、已耗尽、撤销和需要追加短信证明等结果。
- 邀请入职：读取一次性 Enrollment，校验手机号验证码、密码、显示名称、协议版本和协议 Hash，完成员工商城账号创建。
- 联合登录：微信、企业微信自建应用、企业微信第三方应用和 OIDC。
- 多身份选择：联合登录或普通登录后，按授权 Membership 选择 Console/Storefront 目标身份。
- 密码重置：短信挑战通过后设置新密码，并撤销旧会话。
- 严格回跳：只允许回到目标客户端白名单 Origin，拒绝携带用户名、密码或 Hash 的异常回跳 URL。
- PKCE S256 + state + nonce + 一次性 Ticket 交换，避免在前端暴露长期会话凭据。

### 4.3 会话与安全中心

- 读取当前 Session、Membership、Scope、权限版本和安全等级。
- 退出登录并删除当前 Session。
- 查询当前账号的全部 Session/设备会话。
- 撤销指定会话或“其他全部会话”。
- 查询可用 Membership 并切换当前商城；切换后清空前端查询缓存并重新加载授权上下文。
- 修改密码，要求当前密码、至少 12 位新密码、版本校验和二次验证。
- 更换手机号，使用短信挑战 + 6 位验证码 + 版本校验。
- Step-up 二次验证：发起短信挑战、完成验证并提升当前会话安全等级。
- 高风险操作可要求另一位复核人签发与 Operation、输入、资源和版本绑定的一次性 Action Proof。

## 5. 消费者商城 Storefront

Storefront 已实现手机、平板和桌面三类响应式页面；公开页面允许匿名浏览，购物车之后的个人业务由路由 Guard 强制登录。

### 5.1 全局能力

- 从 `storefront.bootstrap.read` 获取当前商城绑定、主题/内容入口、身份状态和初始业务数据。
- 从 `storefront.catalog.read` 读取商城实际可售商品，不从本地 Mock 或静态展示数据推导库存和价格。
- 顶部商城切换：展示当前用户有权进入的多个 Membership/商城并安全切换。
- 全局登录/退出、购物车数量、页面导航和错误提示。
- 支持 URL 中的签名 `referral` Token；登录且商城/会员上下文可信时创建首次有效分销绑定，重复或已有绑定不会覆盖。
- 商品和结算数据均以服务端版本为准；写请求使用幂等键，冲突后要求重新读取。

### 5.3 结算与支付规则

- 报价输入包含购物车版本、商品行版本、收货地址、配送选择、卡券、福利账户抵扣和支付场景。
- 当前前端会把可用且余额大于 0 的福利账户纳入报价；最终可用金额和组合由服务端重新计算。
- 服务端 Quote 带签名和有效期；订单只能从有效 Quote 创建。
- 支持福利账户、餐补/津贴、卡券、微信等支付媒介的服务端拆分和结算；前端不自行认定扣款成功。
- 微信客户端返回“成功”只触发权威状态重读，最终以签名回调或主动查询结果为准。
- 支付不确定时进入 Recovery，并由后台主动查询；不会把超时推测成成功或失败。
- 订单过期会异步释放库存、权益 Hold 和未完成支付资源。

### 5.4 售后与退款规则

- 服务端按履约数量、已售后数量、供应商可退规则和售后时限计算可申请数量。
- 支持质量、破损、错漏发、不再需要、服务未完成等原因及自由文本说明。
- 附件限制为最多 6 个 JPG/PNG/PDF，单个不超过 1 MB、合计不超过 1.25 MB；服务端继续校验 MIME、文件头、SHA-256 和恶意文件扫描结果。
- 退款按原支付媒介拆分，福利、卡券和微信分别恢复/退款；退款与佣金冲正通过追加记录完成，不删除历史事实。
- 需要退货的售后可生成供应商或平台退货指引，后续由收货和验收流程推进。

## 10. 事件驱动能力

系统定义了 97 类正式领域事件，主要自动化链路包括：

- 身份、目录、Membership、Capability 和权限版本变化触发导航重算和报表投影。
- Experience 发布触发 CDN 发布和投影。
- 下单、支付、取消、收货触发订单投影；支付成功触发通知和对账。
- 发货触发订单投影和通知。
- 售后申请/变化、退货验收和退款完成触发投影、通知、对账和返佣冲正。
- 福利发放/到期/撤销、卡券发行/核销触发投影与通知。
- 财务分录、对账差异、结算、期间关闭、提现和发票事件触发投影与通知。
- 客服消息、分派和 SLA 升级触发通知。
- 渠道同步、Webhook、退款变化触发投影或通知。
- 风险案件打开/关闭、交易拦截和扩展降级触发通知。
- 分销申请、审批、绑定、佣金创建/结算/冲正和提现变化触发投影与通知。

事件通过 Outbox 持久化、Inbox 去重和 Projection Offset 消费，不依赖进程内“发完即忘”的消息。

## 11. 横切安全与可靠性能力

### 11.1 授权与敏感操作

- 每个 Operation 定义 Audience、Target、Scope Kind、Permission、Capability、Assurance Level、风险等级和资源解析器。
- 默认拒绝：缺登录、权限、Capability、Scope 或目标客户端不匹配时拒绝请求。
- 写请求校验同源策略、CSRF Token、幂等键和输入 Schema。
- 使用 `expectedVersion` 做乐观并发控制，避免旧页面覆盖新状态。
- 关键操作要求 Step-up；37 个关键 Operation 进一步要求 Maker-Checker 分离和一次性 Action Proof。
- Action Proof 与 Operation、规范化输入 Hash、资源、版本和制作者 Membership 绑定，并防重放。
- Provider Webhook 使用签名验证、时间窗、原始 Body 和 Inbox 去重。

### 11.2 一致性与可恢复性

- 业务写入、幂等记录、审计记录和 Outbox 可在同一 PostgreSQL 事务中提交。
- Operation Handler Registry 启动时核对全部 269 个 Operation，缺失、重复或 Owner 不匹配会启动失败。
- Job 使用数据库租约和 Fencing，防止多 Worker 重复持有同一资源。
- 支付、卡券、福利和财务具有专门 Dead Letter 处理；其他任务进入统一 `runtime.deadletter`。
- 支持主动支付查询、退款查询、对账修复 Preview、确定性业务键和人工恢复。
- 数据库迁移只追加不改写，并记录 Schema Version、Migration Evidence 和发布事实 Hash。

### 11.3 审计、隐私与可观测性

- 高风险读写形成审计记录，审计表使用 Hash Chain 防篡改并禁止普通更新/删除。
- Secret、支付证书、卡号明文、验证码和敏感身份数据不会通过 Console 列表或普通日志回显。
- 客户端错误、API 指标、Job 指标、结构化日志和 Trace 使用统一 Telemetry；日志经过字段脱敏。
- Live/Ready/Startup/Dependency 四类健康检查区分进程存活、启动、就绪和外部依赖状态。
- 导入、导出、附件、发票和归档文件通过私有对象存储及受控下载处理。
