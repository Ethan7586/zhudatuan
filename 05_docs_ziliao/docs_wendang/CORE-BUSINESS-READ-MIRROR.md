# 智慧翼核心业务读镜像架构

版本：1.1
日期：2026-08-15  
目标：在不制造双主库的前提下，让 Web、微信小程序及未来鸿蒙/iOS/Android 客户端获得北京同地域的高速、可降级业务读取能力。

## 1. 架构决议

**镜像可读状态，不镜像交易真相。**

- Supabase PostgreSQL 目前仍是唯一业务真相源。
- 北京阿里云 Tair 是共享读镜像，不接受订单、余额、库存和支付的独立写入。
- OSS + 阿里云 CDN 只承载图片、缩略图和带内容哈希的静态快照。
- Web、小程序和未来原生端使用同一个 Commerce API、同一个读模型版本和同一个媒体域名。
- 任意写操作都必须回到主库事务；缓存只能加速读取，不能成为支付或核销依据。

这不是“复制一套数据库”，而是标准的单写多读、CQRS 读模型与分层缓存。

## 2. 正式拓扑

```text
用户
 ├─ Web ───────────────┐
 ├─ 微信小程序 ───────┤
 └─ 鸿蒙/iOS/Android ─┤（预留平台适配器）
                       ▼
              hbbtzn.com 同源 BFF
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
      L1 进程内      L2 Tair      OSS + CDN
      60 秒热项     北京同 VPC    img.hbbtzn.com
          │            │
          └──────┬─────┘
                 │ 未命中/过期
                 ▼
        Supabase PostgreSQL
        当前主区 ap-southeast-1
        唯一写入与审计真相
```

端内还有 L4 双层快照：小程序主包只同步解析 24 件关键目录，保证结构和文字立即成屏；完整 200 件目录在首帧后从异步存储或延迟加载的包内快照补齐。端内数据只负责立即展示，后台仍会校验版本并更新。

公开目录还有 L3.5 静态清单：`img.hbbtzn.com/catalog/public/v1/latest.json`。小程序更新目录时先请求 CDN，失败才回源 Commerce API；内容版本同时保存为不可变对象，避免每次更新都跨地域访问数据库。

## 3. 为什么放在北京 Tair

当前应用服务器位于阿里云中国区，数据库位于新加坡。没有共享缓存时，首访需要跨地域访问数据库；进程缓存重启后也会丢失。

Tair 应满足：

- 与 ECS 同地域、同 VPC、尽量同可用区或低时延可用区；
- 只使用 VPC 内网连接；
- 白名单只放 ECS 私网地址或安全组；
- 开启 TLS，使用独立账号和密码；
- 选择高可用实例，不使用单副本作为生产缓存；
- 不给 Tair 配公网地址，不通过 Caddy 暴露 3002 端口。

代码中的 `smart-wing-core-read-cache` 只监听 `127.0.0.1:3002`。Storefront 通过本机 HTTP 调用它；只有该进程持有 Tair 凭据，因此 Web 构建、小程序包和浏览器都接触不到缓存密码。

## 4. 核心业务分层

| 业务                 | 真相源                | 读镜像          |   新鲜期 |             允许陈旧 | 写入/判定规则                  |
| -------------------- | --------------------- | --------------- | -------: | -------------------: | ------------------------------ |
| 公开商品、分类、品牌 | PostgreSQL            | Tair + 端内快照 |   5 分钟 |              24 小时 | 只用于浏览；购买时重验         |
| 首页公共模块         | PostgreSQL/CMS        | Tair + CDN      |   5 分钟 |              24 小时 | 发布后版本失效                 |
| 会员资料摘要         | PostgreSQL            | Tair            |    30 秒 |               2 分钟 | 不缓存原始手机号/OpenID        |
| 权限与资格摘要       | PostgreSQL            | Tair            |    60 秒 |       不允许越权陈旧 | key 必须包含 `authzVersion`    |
| 订单列表/详情        | PostgreSQL            | Tair            |  5–15 秒 |           最长 30 秒 | 写后删 key；状态变更回主库     |
| 福利余额摘要         | 账本聚合              | Tair            |  5–15 秒 |           最长 30 秒 | 扣减前锁定并重算主库余额       |
| 库存展示             | PostgreSQL            | Tair            |  5–15 秒 |           最长 30 秒 | 下单前主库预占，缓存不承诺库存 |
| 会话撤销摘要         | PostgreSQL            | Tair            | 30–60 秒 | 不允许失效后继续授权 | 版本/撤销号参与 key            |
| 会员码挑战           | PostgreSQL 审计       | Tair 短期态     |    45 秒 |               不允许 | 原子消费一次，主库留审计       |
| 支付、退款、流水     | PostgreSQL + 微信支付 | 不作为真相缓存  |        0 |               不允许 | 回调验签、查单和主库状态机为准 |

## 5. 缓存键与数据契约

统一前缀：`sw:v2:`。禁止使用姓名、手机号、OpenID、订单明文或其他个人信息作为 key。

建议键：

```text
sw:v2:catalog:public:{mall}:{queryHash}
sw:v2:home:member:{membershipHash}:{authzVersion}
sw:v2:orders:member:{membershipHash}:{version}:{cursorHash}
sw:v2:member:summary:{membershipHash}:{version}
sw:v2:authz:{membershipHash}:{authzVersion}
sw:v2:wingcode:{challengeHash}
```

每个 value 都使用统一信封：

```json
{
  "schemaVersion": 2,
  "projectionVersion": "catalog.0123456789abcdef01234567",
  "sourceCursor": "cursor:0:limit:24:items:24",
  "contentHash": "sha256:...",
  "generatedAt": "2026-08-15T00:00:00.000Z",
  "storedAt": 0,
  "expiresAt": 0,
  "staleUntil": 0,
  "data": {}
}
```

读端必须能识别 `fresh / stale / expired`。schema 不认识、内容哈希不一致或超过陈旧窗口时视为 miss，不得猜测修复。`projectionVersion` 用于跨端确认读到同一批业务投影，`sourceCursor` 用于定位来源窗口，`generatedAt` 用于判断投影年龄。

## 6. 一致性和失效

### 6.1 读取

1. 先查进程内 L1。
2. L1 未命中时查北京 Tair L2。
3. Tair fresh：直接返回。
4. Tair stale：立即返回旧值，同时单飞后台刷新。
5. Tair miss：回源主库并写回 Tair。
6. Tair 故障：自动绕过缓存回源；不得让缓存故障变成商城故障。

所有刷新都必须做请求合并，防止同一个 key 在过期瞬间产生缓存击穿。TTL 增加少量抖动，避免大量 key 同时失效。

### 6.2 写入

正确顺序是：

```text
业务写入主库事务
  ├─ 更新订单/账本/资格等真相表
  └─ 同事务写入 read_model_outbox
提交成功
  └─ 投影 Worker 消费 outbox
       ├─ 删除旧 key 或提升版本
       ├─ 写入新读模型
       └─ 标记事件完成；失败重试/死信
```

禁止先改缓存再补写主库，也禁止在数据库事务中等待 Tair 或外部 HTTP。项目现有 `wechat_payment_outbox` 已证明了同类模式；通用读模型 outbox 应复用这一原则。

### 6.3 写后立即读

- 创建订单、支付、退款、核销后，响应直接使用该次主库事务结果。
- 随后的关键详情读取可携带 `minVersion`；缓存版本不足时绕过缓存。
- 普通列表可以短暂显示旧快照，但必须在后台更新并展示同步状态。

## 7. 安全边界

- Tair 不开放公网；端口 3002 不进入 Caddy、CDN或安全组公网入口。
- Storefront 到 sidecar 使用独立 `CORE_READ_CACHE_TOKEN`，不复用任何会话或签名密钥。
- Tair 账号只允许本项目 keyspace；运维账号与应用账号分离。
- 缓存内不保存密码、验证码、微信 AppSecret、支付私钥、完整手机号、原始 OpenID。
- 会员数据按会员关系和版本隔离，禁止仅按 `memberId` 混用不同企业关系。
- 浏览器/边缘层对会员接口继续使用 `private, no-store`；只有服务器内部可缓存。
- 公开目录可以在 CDN/浏览器缓存，会员资产和订单绝不进入共享 CDN。
- 缓存命中率、容量、淘汰、回源时延只记录指标，不记录缓存正文和个人信息。

## 8. 已落地的第一段

本轮代码完成：

- 新增独立 `services/core-read-cache`，连接 Tair 并提供仅回环可达的受权接口；
- 公共目录读取链变为 L1 → Tair → Supabase；
- Tair 缺失或失败自动回源；
- 公共目录 fresh 5 分钟、最长可陈旧 24 小时；
- stale 时立即响应并后台刷新；
- 同一个目录窗口的并发回源会合并；
- 响应头增加缓存层标记，便于验收而不泄漏数据。
- 公共目录默认只返回首批 24 件，端侧保留 200 件本地快照并在后台按需续取；
- 读镜像信封升级为 v2，带投影版本、来源游标、生成时间和 SHA-256 内容校验；
- 公共目录提供 ETag，版本未变化时返回 304，不重复传输 JSON 正文；
- 小程序冷路径从同步解析 200 件改为同步解析 24 件，完整 200 件只在首帧后异步补齐；
- 新增内容寻址的 CDN 目录清单，`latest.json` 缓存 60 秒、不可变版本缓存一年，CDN 失败自动回源；
- 公共目录返回 `Server-Timing`，可直接观测 API 目录处理时延；
- 新增 PostgreSQL 自校验备份程序与 systemd 定时器，可将主库备份加密写入私有 OSS，并产生独立校验清单。

## 9. 分阶段实施

### P0：公开目录（本轮）

- 创建北京 Tair 高可用实例；
- 配置同 VPC、白名单和 TLS；
- 写入 6 个环境变量；
- 部署后验证第一次 source、第二次 memory/shared，重启 Storefront 后仍能 shared 命中。

代码、协议和回退路径已经落地；Tair 实例与 OSS 私有备份桶仍需在阿里云控制台配置后才算运行态完成。

### P1：会员首页与订单读模型

- 增加通用 `read_model_outbox`；
- 建立会员摘要、订单列表和订单详情投影；
- 以 `membershipId + authzVersion` 隔离权限；
- 所有订单写动作主动失效相关列表与详情。

### P2：会员码短期态

- 45 秒 TTL；
- 使用原子消费，不允许截图复用；
- Tair 只保存挑战态，主库保存签发、核验和消费审计。

### P3：主库地域收敛

长期最优解是把唯一主 PostgreSQL 放到用户和应用所在的中国区同地域，而不是永久依赖北京到新加坡的跨地域主库。迁移时必须通过受控复制、双读核对、冻结写入和一次性切主完成，不能把两边同时开放写入。

## 10. 验收指标

- Tair 同 VPC 命中读取目标：P95 小于 10ms；
- 公共目录 API 热命中目标：P95 小于 50ms（不含图片下载）；
- 小程序同步关键目录预算：小于 20KB；主包预算：小于 500KB；首帧前不得同步读取完整 200 件目录；
- 首屏结构与文字立即出现，远程图片独立渐进加载；
- Tair 故障演练中 API 仍可回源，错误率不增加；
- 重启 Storefront 后共享缓存仍命中；
- 缓存命中率、回源率、陈旧响应率、刷新失败率均可观测；
- 支付、账本和会员码核销测试证明缓存无法绕过主库校验。
- 每日数据库备份必须同时通过 `pg_restore --list`、SHA-256 清单和 OSS 对象长度校验；每月至少在隔离数据库做一次恢复演练。

## 11. 架构评价

能体现架构水平的不是“层数多”，而是以下四件事同时成立：

1. 只有一个交易真相源，避免双写和资金分叉；
2. 读取被投影到用户附近，首访不再依赖跨地域往返；
3. 每类数据有明确新鲜期、陈旧窗口和失效方式；
4. 缓存坏了系统仍能运行，缓存旧了也不能越权、扣错钱或重复核销。

这套方案满足这四点。它是面向 MVP 的专业架构，也保留了向同地域主库和多实例扩展的路径。
