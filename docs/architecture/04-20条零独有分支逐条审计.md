## 二、判定标准

### 2.1 “独有提交为 0”

对每条候选分支执行：候选 tip 的可达提交减去其余 27 条远程分支的可达提交。结果为 `0`，表示它的全部提交仍由至少一条其他远程分支承接。

### 2.2 “被继承”

本表只把严格 Git 祖先关系称为继承：

```text
git merge-base --is-ancestor 候选分支tip 存活承接分支tip
```

“承接线 +N”表示承接线在该候选 tip 之后还有 N 个提交。不是按文件名相似、分支名相似或人工猜测判断。

### 2.3 “阿里云已继承”与“生产证据锚点”

这两个方向必须分开：

- **在线包含候选 tip**：候选 tip 是某个阿里云在线来源提交的祖先，说明该分支的完整提交历史已经进入该在线版本。
- **候选分支包含在线 SHA**：候选分支只是包含某个更老的在线提交，不代表该候选 tip 已发布。
- **精确在线来源**：候选 tip 与在线服务来源 SHA 完全相同，关闭前应先留下不可变生产证据。
- **精确历史制品**：阿里云仍保留以候选 tip 命名的 release 目录。删除 GitHub 分支不会删除服务器 release，但应把二者关系写入账本。

## 六、每一刀的固定动作

即使 Ethan 一次授权多条，也必须逐支执行：

1. 刷新远程并确认分支 tip 没变。
2. 重新计算独有提交仍为 `0`。
3. 确认表中的存活承接线存在，且不在同批被删除。
4. 确认 bundle 或生产证据包含精确 SHA。
5. 检查同名 worktree 为干净；有任何改动立即停止该条。
6. 单独删除一条 GitHub 远程 ref。
7. 验证远程总数只减少 `1`，该 ref 确实消失。
8. 仅清理该条对应的干净本地分支/worktree。
9. 验证远程、本地分支和 worktree 登记均已收口。
10. 写独立 Markdown 与 JSON 账本，提交并推送 `zdt-next`。

任何 SHA 变化、独有提交不再为 0、承接线缺失、bundle 校验失败、worktree 变脏、分支成为生产唯一锚点或分支数量不匹配，都必须停止，不能静默换下一条。
