# **主打团标准订单管理系统提示词**

## **适用范围与使用方法**

本提示词体系只用于升级 zhudatuan 主打团订单管理系统，目标产品名称为：

> **Smart Wing OMS 2.0**  
> **WCHS-MCBS Order Profile 1.0**

目标公式：

> **真实订单业务闭环 + Smart Wing VI 1.2 + WCHS-MCBS 1.0**

本体系覆盖订单管理前端、订单领域后端、订单读模型、售后、异常、导出、批量下单以及与支付、履约、渠道、财务、组织、客服和报表之间的协同契约。

本体系不等于整个商城重构，不负责重做商品、支付、财务、渠道或组织系统内部实现；只定义订单系统拥有的事实、跨系统契约以及订单运营所需的稳定摘要。

使用顺序：

1. 第一部分作为永久业务与工程基线，附加到后续每个订单任务。
2. 第二部分只做现状审计和重新评分。
3. 第三部分只做 9.5 分目标蓝图和交互设计。
4. 第四部分只把已确认蓝图转换为代码修改清单。
5. 第五部分每次只实施一个可独立验收的工作包。
6. 第六部分在全部工作包完成后独立验收和评分。

禁止把六个阶段合并成一个“一口气全部完成”的任务。

当前“8.2 分”只是设计讨论中的起点，不是事实结论。现状审计必须根据真实代码、真实数据、真实接口和真实浏览器重新评分；最终“9.5 分”必须由证据计算，不能凭截图、主观印象或功能名称宣布。

## **第一部分：永久业务与工程基线**

### **项目名称**

zhudatuan 主打团 Smart Wing OMS 2.0 升级

### **一、9.5 分的可测量定义**

满分 100 分，最终达到 95 分及以上才可称为“9.5 分订单管理系统”。

| 评分维度 | 分值 | 核心判断 |
| --- | ---: | --- |
| 真实业务闭环 | 25 | 能查、能看、能标、能处理、能恢复、能导出，不用占位动作冒充功能 |
| 数据事实与契约 | 15 | 单一订单事实源、状态维度独立、历史快照稳定、跨系统摘要可追踪 |
| 运营交互效率 | 15 | 角色任务清晰、操作就近、批量高效、反馈完整、无伪功能和无意义大按钮 |
| 跨系统协同与恢复 | 15 | 支付、履约、渠道、财务、售后等延迟或失败时可解释、可重试、可恢复 |
| WCHS-MCBS 后端质量 | 15 | Operation、Handler、Repository、事务、幂等、Audit、Outbox 和所有权符合标准 |
| VI 1.2 与可访问性 | 10 | 视觉统一、响应式、键盘、触控、状态语义和密度均通过真实浏览器验收 |
| 测试、性能与发布证据 | 5 | Journey、恢复、性能、构建、发布和回滚证据完整 |

除总分达到 95 分外，下列任一红线未通过时，最终得分最高只能是 8.9 分：

1. 生产仍以 Preview、Fixture、Mock 或本地静态数据冒充真实订单能力。
2. Console 与 Storefront 使用两个可写订单事实源，或存在订单双写、回写、自动 Fallback。
3. `OMS-001` 至 `OMS-009` 任一核心闭环只有页面、按钮或接口名称，没有真实服务端行为。
4. 一个订单状态字段同时冒充支付、履约、售后、采购、发票或异常状态。
5. 订单模块直接修改支付、履约、渠道或财务拥有的数据。
6. 关键写操作没有版本冲突、幂等、Audit 或可恢复失败处理。
7. 支付成功、退款、退货、渠道 Unknown、财务失败等关键异常没有恢复 Journey。
8. 订单页面偏离已确认的 Smart Wing VI 1.2，或把方案图、架构图当成用户功能长期展示。
9. 关键角色的数据范围与已存在的组织 Scope 不一致。
10. 存在未关闭的严重数据不一致、严重 Journey 失败或无法回滚的发布缺口。

### **二、核心术语**

1. “Smart Wing OMS 2.0”是订单运营控制面，不是商城首页，也不是营销展示页。
2. “订单事实”指订单自身拥有的稳定业务事实，包括订单、订单行、子订单、订单快照、订单生命周期、售后、标签、备注和人工采购标识。
3. “跨系统摘要”指支付、履约、渠道、财务、发票、组织和客服系统通过契约提供给订单工作台的只读事实，不等于订单模块拥有这些事实。
4. “Order Workspace Projection”是为订单列表、筛选、指标、异常和导出构建的可重建读模型，不得反向写业务表。
5. “Watermark”表示读模型已消费到的事实时间或事件位置，用于解释数据新鲜度。
6. “异常订单”是由可解释原因形成的运营案件，不是新增订单主状态。
7. “人工采购标识”只表示运营人员已确认采购动作，不等于渠道系统已经受理外部采购。
8. “方案图”用于设计师和开发者理解系统关系，默认不作为一级业务功能展示。
9. “功能图”必须能够承载真实记录、状态、负责人、下一步动作和反馈；只有可操作时才能进入产品界面。
10. “WCHS-MCBS 1.0”全称为 **WCHS Modular Commerce Backend Standard 1.0 / WCHS 模块化商业后端标准 1.0**。

### **三、角色与数据范围**

| 角色 | 核心任务 | 数据范围 |
| --- | --- | --- |
| 平台 / 中台 Owner | 全域订单、售后、异常、统计、跨机构观察与恢复协调 | 全平台 |
| 机构管理员 | 机构订单、售后、异常、采购标识、导出和采购对账 | 当前机构及后代商城 |
| 子机构管理员 | 与机构管理员相同，但范围缩小 | 当前子机构及后代商城 |
| 商城管理员 | 商城订单、详情、标签备注、导出、批量下单和商城对账 | 当前商城 |
| 供应商 / 门店 | 发货、退货、售后处理以及与自己有关的履约信息 | 自己参与的子订单、履约单和售后单 |
| 客服 | 查看订单快照、物流、历史售后和时间线，发起已有权限允许的协同 | 当前工单授权范围 |
| 会员 | 下单、付款、确认收货、申请售后和查看进度 | 本人订单 |

角色只决定可见范围和允许动作，不得复制七套订单页面、七套订单状态或七套后端实现。

浏览器不得自行声明组织后代范围。订单系统只复用当前已经存在并确认的 Permission、Capability 和 Scope，不得在本升级中顺手新增权限策略或权限旁路。

### **四、锁定订单能力**

以下需求编号继承现有权威预案，不得另造第二套编号：

| ID | 能力 | 完成定义 |
| --- | --- | --- |
| `OMS-001` | 订单状态分组 | 待支付、待发货、已发货、已完成、已取消/关闭等视图由服务端真实筛选 |
| `OMS-002` | 订单详情 | 订单号、金额、收货人、商品行、供应商、账号、机构/商城、支付、履约、售后、发票/核销摘要完整 |
| `OMS-003` | 标签与备注 | 可新增标签、内部备注，支持筛选并保留操作者、时间和操作记录 |
| `OMS-004` | 层级可见性 | 平台、机构、子机构、商城、供应商和会员的数据范围与组织 Scope 一致 |
| `OMS-005` | 多维检索 | 时间、订单号、姓名/手机号、收货人、商品、供应商、类型、状态、商城、核销、开票可组合检索 |
| `OMS-006` | 采购标识 | 单条或批量标记已采购；人工标识与真实 Provider 采购状态分别表达 |
| `OMS-007` | 多模板导出 | 订单总表、发货表、自定义发货表、礼包/积分商城/机构对账等由服务端异步生成 |
| `OMS-008` | 售后工作台 | 申请、审核、退货、收货、退款、拒绝和完成的完整时间线可查看、可处理 |
| `OMS-009` | 异常订单 | 按可解释原因形成案件，不污染订单主状态，并可筛选、导出、恢复和关闭 |
| `OMS-010` | 批量下单 | 模板下载、上传、预检、选择供应商和下单账号、确认后扣减并建单，逐行返回结果 |
| `OMS-011` | 对账与结算 | 机构、商城、供应商和采购维度账单可追踪到订单和经济腿 |
| `OMS-012` | 订单数据中心 | 订单量、GMV、退款、净销售额、客单价、状态分布、趋势和退款原因均带 Watermark |
| `OMS-013` | 客服关联订单 | 工单显示订单快照、物流、历史售后和时间线，不直接改写订单事实 |
| `OMS-014` | 运费差额 | 用户展示运费、Provider 成本和平台补贴拆成报价与结算快照 |

`OMS-001` 至 `OMS-009` 是首个完整订单运营闭环，必须先于第二批能力完成。

`OMS-010` 至 `OMS-014` 属于紧邻订单的第二批能力，不能被永久排除，也不能在第一批未闭环前制造大量空入口。

### **五、系统边界与高度协同关系**

| 系统 / 模块 | 向订单系统提供 | 订单系统向其提供 | 禁止行为 |
| --- | --- | --- | --- |
| 商品与库存 | 商品、SKU、价格、库存预占/释放/确认摘要 | 订单创建、取消和售后所需稳定事实 | Order 直接改库存表 |
| 支付 | Intent、Attempt、Payment、Refund 和回调结果 | 应付金额、订单引用、退款业务请求 | Order 直接扣款或改支付状态 |
| 履约与物流 | 包裹、发货、轨迹、签收、退货和质检 | 可履约订单行、收货快照、取消/退货业务事实 | Order 直接改包裹或物流事实 |
| 渠道接入 | Provider 采购、外部单号、受理、Unknown 和恢复状态 | 采购请求和订单快照 | Channel 直接访问 Order 数据库 |
| 财务与对账 | 凭证、账单、结算、发票、对账和差异摘要 | 已确认的订单和现金经济事件 | Order / Payment 直接写财务表 |
| 卡券与权益 | 抵扣、占用、释放和权益快照 | 订单确认、取消和逆向业务事实 | 权益变化改写历史订单快照 |
| 组织与权限 | 组织树、Scope 和当前身份 | 订单查询所需 Scope 请求 | 接受浏览器声明的后代范围 |
| 客服 | 工单、消息和协同记录 | 稳定订单快照与售后引用 | 客服工单直接改订单、退款或库存 |
| 分销返佣 | 返佣归因和结算状态摘要 | 可结算订单业务事件 | 返佣失败阻塞订单完成 |
| 数据报表 | 经营分析和长期聚合 | 可重放订单事件和 Projection | 报表成为订单写入者 |

跨系统协作只能通过明确的 Command、Query、Public Port 或 Domain Event 完成。

每个关键协同节点必须说明：

- 触发者
- 前置状态
- 输入
- 同步或异步
- 主动握手或被动触发
- 所有权
- 状态变化
- 超时发现
- 重试与幂等
- 最终失败位置
- 人工恢复
- 用户反馈
- 运营告警
- 对应逆向节点

### **六、状态与数据所有权**

禁止用一个 `status` 字段承载全部含义。至少保留下列独立维度：

| 状态维度 | 示例状态 | 权威模块 |
| --- | --- | --- |
| Order Lifecycle | `created / awaiting_payment / paid / fulfilling / shipped / received / completed / cancelled` | Order |
| Payment | `unpaid / authorizing / paid / partially_refunded / refunded / failed` | Payment，投影到订单工作台 |
| Fulfillment | `unallocated / allocated / processing / shipped / delivered / received / cancelled / returned` | Fulfillment，投影到订单工作台 |
| Aftersale | `none / applied / reviewing / approved / returning / received / refunding / resolved / rejected` | Order Aftersale |
| Procurement Marker | `unmarked / marked` | Order Annotation |
| Provider Purchase | `not_required / pending / submitted / accepted / unknown / failed / cancelled` | Channel |
| Invoice | 复用 Finance / Invoice 已有状态 | Finance |
| Exception Case | `open / investigating / waiting / recovering / resolved / dismissed` | Reporting / Exception Projection |

每个核心对象只能有一个写入者。至少明确：

- Order / OrderLine / Suborder
- OrderSnapshot
- OrderAnnotation / OrderTag
- Aftersale / AftersaleLine
- Payment / Refund
- Fulfillment / Package / Return
- ProviderPurchase
- Invoice / Journal / Statement / Reconciliation
- OrderWorkspaceProjection
- OrderExceptionProjection
- ExportRequest / ExportArtifact
- BatchOrder / BatchOrderRow

历史订单必须保存商品、SKU、价格、优惠、权益、收货信息、组织、供应商、运费和资金分配快照。后续配置变化不得改写历史事实。

### **七、锁定交互原则**

#### **1. 页面层级**

一级订单入口默认只呈现真正的运营工作台，不展示设计师方案图。

建议产品层级：

1. 订单总览与订单列表。
2. 订单详情。
3. 售后工作台。
4. 异常订单工作台。
5. 导出任务中心。
6. 批量下单任务中心。
7. 对账入口或订单关联摘要。

不为一个没有独立任务目标的页面制造二级或三级导航。

#### **2. 系统协同关系图**

系统协同关系图首先是架构与方案资料，默认隐藏在设计文档或帮助说明中。

如果需要进入产品，必须转化为“订单协同异常”功能，至少具备：

- 真实异常记录
- 来源系统
- 受影响订单和事实
- 当前状态
- 当前负责人
- 最近一次事件
- 阻塞原因
- 下一步动作
- SLA / 等待时长
- 重试、转交、关闭或查看详情
- 完整处理时间线

只有说明“发生了什么、谁负责、下一步做什么”的内容才是功能；单纯把多个系统画在订单周围不算功能。

#### **3. 刷新机制**

刷新能力有必要，但 Hero 中的大型“刷新数据”按钮没有必要。

锁定规则：

1. 页面首次进入时自动获取数据。
2. 切换组织范围、筛选条件、分页和视图时自动获取对应服务端结果。
3. 浏览器窗口重新获得焦点时，如果数据超过新鲜度阈值则自动刷新。
4. 标签、备注、售后、异常恢复等动作成功后，只刷新受影响的查询和详情。
5. 后端具备事件或推送能力时优先使用事件失效通知；没有时再根据测量结果决定 30～60 秒轮询。
6. 页面隐藏时不得无意义高频轮询。
7. 右上角显示“数据更新于 HH:mm”或 Watermark，并在其旁保留一个紧凑刷新图标作为故障兜底。
8. 桌面端刷新图标视觉尺寸保持紧凑；移动端可视尺寸可小，但可点击区域不得小于 44px。
9. 刷新中不得清空已有列表；使用 Refreshing / Stale 状态表达。
10. 刷新失败保留已有数据并说明错误，不得把旧数据伪装成最新数据。

#### **4. 动作位置与层级**

1. 全局动作放页面上下文区，订单动作靠近订单或详情，售后动作靠近售后案件，异常恢复动作靠近异常案件。
2. Hero 只承担身份、范围、目标和关键摘要，不做营销大图，不堆放次级按钮。
3. 导入、导出、批量操作必须说明范围、后果、进度、部分失败和结果下载位置。
4. 危险或不可逆动作必须复用已有确认模式，不新增未经确认的安全门禁。
5. 禁用按钮必须显示 Disabled Reason，不能让用户猜测。
6. 批量操作只作用于显式选中的 ID 集，不得把“当前筛选结果”默认为全部目标。
7. 所有动作必须有 Pending、Success、Partial Failure、Conflict 和 Retry 反馈。

#### **5. 信息密度**

1. 订单列表保持可比较的表格密度，不把大表强塞进窄 Master 列。
2. 详情使用分组摘要、时间线和稳定的金额对齐。
3. 售后和异常适合使用竖向 MasterDetail：左侧案件列表，右侧快照、时间线和动作。
4. 指标只展示能够驱动运营动作的数据，不制造无决策意义的卡片。
5. 所有金额使用整数分作为后端事实，前端使用 Financial Font 和 Tabular Numerals 展示。

### **八、WCHS-MCBS 1.0 后端标准**

1. **单运行时事实**：生产只有一个 Commerce 制品；API、Jobs 和 Migration 使用同一代码和 Contract Hash。
2. **单数据库事实**：PostgreSQL 是订单交易事实源；缓存和 Projection 可重建。
3. **Operation First**：接口先登记 Operation、Owner、Schema、错误、Scope、幂等、版本、Handler、SDK 和 Requirement ID。
4. **一 Operation 一真实 Handler**：Handler 只编排一个用例，不得成为转发到通用 Operations 的空壳。
5. **固定依赖方向**：`interface → application → domain ← port ← infrastructure`。
6. **模块 Schema 所有权**：模块只通过自己的 Repository 写自己的对象；跨模块使用 Public Port 或 Event。
7. **不透明事务上下文**：Handler 和 Public Port 看不到 PG Client、`query()`、commit 或 rollback。
8. **强一致与最终一致分开**：强事务使用同一事务；Provider、导出、通知等使用 `prepare → commit → finalize` 和 Outbox / Inbox。
9. **显式状态与版本**：状态维度独立，更新使用 expectedVersion / CAS，金额使用整数分，业务快照不可变。
10. **唯一 Catalog 和生成物**：Operation、Event、Error、Permission、Module、Provider、Ownership 和 Requirement 各有唯一权威来源。
11. **可证明质量**：Unit、Repository Integration、Contract、Journey、Performance、Recovery 和架构检查组成同一质量证据链。
12. **单路径切换**：生产不保留同一订单能力的新旧双路径、双写、Fallback、Simulation 或兼容别名。

Smart Wing OMS 2.0 的目标不是把现有订单页面做得更大、更蓝或更复杂，而是让运营人员能够在同一个可信工作台中：

> **看见真实订单 → 理解当前状态 → 定位责任系统 → 执行允许动作 → 处理异常 → 验证结果 → 保留完整证据。**

真正的 9.5 分来自五件事同时成立：

1. 订单事实唯一可信。
2. 核心业务能够正向完成、逆向恢复。
3. 跨系统延迟和失败可解释、可追踪、可处理。
4. WCHS-MCBS 后端边界和质量可以被代码证明。
5. Smart Wing VI 1.2 让复杂能力保持清晰、克制和高效。

视觉只能决定第一印象；真实业务闭环、后端事实和故障恢复决定订单系统能否从 8.2 分真正提升到 9.5 分。
