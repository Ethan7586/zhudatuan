# 双重事实源审计（2026-08-20）

## 1. 审计口径

本审计不把“代码长得像”等同于业务重复。只有两个入口能独立决定同一业务事实，并且可能得到不同结果，才认定为双重事实源。核对优先级是资金、权限、幂等、输入校验、商城发布和运行配置。

每个确认项按四个条件验收：唯一 canonical source、读写调用点、旧路径删除或失败关闭、分歧回归测试。

## 3. 高风险项详细结论

### 3.1 distributorId

`membershipContext.ts` 只从 `scopeBindings` 取互异 distributor ID，且数量必须恰好为 1。`membership.context.distributorId`、cookie 和 client 都不能覆盖这个结果。DB canonical binding 使用 `distributors.id`，`org_unit_id` 仅是组织树锚点；关系失效、分销商停用、绑定歧义都会失败关闭。

### 3.2 传输幂等与业务幂等

Header 是命令 ID 的唯一传输来源，DB 才是命令结果的权威源。两者是单向投影，不是两个可以各自决定的键。DB 重放除了比较 hash，还比较 resource、scope、金额和 tender 组成，防止可信调用点回归成“同 hash 换命令”。

### 3.3 资金事实与投影

`payments`、`refunds`、余额 ledger、PaymentIntent 和 Journal 有不同语义，因此不能为了清除表面重复而合表。约束、同事务写入、Outbox/Inbox 以及 reconciliation 保证它们不能静默分叉。Tender 的 `succeeded` 表示尚未全退，累计全退后统一为 `refunded`；不可变 capture Journal 保留原支付事实。

### 3.4 商城配置

V2 DSL 只存在现有 `mall_application_versions.config_json`。编辑、保存、发布、恢复均经严格 parser 和 DB 权限边界。找回归档中的旧 layout DSL 未复制，只用于评估 V1→V2 转换。

### 3.5 库存硬切换

`public.inventory` 曾被 6 个读 RPC、3 个写 RPC 和 ABO REST 脚本独立读写，与 Reservation 状态机会产生可售量分歧。`20260820133000` 冻结该快照：零保留且无 canonical activity 的行自动审计切换；其余行保持 `manual_review`、对外可用量为 0，只允许平台 Owner 在 DB 重验权限、Scope、Session 和 StepUp 后按实物盘点审核。目录、购物车、后台和供应商快照统一读写 canonical 表，旧表和测试入口在同一硬切换迁移末尾删除。

## 4. 相似度窗口分类

`04_tools/scripts/audit/duplicate.mjs` 会继续打印归一化 8 行滑窗，但它们只是人工语义审查输入，不再自动当作发布缺陷。本轮剩余窗口归为：

- UI Props、商品卡片、券按钮与多端布局的展示模板；不能改写 DB 事实。
- 小程序页面生命周期、abort/resize 样板；不拥有支付或订单状态机。
- 只读类型镜像、package re-export 和审计脚本 parser；不产生运行时业务决策。
- RPC 命令 envelope 的结构相似；每个 RPC 的 resource/hash/scope 仍由 DB 幂等记录权威判定。

上述窗口不影响资金、权限、幂等、输入、商城发布或库存结果。需注意，相似度脚本输出 0 不能代替上述库存语义契约。

## 5. 仍未允许冒充完成的边界

- 生产 DSN 目标身份指纹已与运行项目匹配，但直连端点仅提供 IPv6，本机无 IPv6 路由；未发出任何 SQL。因此生产 `schema_migrations` 历史、表总数和 platform org unit `active` 状态仍是 unknown。旧源码谱系与生产对象缺失只支持把未发布候选 `voucher_operations_foundation` 改为本地唯一版本 `20260820110000`，不得把这次仓库消歧写成生产 ledger 事实。
- 历史 `apply-mall-application-builder.sh` 是直接 `psql --file` 并写 success marker，不登记 Supabase 迁移账本；未来必须把 `20260818120000` 的 ledger 记录与对象效果交叉核对，不得用 `.ok` 或对象存在推断迁移历史。
- 旧服务器源码谱系、六组历史 `.ok` 与可读 dump 只能证明曾有 raw-SQL 运维动作；marker 不含目标项目、迁移 name、statements 或 hash。即使脚本默认项目与当前运行时项目的标识哈希相符，也可能被环境覆盖，不能据此补写 ledger 或判断重复版本已发布。
- 仅直接确认生产运行时项目缺少 `distributors` / `distributor_tenants` / `distributor_sync_runs`。
- 生产只读 RPC 已确认 `ethan` 当前有且仅有一个有效平台 Owner 管理 membership；这不是密码登录或 migration ledger 证据，部署后仍须由用户本人完成登录、会话刷新与权限 E2E。
- `npm run replay:fresh` 明确拆成两段：空库 portable schema + 全部 SQL contracts，以及带显式 `ethan` fixture 的 environment bootstrap/reconciliation 重放。环境绑定迁移不再被伪装成“无前置数据的纯 schema”；最终 reconciliation 从组织树声明式补齐 Owner scope，并停用全部测试身份。
- 内部+微信/券混合 Tender 和部分退款分配规则没有正式签字；当前必须失败关闭，不得臆造财务规则。
- 退货签收/QC/入库、外部履约和正式消息投递、人工死信 UI/API 仍是独立未完成能力，不能因为已有 durable pending/deadletter 事实就宣称闭环。
- 找回的旧分销/佣金/装修归档是评估证据，不是可直接运行或复制的权威实现。
