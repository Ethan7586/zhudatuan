# AU-415｜微信退款闭环

## 范围与方法

- 主审文件：`02_platform_pingtai/database/supabase/migrations/20260820128000_wechat_refund_closure.sql`（1,417 行）。
- 交叉核对：退款申请、命令、通知、终态、事件、财务对账与 ACL 契约测试；Commerce 退款运行入口的精确调用检索。
- 本批为静态调用链与迁移语义审阅；未执行数据库重放、构建或线上操作。

## 运行结论

该迁移建立微信退款的完整闭环：受权退款申请生成可租约领取的 provider 命令；供应商接受仅推进为待查询状态，只有经严格证据核验的成功通知才生成退款成功事件。事件执行在订单—支付—尝试锁边界内更新退款、支付与售后状态，写退款财务分录、客户/运营通知并以 inbox 去重；金额上限、重复提供商 ID、终态冲突、过期租约、退避与死信均被限制。退款分录与既有捕获分录保持双录平衡，授权财务对账会检测支付、退款、账本和状态失配。

所有内部表与原语均关闭直接访问，受限 RPC 的权限矩阵按服务角色区分。退款契约覆盖申请幂等、命令/通知/事件生命周期、终态、ACL、内部退款和对账。

固定基线未找到这些 canonical RPC 的仓内运行消费者，Commerce 运行代码也未出现对应调用，且仍存在另一退款路径。该结论不能证明废弃：迁移会补记历史退款分录，并且支付提供商 webhook、生产 service-role 作业和历史资金数据均在仓外/运行时范围。
