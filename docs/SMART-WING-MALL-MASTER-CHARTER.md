# 智慧翼企业福利商城总纲

版本：1.0  
日期：2026-08-13  
性质：产品思想、商业模型、会员体系、权限与资格、设计、技术和交付的共同上位文件  
Owner：Ethan（全系统唯一 Owner）

> **智慧翼不是把普通电商换一个蓝色皮肤。它要把企业发出的每一份福利，与员工真实得到、理解和使用的每一份价值连接起来。**

> **让每一份福利，被看见、被理解、被善用。**

## 0. 如何使用这份总纲

这份文件回答五个问题：

1. 智慧翼为什么存在，以及它与普通商城有什么本质区别。
2. 员工、企业、平台、供应商和合作门店分别能得到什么。
3. 会员、权限、资格、交易、支付、会员码和 AI 如何组成一个系统。
4. iOS、Android、微信小程序、Web 商城和管理后台如何使用同一套 VI 与业务规则。
5. 仓库中的每一类代码、数据库和文档负责什么，哪些已经实现，哪些仍需外部资质或正式联调。

它是项目的上位解释，但不是用来覆盖更精确的机器可读定义：

- 数值与颜色以 `packages/design-system` 的令牌为准。
- 权限编码以 `packages/api-contract/src/permissions.ts` 为准。
- 实际鉴权以 `packages/authz` 与数据库约束为准。
- 数据结构以 `database/supabase/migrations` 的追加迁移为准。
- 接口行为以 `services/commerce-api` 为准。
- 已批准页面构图以 `docs/mobile/design-previews` 为准。

任何实现如果与本总纲的核心思想冲突，应停止并由 Owner 决策；任何图片如果与正式令牌冲突，以令牌为准。

## 1. Ethan 的核心思想

### 1.1 从“发福利”转向“福利真正被使用”

传统企业福利常见四个断点：

- 企业知道花了多少钱，却不知道员工是否真正得到价值。
- 员工知道自己有福利，却不知道能买什么、为什么不能买、什么时候会过期。
- 商品、实体券、商超、餐饮和生活服务分散在不同入口，身份和资产无法统一。
- 管理者靠 Excel、群消息和人工审批维持规则，无法解释一次购买为什么被允许或拒绝。

智慧翼要建立一条完整价值链：

```text
企业福利预算
  → 员工唯一会员身份
  → 可见、可买和限售资格
  → 福利商品、服务与实体/电子券
  → 会员码核验与交易履约
  → 资产和消费行为沉淀
  → 可解释的 AI 洞察与行动建议
  → 更高的福利使用率与员工获得感
```

这不是为了鼓励无意义消费，而是减少福利浪费，让员工在正确时间、正确场景使用自己真正拥有的权益。

### 1.2 AI 时代，会员码是中央入口

会员码不是底栏中一个二维码按钮，也不是支付码的翻版。它是一个人的福利数字身份入口：

```text
会员码
├─ 我是谁：会员、企业、部门、等级、认证状态
├─ 我拥有什么：福利余额、餐卡、积分、实体券、电子券
├─ 我能做什么：可见商品、可买范围、适用城市、合作门店、限购额度
├─ 我做过什么：订单、核销、消费结构、节省金额、常购场景
└─ 下一步做什么：到期提醒、采购清单、再买一次、附近门店、组合支付
```

因此，智慧翼移动端的固定五栏是：

`首页 / 分类 / 会员码 / 订单 / 我的`

会员码位于中央，是三端唯一的品牌级超级入口。它连接线上商城和线下核销，连接静态会员身份和动态场景行动，也连接今天的福利账户与未来的智能消费管家。

### 1.3 一个真人，只建立一个 Member

账号、手机号、微信和企业微信不是四个用户，而是同一个人的四种登录别名：

```text
Member
├─ local_username：账号密码
├─ local_phone：经短信验证的手机号
├─ wechat：微信 OpenID / UnionID
└─ wecom：企业微信身份
```

所有会员关系、福利资产、订单、卡券、权限和审计历史都归属于同一个 Member。后续绑定新身份时追加别名，不重新创建会员，避免一个人出现多个余额、多个订单历史和多个权限身份。

### 1.4 身份、权限、资格是三件不同的事

- **身份认证**回答：你是谁，这次验证强度够不够。
- **后台权限**回答：你能管理什么业务和什么数据范围。
- **员工购物资格**回答：你能看见、购买或核销哪些资源。

三者不得混为一个“角色”字段，也不能只靠隐藏菜单或前端筛选。

### 1.5 只有一个 Owner

全平台唯一 Owner 是 Ethan。Owner 不是普通管理员的最高档角色，而是平台最终控制权：

- Owner 不允许通过注册、导入或角色复制产生。
- 其他人员只按职责获得管理员、运营、客服、商家、财务或资格审批人权限。
- 双人审批中的第二人是被授权的审批人，不等于第二个 Owner。
- Owner 的保留、恢复、交接和紧急访问必须具有独立审计与强认证。

### 1.6 HR 是数据来源，不是审批领导

未来 HR 系统可以同步部门、城市、在职状态和员工标签，但不自动进入业务审批链。资格规则由有权限的运营人员配置，高风险变更由独立资格审批人审批。外部 HR 标签必须保留来源，不能被人工悄悄覆盖。

### 1.7 开放合作，但智慧翼始终是主平台

麦德龙、沃尔玛、山姆、大润发、永辉等可以成为商品、门店或履约来源。智慧翼不是复制这些商超的页面，也不把自己变成某一家商超的附属入口：

- 智慧翼负责会员、企业资格、福利资产、订单总览与售后入口。
- 合作商负责授权范围内的商品、库存、门店、配送、核销或售后履约。
- 用户必须看得懂商品来自哪里、谁履约、谁负责售后。
- 未取得书面授权前，只使用中性文字标签和演示占位，不冒用 Logo、专属色或“官方合作”表述。

## 2. 产品定位：一套企业福利数字基础设施

智慧翼由四个系统组成：

| 系统         | 核心问题                                       | 主要对象                   |
| ------------ | ---------------------------------------------- | -------------------------- |
| 福利交易系统 | 商品、库存、购物车、订单、支付、售后如何闭环   | 员工、供应商、财务、客服   |
| 会员身份系统 | 一个人如何跨账号、手机、微信保持唯一身份       | 会员、安全管理员           |
| 企业资格系统 | 不同企业、部门、城市和标签员工能看见与购买什么 | 员工、企业运营、资格审批人 |
| 平台治理系统 | 谁能管理什么、管理多大范围、如何审计与追责     | Owner、管理员、运营、审计  |

四者共用一个服务端事实源。任何客户端都不能自行决定余额、资格、权限、价格、库存、订单或支付结果。

### 2.1 五类参与者

#### 员工/会员

- 一个入口看清所有福利资产。
- 明确知道可见、可买、限购和不可购买的原因。
- 在线购物，也能在合作门店出示会员码、实体券或电子券。
- 手机未认证时可以浏览和管理账号，但不能进入个人付款。
- 获得可解释、可关闭的 AI 消费建议。

#### 企业客户

- 建立本企业、部门、员工、福利计划和商城范围。
- 配置企业专区、城市专区、商品池和限售规则。
- 看汇总使用效果，不默认窥视员工个人消费明细。
- 在员工入职、调岗、离职时即时更新资格。

#### 智慧翼平台

- 管理租户、分销、企业、商城、会员与治理规则。
- 统一接入供应商、品牌、门店、支付和身份服务。
- 保持跨租户隔离、审计、对账、风控和故障恢复。

#### 供应商/合作商/门店

- 在明确协议、品牌授权和服务范围内供货或履约。
- 只看到本次履约所需的最小会员信息。
- 使用核验端完成会员码或券核销，支持撤销、冲正与审计。

#### 管理与服务人员

- 运营管理商品、会员、资格和活动。
- 客服处理授权范围内的订单与售后。
- 财务完成支付配置、结算、发票、对账和差错处理。
- 审批人处理高风险资格变更，申请人不能审批自己。

## 3. 完整业务闭环

```text
注册/企业邀请/微信进入
  → 绑定唯一会员身份
  → 选择有效企业会员关系
  → 服务端计算认证等级、角色、数据范围与购物资格
  → 首页发现福利、商超、专区、卡券和服务
  → 商品目录先过滤不可见内容
  → 详情解释可买/不可买、城市、限购、配送和售后
  → 加入购物车时重新校验
  → 结算预览重新计算价格、库存、资格和账户
  → 创建订单事务内最终校验并锁定库存
  → 福利余额/餐卡/券/积分 + 个人支付组合
  → 后端确认支付和订单状态
  → 供应商或门店履约
  → 会员码/券核验、收货、售后、退款与对账
  → 交易证据进入流水与不可变审计
  → AI 基于本人授权数据形成洞察与行动建议
```

每一个箭头都必须有状态、有失败处理、有审计证据，不能只画成功路径。

## 4. 会员与账号体系

### 4.1 注册策略

首期采用“账号 + 密码 + 企业邀请码”注册：

- 自助注册只能创建普通员工会员。
- 用户名全局唯一且不区分大小写。
- 密码只保存独立盐值哈希，不保存明文。
- 邀请码决定进入哪个企业/商城以及初始员工关系。
- 管理员、客服、运营、商家和 Owner 不能通过自助注册获得。

### 4.2 认证等级

| 等级    | 获得方式           | 能力                                 |
| ------- | ------------------ | ------------------------------------ |
| account | 账号密码注册并登录 | 浏览、收藏、购物车、密码和设备管理   |
| phone   | 完成真实短信验证   | 提交订单、进入个人付款和更高信任动作 |

“手机未认证不能付款”必须同时存在于页面解释、Commerce API 校验和数据库事务授权中。篡改按钮或直接调用接口不能绕过。

### 4.3 未来身份接入

- 短信：绑定/换绑手机号、找回密码、提升认证等级。
- 微信：`wx.login` 换取服务端会话，再绑定现有会员。
- 企业微信/SSO：通过企业权威身份建立或关联会员关系。
- 身份合并：出现同一真人多个历史会员时必须走受审计的冲突处理，不能自动合并资产。

### 4.4 安全中心

- 修改密码必须校验当前密码。
- 找回密码必须使用真实验证渠道，并撤销全部旧会话。
- 换手机需要当前凭证、旧/新身份验证和风险审计。
- 显示当前设备与登录会话，可下线单个或其他全部设备。
- 密码、手机、角色、范围和会员状态变化后，旧会话必须即时或下次请求失效。

## 5. 会员生命周期与运营中心

完整生命周期：

```text
邀请 → 注册/后台建档 → 账号认证 → 手机认证 → 入职/激活
→ 调岗/换部门/换城市 → 权益与权限变化 → 暂停/冻结
→ 离职/停用 → 会话、会员码和资格即时失效 → 重新启用或归档
```

会员运营中心应支持：

- 创建企业邀请码、有效期和使用限制。
- 后台创建普通会员，但不能看见或设置用户明文密码。
- 编辑非敏感资料，敏感变更进入更高认证和审计。
- Excel 批量导入、逐行错误报告、幂等重试和导入历史。
- 查看会员状态、认证等级、组织位置、角色与范围摘要。
- 停用、离职、重新启用和强制下线。
- 操作历史说明谁、何时、为什么、依据什么权限进行了变更。

## 6. 组织、商业资源和多租户

### 6.1 严格组织层级

```text
平台 Platform
├─ 分销 Distributor（可选）
└─ 安全租户 Tenant
   └─ 集团 Enterprise
      ├─ 商城 Mall
      └─ 部门 Department
         └─ 子部门
```

- Tenant 是安全隔离边界，不承担平台或分销的混合语义。
- 平台是全局治理根，平台范围只授予受保护角色。
- 分销层可以覆盖名下多个安全租户，但必须由数据库验证祖先关系。
- 集团、商城和部门不能跨安全租户拼接。
- 祖先路径来自服务端数据库闭包关系，不接受浏览器自报路径。

### 6.2 商业资源不是组织树

供应商、品牌、门店与商城是多对多经营关系：

```text
供应商 ─经营/供货→ 品牌
品牌   ─拥有/授权→ 门店
供应商 ─供货协议→ 商城
品牌   ─销售授权→ 商城
门店   ─履约/核销→ 企业、商城或区域
```

它们必须通过显式关系表建模，不能为了图省事塞进单父级组织树。跨商城、跨品牌或跨租户合作必须有协议、有效期和授权证据。

### 6.3 商品池

- 上游来源池：供应商或合作平台提供的候选商品。
- 商城已选池：当前商城正式选择的 SKU。
- 组合池：节日、健康、办公、家庭等主题组合。
- 城市专区：受城市可见/可买规则控制的商品集合。

商品出现在目录之前，至少要满足有效商品、有效库存/供货关系、商城商品池、品牌授权（如配置）和当前资格策略。

## 7. 后台权限系统

### 7.1 RBAC + 数据范围 + 明确禁止

权限不是一个管理员布尔值，而是：

```text
最终授权 = 有效会员关系
         + 角色允许的权限
         + 命中的数据范围
         - 明确禁止
         + 必要的二次验证
```

当前共享目录已定义 85 个权限，覆盖账号安全、商业资源、资格、商品、库存、订单、售后、卡券、财务、会员、角色、组织、商城、供应商、门店、客服、审计、接口和平台治理。

### 7.2 数据范围

范围包括：

`platform / tenant / distributor / enterprise / mall / supplier / brand / store / department / self`

组织型范围可以通过数据库祖先关系包含后代；供应商、品牌和门店范围必须查询商业关系，不能假设天然父子关系。

### 7.3 决策原则

1. 默认拒绝。
2. 无效或过期会员关系直接拒绝。
3. 明确禁止优先于任何角色允许。
4. 没有权限编码直接拒绝。
5. 没有命中服务端加载的数据范围直接拒绝。
6. 跨租户只允许经数据库验证的平台/分销祖先范围。
7. Critical 权限必须有新鲜的二次身份验证。
8. 结果返回授权证据，便于审计与解释。

### 7.4 角色中心

- 系统角色是默认模板，不可无痕篡改。
- 自定义角色支持创建、复制、编辑和停用。
- 授权工作流是：选人 → 叠加角色 → 数据范围 → 明确禁止 → 变更原因 → 保存。
- 角色、范围或禁止项变化需要提升 `authzVersion`，使旧会话失效。
- 高风险权限和范围授予需要二次验证；未来可按金额、数量、时间和职责分离引入条件风险规则。

## 8. 员工端资格系统

资格系统不是后台权限。它决定员工在某个时间、城市、企业和福利计划下能否看到、购买或核销某个资源。

### 8.1 资格事实

- 企业和组织节点。
- 部门及是否包含子部门。
- 员工/会员身份与状态。
- 城市和收货城市。
- 人工标签、HR 标签或外部来源标签。
- 福利计划、账户种类与有效期。

### 8.2 策略对象

- 资源：全部、商品池、SPU、SKU、城市专区。
- 对象：全部、企业、部门、员工、会员、标签。
- 动作：可见、可买、限额、价格层级或拒绝。
- 条件：城市、时间窗、账户、累计数量、购买频次和状态。

### 8.3 判定优先级

1. 缺少有效商业资源关系，直接不可见/不可买。
2. 明确拒绝优先。
3. 更具体的资源与对象优先。
4. 配置了 Allow 的资源必须至少命中一条 Allow。
5. 没有配置的新模块按兼容策略处理，但不能扩大跨租户范围。

### 8.4 六个强制执行点

1. 目录查询：不可见商品不返回。
2. 商品详情：重新校验并解释原因。
3. 加购物车：重新校验 SKU、数量、城市和有效期。
4. 购物车读取：资格失效时取消选中并提示。
5. 结算预览：重新计算资格、价格、账户和限额。
6. 创建订单：事务和锁内最终校验，防并发绕过。

订单要保存当时命中的策略版本和原因证据，之后才能解释“为什么当时允许购买”。

### 8.5 限售模板

- 支持 SKU 或 SPU 汇总。
- 支持单次、自然日、自然月、生命周期。
- 同时支持数量和金额上限。
- 以 Asia/Shanghai 作为业务边界。
- 下单时使用服务端事务锁，不能依赖前端计数。

### 8.6 资格治理

- 发布前预览影响员工、SKU 和状态变化。
- 高风险发布、停用或回滚进入双人审批。
- 申请人不能审批自己的申请。
- 历史版本不可改写；回滚创建新版本。
- 资格模拟器输入会员、SKU、城市和数量，返回完整判定路径。
- HR 同步只提供事实，不自动批准业务规则。

## 9. 商品、交易、支付与履约

### 9.1 商品与库存

- SPU 表达商品，SKU 表达可购买规格。
- 商品显示来源、门店/供应商、库存更新时间、配送、预计送达和售后责任方。
- 库存预占必须原子执行，失败时回滚整个下单事务。
- 不允许客户端裁决最终价格和库存。

### 9.2 购物车

- 购物车是服务端数据，多设备一致。
- 首页、分类、搜索、列表和详情保留全局购物车入口与角标。
- 不同供应商或履约方的商品在结算时解释拆单。
- 资格、库存和价格发生变化时局部更新，不让整个页面白屏。

### 9.3 订单

- 一个主订单可按供应商拆成多个子订单。
- 创建订单要求幂等键，同一键不能提交不同内容。
- 收货人姓名、电话和地址加密入库。
- 订单状态、支付状态、履约状态和售后状态分别建模，不能只用一个万能状态。

### 9.4 福利资产和组合支付

可组合：

- 福利余额。
- 餐卡余额。
- 电子券/实体券。
- 积分。
- 个人微信支付差额（接入真实渠道后）。

金额一律使用“分”的整数，禁止用浮点数。账户扣减在数据库行锁和事务中完成，分摊之和必须严格等于订单应付金额；不可变账户流水和审计日志禁止更新或删除。

### 9.5 微信支付

真实微信支付的正确链路：

```text
服务端创建订单并锁定资格/库存/价格
→ 预占福利资产
→ 计算个人差额
→ 服务端向微信申请 prepay_id
→ 小程序调用 wx.requestPayment
→ 服务端验签处理异步通知并主动查单
→ 确认订单与福利扣减
→ 失败/超时释放预占
→ 退款按原渠道退回并参与对账
```

前端“支付成功”回调不能作为到账证据。AppSecret、商户私钥、API v3 密钥和合作商密钥不得进入任何客户端。

### 9.6 会员码核验

- 二维码只包含短期、不透明、可撤销的挑战凭证。
- 默认 45 秒有效，成功核验后立即消费，截图不能重复使用。
- 会员停用、离职、冻结、切换主体或权限版本变化后立即拒绝。
- 核验人员必须登录，并受合作商、门店、设备和业务范围限制。
- 核验端只显示本次权益所需的最少信息，不暴露完整消费画像。
- 撤销、冲正和失败都有审计编号。

## 10. AI 消费管家

AI 的价值不是在首页放一个紫色闪光按钮，而是让员工理解并行动：

### 10.1 可以做

- 解释本月额度使用、剩余额度和消费结构。
- 找出即将到期的卡券和可能浪费的福利。
- 基于本人历史生成家庭、办公、健康或节日采购清单。
- 提醒常购商品、附近可核销门店和可使用券。
- 解释推荐依据、时间范围和适用资格。

### 10.2 不能做

- 未经本人确认付款。
- 修改企业额度、角色、资格或限售规则。
- 推荐资格范围外的商品。
- 把个人消费明细默认交给企业管理员或合作商。
- 用模糊模型输出替代库存、价格、资格和支付的确定性服务端判定。

### 10.3 AI 行动必须重新过规则

AI 只负责提出建议。用户点击行动后，商品仍需经过可见、可买、城市、标签、限售、库存、价格和支付门禁。每一条建议需标明“根据什么得出”和“用户下一步可以做什么”。

## 12. 统一 VI 与三端设计

### 12.1 同一品牌、同一业务、平台原生

Web、微信小程序、鸿蒙、iOS 和 Android 在以下方面必须一致：

- Logo、品牌色、字体层级、图标语义。
- 五栏导航和中央会员码。
- 会员卡、动态码、资格原因、资产和订单结构。
- 文案、状态、金额精度和业务规则。

允许不同的是平台原生交互：iOS 安全区与手势、Android Material 触控和系统返回、微信胶囊/自定义 TabBar/分包与后台刷新。

当前每项新业务能力以 Web + 微信小程序为强制交付对：共享合同、服务端状态机、同步/异步语义和错误码先确定，两端同批实现与验收。鸿蒙、iOS、Android 通过平台适配端口接入；身份凭据、支付调起、安全存储、分享、导航和生命周期可平台化，价格、资格、库存、订单、余额、支付结果和会员码规则不得平台化。单端完成不得表述为整体完成。

### 12.2 冻结品牌令牌

| 角色     | 色值      |
| -------- | --------- |
| 智慧蓝   | `#1F5EFF` |
| 交互深蓝 | `#174ED1` |
| 深海蓝   | `#143A8F` |
| 夜空蓝   | `#07182F` |
| 浅品牌蓝 | `#EAF1FF` |
| 页面背景 | `#F5F7FA` |
| 正文     | `#172033` |
| 成功     | `#0F9F6E` |
| 警示     | `#F59E0B` |
| 风险     | `#DC2626` |

品牌渐变：`135deg #1F5EFF → #143A8F`。

- 采用 8pt 网格。
- 小程序页面横向安全边距 32rpx。
- 圆角 8/12/16/24，禁止随意创造巨大圆角。
- 普通卡片优先边框，不堆重阴影。
- 图标统一为 2px 圆角线性风格，禁止 emoji 和 CSS 拼图。
- 图片失败使用正式本地占位，禁止浏览器破图标志。

### 12.3 设计到代码的方法

```text
读正式规范与全部设计板
→ 建立设计区域到组件/令牌/资产的映射
→ 只实现一个页面
→ 微信开发者工具或目标真机截图
→ 与批准稿同区域并排对照
→ 记录一致、有意适配、尚未完成
→ Owner 确认后进入下一页
```

不得一次写完全部页面再让 Owner 验收，也不得把批准稿当“灵感”自由重画。

### 13.2 前端职责

#### `apps/storefront-web`

已包含首页、分类、商品详情、购物车、结算、订单、支付结果、余额、流水、卡券、用户中心和售后等页面。浏览器只访问同源 `/api`，不接触数据库管理密钥。

#### `apps/admin-web`

包含经营驾驶舱、商品治理、订单履约、企业福利、财务对账、会员运营、会员权限、自定义角色、商业资源、员工资格、审批、历史、模拟和系统控制等工作台。前端隐藏不作为权限边界，所有读取和写入由服务端再次裁剪与鉴权。

#### `apps/auth-web`

负责账号登录、会员关系/主体选择、注册、忘记密码和二次验证界面。真实认证结果必须来自 Commerce API，任何演示万能密码、固定验证码或会员回退数据都不得进入正式流程。

#### `apps/wechat-miniapp`

目标为原生微信小程序，不使用 WebView 套网页。当前目录存在首页、分类、详情、购物车、会员码、订单、我的和自定义底栏代码，但它处于设计重建/重新验收状态，不能仅因“能编译”就视为视觉完成。开发前必须从 `00-新任务从这里开始` 进入。

### 13.3 服务端职责

`services/commerce-api` 是唯一可信业务边界，包含：

- 注册、登录、凭证发现、初始改密、找回密码和退出。
- 会话、账号安全、手机换绑、二次验证和身份保证等级。
- 会员关系上下文、权限与数据范围加载。
- 商品、首页、购物车、地址、账户、流水、订单和售后。
- 管理后台商品、会员、角色、权限、商业资源和资格配置。
- 资格预览、审批、历史、回滚和模拟。
- 测试支付模拟与财务对账。

客户端提交的用户 ID、会员 ID、权限、范围、员工标签、余额和支付结果都不是可信事实。服务端从会话与数据库重新加载。

### 13.4 共享合同与鉴权

- `packages/api-contract` 是前后端共享类型和 85 项权限目录。
- `packages/api-contract/src/platform.ts` 固定 Web、微信小程序、鸿蒙、iOS、Android 的平台端口与同步/异步通用语义。
- `packages/api-contract/src/delivery-matrix.json` 记录各业务能力的真实多端完成度；只有 Web 与微信小程序均为 implemented 才能标记 releaseReady。
- `packages/authz` 按会员有效性、明确禁止、权限、数据范围、跨租户边界和二次验证作出纯决策。
- 资源范围必须由服务端从真实数据库行获得，不能用请求参数伪造。

### 13.5 数据库方法

- PostgreSQL/Supabase 是权威数据源。
- 所有数据库演进通过追加迁移，禁止修改已应用历史迁移。
- RLS、撤权、受控 RPC、触发器和检查约束共同形成最后防线。
- 订单、库存、支付、限售使用数据库事务、锁和幂等。
- PII 加密入库，日志和导出按最小披露。
- 流水、审计和关键历史不可变。

## 15. 性能、Keep 与渲染手段

“拉数据慢”不能靠一个全局 loading 掩盖，必须从请求、服务端和渲染三层处理。

### 15.1 请求层

- 首页使用聚合接口，避免组件各自串行拉取形成瀑布。
- 互不依赖的数据并行请求。
- 同一请求去重，切页时取消已经无意义的请求。
- 短时缓存稳定字典和权限摘要；敏感余额、库存、资格和订单使用较短新鲜期并后台更新。
- 返回页面时先展示保留数据，再进行静默刷新；不能每次切 Tab 都整页清空。
- 修改成功只失效相关数据，不刷新整个系统。

### 15.2 服务端层

- 使用范围明确、分页、可索引的查询，禁止无界全表读取。
- 后台会员列表采用服务端分页、搜索和统计聚合，不一次传全部会员详情。
- 资格预览、权限摘要和首页数据由服务端聚合，减少网络往返。
- 对慢接口记录 P50/P95、查询耗时和请求 ID，不能凭感觉判断网络。

### 15.3 渲染层

- 首屏骨架而不是整页白屏。
- 大列表分页/虚拟化，稳定 key，避免无关组件重复渲染。
- 图片使用合理尺寸、懒加载、本地占位和失败回退。
- 列表筛选采用输入防抖，按钮提交防重复。
- 乐观更新只用于可安全回滚的低风险交互；余额、资格、订单和支付不得伪造成功。

### 15.4 诊断顺序

```text
先看本地编译错误
→ 再看浏览器/开发者工具 Network 与耗时
→ 再看服务端请求 ID、数据库和外部依赖
→ 最后判断代理/VPN/公网链路
```

不能看到白屏就先归因于 v2rayN；本地 WXSS/JS 编译错误与网络无关。

## 16. 安全与隐私原则

1. 默认拒绝，前端永远不是安全边界。
2. 密码、AppSecret、支付私钥、数据库密钥和合作商密钥不进入客户端或 Git。
3. Cookie 使用 HttpOnly、Secure、SameSite 和 Host-only 边界。
4. 微信小程序令牌短期、可撤销，并绑定会员与权限版本。
5. PII 最小采集、加密存储、脱敏展示、受控导出。
6. 登录、验证码和注册按可信来源限流；IP 白名单只能短期绕过限流，不能绕过认证。
7. 关键写操作有幂等键、版本号、原因和操作者证据。
8. Critical 操作使用二次验证；金额/数量型风险逐步升级为条件规则。
9. 会员停用、离职和权限变化后，会话与会员码失效。
10. 合作商只读取履约必需信息，不获得完整会员画像。
11. AI 数据用途透明、可关闭，账务与法定审计记录不因关闭 AI 被删除。
12. 生产不提供固定验证码、万能密码、模拟支付成功或身份回退。

## 21. 冻结决议

以下内容属于智慧翼路线基线，未经 Owner 明确确认不得修改：

1. 全系统只有一个 Owner：Ethan。
2. 智慧翼是企业福利数字基础设施，不是普通电商换皮。
3. 一个真人只有一个 Member，账号、手机、微信和企业微信是登录别名。
4. 身份、后台权限、员工购物资格和套餐能力分别建模。
5. 明确禁止优先于角色允许，关键操作需要二次验证与审计。
6. 组织层级和商业资源关系分别建模。
7. 资格在目录、详情、购物车、结算和下单全链路服务端执行。
8. 用户可见名称统一为“会员码”；底栏固定为首页/分类/会员码/订单/我的。
9. 会员码是身份、福利资产、实体/电子券、消费洞察与行动的中央入口，不等于支付码。
10. 手机未认证时可以使用基础会员功能，但个人付款被服务端阻止。
11. AI 只建议和解释，不拥有付款、权限、资格和额度修改权。
12. iOS、Android、微信小程序使用统一 VI 与业务，保留平台原生交互。
13. 合作商可以接入，但智慧翼保持主品牌、会员与交易治理入口。
14. 未取得资质、密钥和真实联调的短信、支付、微信与合作商能力不得宣称已开通。
15. 设计必须单页实现、真实截图对照、Owner 确认后再进入下一页。

## 结语

智慧翼真正的竞争力，不是页面多、按钮多，也不是简单拥有一个商城。它的核心是把企业、员工、福利资产、商品服务、线下门店和智能建议放进同一个可信的身份与规则系统里。

对员工，它应该越来越像一个理解自己福利生活的数字助手；对企业，它应该是可配置、可解释、可审计的福利经营系统；对合作商，它应该是边界清晰的履约入口；对平台，它必须始终可治理、可扩展、可回退。

会员码位于中央，不是为了视觉新奇，而是因为它代表了智慧翼最重要的产品判断：

> **先确认这个人是谁、拥有什么、在当前场景能做什么；然后帮助他把福利真正用好。**
