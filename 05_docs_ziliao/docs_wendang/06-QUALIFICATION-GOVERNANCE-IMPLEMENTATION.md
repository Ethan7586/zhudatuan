# 资格治理实现说明

## 本阶段交付

- 发布前影响预览：计算预计影响员工数、SKU 数、当前与目标状态，并返回命中的风险原因。
- 双人审批：高风险发布、停用或回滚只进入待审批队列，申请人不能审批自己的申请。
- 历史版本：从不可变审计记录读取服务端快照；回滚会创建新版本，不改写旧历史。
- 员工资格事实：管理员人工维护城市、状态与人工标签，每次变更要求原因和二次验证。
- 资格模拟器：选择当前商城员工、SKU、数量与测试城市，返回可见、可买、限制原因及命中规则。

HR 不进入审批链。当前阶段的员工事实由管理员维护；未来 HR 同步仅作为资料与标签来源。非人工来源标签在数据库层禁止被人工覆盖。

## 默认权限边界

| 权限                            | 用途                                 | 默认授予                     |
| ------------------------------- | ------------------------------------ | ---------------------------- |
| `employee_qualification.read`   | 查看员工城市、状态与标签；运行模拟器 | 仅 Owner                     |
| `employee_qualification.manage` | 人工维护员工资格事实                 | 仅 Owner                     |
| `qualification.approve`         | 审批高风险资格变更                   | Owner 与独立“资格审批人”角色 |

普通规则管理员继续使用商业资源、资格策略、限售模板各自的管理权限，可起草和提交申请，但不会自动获得审批权。数据库会再次核验审批权限、当前商城身份和“申请人与审批人不是同一用户/身份”。由于系统只允许一个 Owner，测试账号 `admin001` 预置为第二审批人；正式环境不自动指定人员，由 Owner 明确授予“资格审批人”角色。

## 高风险判定

以下场景进入双人审批：

- 把当前生效配置改为草稿或停用；
- 发布城市专区或限售模板；
- 发布明确拒绝策略；
- 发布覆盖全部员工或全部商品的策略；
- 商品池一次影响至少 50 个 SKU；
- 生效规则预计影响至少 100 名员工。

未命中高风险条件的发布在管理员完成二次验证后直接生效；草稿保存不影响员工端。

## 一致性与安全约束

- 配置保存、审批申请、审批落地均使用服务端主体、商城范围、幂等键和乐观版本。
- 审批时如果配置版本已经变化，申请自动标记为 `stale`，不会覆盖新配置。
- 所有历史快照和回滚源数据由服务端审计日志提供，浏览器不能提交伪造快照。
- 员工必须拥有当前商城的有效员工端身份，才能被维护或用于模拟。
- 员工事实变更保留人工标签与未来 HR/外部来源标签的来源边界。

- 管理后台本地浏览器视觉验收：审批、员工资格、历史与模拟三个界面无控制台错误。
