# 智慧翼认证、短信与运行可靠性评估

版本：1.0
日期：2026-08-15
范围：Web、微信小程序、Commerce API、阿里云 ECS/OSS/CDN/Tair、Supabase PostgreSQL

## 结论与评分

当前架构方向正确，但还不能称为“极致”或“无单点”。在微信注册与阿里云短信代码完成、生产配置和真实链路尚未验收的口径下：

| 维度           |   分数 | 结论                                                                                         |
| -------------- | -----: | -------------------------------------------------------------------------------------------- |
| 架构平衡       | 78/100 | 权威写库、只读镜像、媒体 CDN、统一 API 的边界清楚；运行实例与动态数据仍有单点和跨地域依赖    |
| 公开浏览性能   | 88/100 | 200 件目录快照、OSS/CDN 图片和本地缓存已形成快路径                                           |
| 登录后动态性能 | 68/100 | 北京 ECS 访问异云 PostgreSQL，会员、订单、安全链路仍受跨地域往返影响                         |
| 安全与一致性   | 84/100 | 客户端不接触数据库密钥；注册、绑定、支付和余额以服务端事务为准；仍需生产短信、迁移和灾备演练 |
| 可恢复性       | 63/100 | 有备份设计，但当前单 ECS、单进程副本和手工部署仍会扩大故障时间                               |

用户是否登录 Supabase Dashboard 与网站运行无关。运行服务使用服务器内的 `SUPABASE_URL` 和服务角色凭证访问数据库；浏览器后台登录状态既不参与请求，也不应该参与请求。

## 当前运行链路

```text
Web / 微信小程序 / 未来 iOS、Android、鸿蒙
              │
              ├── 公开目录快路径 ──► OSS + CDN / 目录快照 / 客户端缓存
              │
              └── 登录后业务 ─────► 北京 ECS + Caddy + Commerce API
                                             │
                                             ├── Tair 只读镜像
                                             └── Supabase PostgreSQL 权威事务
```

不可改变的边界：

- PostgreSQL 是会员、订单、支付、余额、库存预占和会员码消费的唯一真相。
- Tair、CDN、OSS 和客户端缓存只负责读加速，不得成为第二写库。
- 客户端只调用 Commerce API，不直连数据库，也不持有微信、短信或数据库密钥。
- 微信、Web 和未来原生端共享同一业务合同；平台端只做会话、安全存储、支付、分享和生命周期适配。

## 本次新增的两个闭环

### 微信新会员注册

```text
wx.login 一次性凭证
  → 服务端换取 OpenID
  → 未绑定时签发一次性绑定挑战
  → 用户填写用户名、密码、姓名、企业邀请码并同意协议
  → 单个 PostgreSQL 事务创建 Member + Membership + 微信绑定
  → 事务成功后签发小程序短期会话
```

OpenID 只证明微信身份，不证明企业归属。因此注册必须使用企业邀请码，禁止仅凭 OpenID 自动创建会员。会员创建和微信绑定在同一事务内完成；绑定失败时整个注册回滚，不留下孤儿会员或重复资产。

### 阿里云手机号验证

统一短信发送器服务于注册、找回密码和手机号认证：

- 生产环境仅允许 `SMS_PROVIDER=aliyun`；测试验证码只允许开发和测试环境。
- 服务端生成六位验证码，只将摘要写入数据库；阿里云只接收发送所需字段。
- 单次请求不自动重试，避免网络抖动导致重复短信和重复计费。
- 发送成功后挑战才进入 `sent`；发送失败立即作废，失败验证码不可继续使用。
- 手机号认证入口位于“小程序 → 我的 → 账号与安全”，需当前密码和短信验证码共同确认。
- AccessKey 优先使用绑定到 ECS 的 RAM 角色；如暂用专用 AccessKey，只授予短信发送最小权限。

## 反复报错和“断联”的真实原因

前期错误来自多个控制面问题叠加，并非一种网络故障，也不是 Supabase Dashboard 未登录：

| 现象                      | 已确认原因                                           | 是否影响真实用户                     |
| ------------------------- | ---------------------------------------------------- | ------------------------------------ |
| 本机偶发无法拉取 GitHub   | Windows 到 GitHub 443 的临时网络失败                 | 不直接影响已部署网站                 |
| 服务器能拉不能推          | 部署 SSH Key 是只读权限                              | 不影响运行，但会卡发布/回传          |
| 补丁应用失败              | 服务器 Git 未配置提交身份                            | 不影响运行，只影响手工发布           |
| 一次命令出现异常字符/变量 | PowerShell、SSH 和远端 Shell 多层引号混用            | 不影响运行，但会制造误判             |
| 数据库 REST 写入 403      | 受保护字段不允许直接更新，必须走安全 RPC             | 影响该操作；改为 RPC 后边界正确      |
| 商品更新后仍显示旧数据    | 进程内缓存未失效，需版本化缓存或 reload              | 会造成短期陈旧，不是断库             |
| CDN 首次 MISS/REFRESH     | `latest.json` 短缓存和新版本首次回源                 | 只影响首个请求；版本化资产命中后稳定 |
| 微信工具预览 code 10      | 本地项目列表仍记录 `touristappid`，与正式 AppID 冲突 | 影响预览/上传，不影响线上 API        |

这些问题的共同根因是发布链路仍依赖人工、跨终端复制和隐式本机状态。它们多发生在“控制面”（部署、工具、缓存刷新），不是用户访问的“数据面”；但如果不治理，会拉长故障恢复时间。

## 防止下次重复的发布标准

1. 发布前自动检查：工作区、分支、提交号、必要环境变量是否存在、数据库迁移是否已应用。
2. 固定发布身份：部署机使用专用只读拉取凭证；代码提交与服务器发布分离，不在生产机临时提交。
3. 一次发布脚本完成：拉取指定提交、安装锁定依赖、构建、迁移、原子切换、健康检查；任一步失败立即停止。
4. 健康检查分层：静态首页、公开目录、数据库读、微信登录、短信配置分别探测，不能用一个 HTTP 200 代表全部正常。
5. 缓存按版本发布：目录和图片使用不可变版本 URL；`latest` 只做短期指针；业务写入通过 outbox/版本号失效读镜像。
6. 全链路 Request ID：Caddy、API、数据库 RPC、阿里云短信记录同一个请求编号，便于一次定位。
7. 建立最小 SLO：公开目录可用性、登录成功率、短信发送成功率、API P95 延迟和数据库跨区延迟必须可观测。
8. 保留一键回滚：上一版应用包、上一份目录 manifest 和数据库向前修复脚本必须可用。

## 生产启用清单

代码完成不等于线上已启用。正式开放前必须全部满足：

1. 应用 `20260815123000_wechat_registration_aliyun_sms.sql` 迁移。
2. 阿里云短信签名和验证码模板审核通过。
3. ECS 已绑定仅允许发送短信的 RAM 角色，或配置专用短信 AccessKey。
4. 服务端设置 `APP_ENV=production`、`SMS_PROVIDER=aliyun`、`WECHAT_REGISTRATION_ENABLED=true`，并配置签名、模板和微信小程序服务端参数。
5. 重载 Commerce API 后，分别完成一笔新微信注册、一笔短信认证、一笔错误验证码和一笔重复提交测试。
6. 验证数据库只生成一个 Member、一条有效 Membership 和一条微信绑定；短信失败挑战不可使用。

## 下一阶段性能优先级

1. 先消除运行单点：Commerce API 至少双实例，Caddy/负载均衡健康摘除。
2. 再治理动态跨区延迟：测量北京 ECS 到 Supabase 的 P50/P95/P99；读多数据进入 Tair，所有写仍回权威库。
3. 最后准备数据库迁移：只有真实指标证明跨区数据库成为瓶颈时，再迁入同地域 PostgreSQL；迁移前先做双份可恢复备份和回放演练。
