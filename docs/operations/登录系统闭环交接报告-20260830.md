## 6. 当前真实阻塞：授权双时钟

### 6.1 复现结果

真实 Node HTTP + PostgreSQL 17 闭环已走过：

- 全部迁移。
- Owner 密码登录。
- PKCE/AuthTicket 单次交换及 replay 401。
- Owner 创建邀请。
- Owner 撤销另一枚邀请，撤销后解析 404。
- 受邀 operator 注册。
- OTP 登录成功。

随后新成员调用 `GET /api/v1/identity/session` 返回 403。

数据库诊断显示：

- membership active。
- access version 一致。
- `role:self` 存在。
- self scope grant 存在。
- `identity.session.read` permission 存在。
- `identity.session.read` capability 存在。
- resolve_scope 返回正确 `self:<principal>`。

但纯策略 `precheck` 返回 `PERMISSION_MISSING`，`checkScope` 返回 `SCOPE_DENIED`。

### 6.2 精确根因

Grant 的数据库时间：

```text
2026-08-30T02:37:29.98773+00:00
```

Node 决策时间：

```text
2026-08-30T02:37:29.486Z
```

数据库时钟比 Node 快约 501ms。`access.resolve_membership()` 已按数据库时钟筛选一次有效 grant，AccessPipeline 又按 Node 时钟二次判断，结果把刚刚生效的 grant 当成“未来权限”。Step-Up freshness 也有同类风险。

### 6.3 正确修复方向

不要 sleep，不要给注册 grant 特判回拨时间，也不要简单增加容忍窗口。

应让一次授权决策只有一个权威时间：

1. `PgMembershipResolver` 在同一条 SQL 中用 MATERIALIZED CTE 取得 `access.resolve_membership()` 结果和数据库 `evaluated_at`。
2. Resolver 返回 `{ access, evaluatedAt }` 形式的 snapshot。
3. AccessPipeline 使用这个数据库 snapshot 时间执行 permission、scope、assurance 和 Step-Up freshness 判定。
4. 移除 AccessPipeline 对应用 `SystemClock` 的授权依赖，并更新 Commerce、WebBusiness、Purchase、Identity Edge 构造点和测试。
5. 增加回归测试：即使 Node 时钟落后 501ms，数据库已认定有效的即时 grant/Step-Up 也不能误拒；真正未生效或已过期的授权仍必须拒绝。

## 11. 当前 main 的登录、邀约、手机验证码与 Owner 邀请闭环代码方案

本节是待实施方案，不表示代码已经完成。实施必须复用 Canonical Contract、SDK 和 `services/commerce`，不得在 Compatibility API 中再复制一套 Owner 权限真值。

### 11.1 安全目标与角色

系统只接受服务端权威角色，不接受前端传入角色、Scope 或 Owner 标记。

| 主体                   | 登录方式                                   | 可执行能力                                                                 |
| ---------------------- | ------------------------------------------ | -------------------------------------------------------------------------- |
| Owner（高级管理员）    | 密码或受控联合登录；敏感操作前短信 Step-Up | 管理邀请码、成员和权限；仍受 Scope、CSRF、幂等、审计和 Risk 限制           |
| Operator（普通管理员） | 邀请注册后使用手机号验证码或密码登录       | 仅获得邀请中固定的普通管理员角色和精确 Scope，不可创建 Owner 或 Owner 邀请 |
| 未认证用户             | 无 Session                                 | 只能解析受限邀请、申请验证码、完成注册和交换一次性 Ticket                  |

Owner 必须是租户内唯一有效 Owner。Owner 身份来自数据库约束和服务端投影，不以 `isOwner=true`、邮箱、手机号或前端菜单判断。

### 11.2 权威调用链

```text
Auth Web / Console
  → @shop/sdk
  → @shop/contract Operation
  → Commerce Identity Module
  → AccessPipeline（身份、权限、Scope、Capability、Step-Up、Risk）
  → Identity / Member / Access Port
  → PostgreSQL + Outbox
  → SMS Provider Worker
```

- `apps/auth-web` 只负责输入、PKCE、跳转和错误展示。
- `apps/console` 只负责 Owner 邀请管理界面。
- `services/commerce` 是身份、邀请和权限的唯一业务入口。
- Identity 编排注册流程，但不得直接写 `member.*` 或 `access.*`；必须调用 `MemberPort` 和 `AccessPort`。
- PostgreSQL RLS、Scope 函数和唯一约束是最后一道隔离边界。

### 11.3 闭环时序

#### A. Owner 登录与提升认证等级

1. Auth Web 生成 PKCE verifier/challenge，verifier 只保留在当前浏览器内存或受控短期存储。
2. 调用 `POST /api/v1/identity/sessions`，服务端验证 Owner 凭据、租户和 Membership 状态。
3. 服务端只返回短时、一次性 AuthTicket，不把 Session Token 放进 URL 或 Web Storage。
4. Auth Web 调用 `POST /api/v1/identity/tickets/exchange`，提交 Ticket、PKCE verifier、state 和 nonce。
5. API 设置 host-only、`HttpOnly`、`Secure`、`SameSite` Session Cookie，并单独设置可读取的 CSRF Cookie。
6. Owner 创建邀请码前，如果 `identity.invitation.manage` 的策略要求更高 assurance，则调用 Step-Up start/complete，以当前 Owner 和当前 Session 绑定短信验证结果。

#### B. Owner 生成和撤销邀请码

1. Console 调用 `POST /api/v1/identity/invitations`，只提交手机号、显示标签和客户端请求幂等键。
2. AccessPipeline 验证：当前唯一 Owner、`identity.invitation.manage`、tenant 根 Scope、Capability、最近 Step-Up 和 Risk。
3. 服务端固定邀请结果：`target=console`、`role=operator`、单次使用、7 天有效；客户端不能选择 Owner 角色。
4. 使用 256-bit 随机数生成邀请码；数据库只保存 `SHA-256/HMAC` 摘要，明文只在创建响应中出现一次。
5. 邀请绑定规范化手机号摘要、租户、普通管理员角色、Scope、协议版本、创建者、过期时间和 `maxUses=1`。
6. 撤销使用 `DELETE /api/v1/identity/invitations/{invitationid}`、`If-Match` 和幂等键；撤销后 resolve、注册和重放全部失败。

#### C. 受邀手机号验证码注册

1. 用户通过 `POST /api/v1/identity/invitations/resolve` 提交邀请码；返回脱敏租户、邀请目标和协议信息，不返回成员或手机号真值。
2. 用户调用 `POST /api/v1/identity/challenges`，用途固定为 `registration`；服务端校验邀请码与手机号摘要一致。
3. Challenge 绑定 `purpose + inviteDigest + destinationDigest + deviceDigest`，验证码仅保存 KMS 加密值或不可逆校验值。
4. 发送接口始终返回反枚举响应；真实发送通过 Outbox/Job 执行，API 数据库事务内不得调用短信供应商。
5. 用户调用 `POST /api/v1/identity/members`，提交邀请、Challenge、验证码、协议 Hash、显示名和可选密码。
6. 在同一个 serializable 事务中锁定邀请和 Challenge，验证未过期、未撤销、未消费、手机号一致和尝试次数，然后原子消费二者。
7. Identity 通过 Port 创建 Principal、Member、Membership、Operator Role 和最小 Scope Grant；数据库约束禁止该路径创建 Owner。
8. 写入注册审计和 Outbox。事务提交后才能通知外部系统。

#### D. 手机验证码登录

1. 用户调用 `POST /api/v1/identity/challenges`，用途为 `login`；响应不能泄露手机号是否存在。
2. 服务端按手机号摘要、IP、设备和租户分别限流，验证码短时有效并限制尝试次数。
3. 用户调用 `POST /api/v1/identity/sessions`，`loginMethod=phone_otp`，提交 Challenge 和验证码。
4. 同一事务中使用行锁原子消费验证码；并发请求只能一个成功，失败重试不得再次创建 Session。
5. Membership 由服务端根据已验证手机号解析；存在多个 Membership 时返回不含敏感信息的受控选择上下文，再由服务端验证选择是否合法。
6. 登录成功仍返回一次性 AuthTicket，再通过 PKCE exchange 建立 Cookie Session。

#### E. Session、权限与退出闭环

1. `GET /api/v1/identity/session` 返回服务端计算的 Actor、Membership、Scope、Permission、Capability 和 Assurance。
2. AccessPipeline 的一次授权决策只使用 PostgreSQL 返回的 `evaluated_at` snapshot；不得混用 Node 时钟二次判断即时 Grant 或 Step-Up。
3. 新 Operator 必须能读取自己的 Session，但调用邀请码创建必须得到 403。
4. 所有浏览器写操作要求 allowlisted Origin、匹配的 CSRF double-submit token、幂等键；高风险操作还要求 Step-Up。
5. `DELETE /api/v1/identity/session` 撤销当前 Session 并清空 Cookie；缺失或错误 CSRF 必须失败，旧 Session 随即不可使用。
6. Membership 停用、角色变化和权限变化必须增加 `access_version` 并撤销或使旧 Session 失效。

### 11.4 数据模型与约束

优先复用现有 `identity.credential`、`identity.session`、`identity.challenge`、`identity.challengesecret`、`identity.challengedelivery`、`identity.authticket` 和 `member.invite`。缺失字段通过不可变 migration 增补，不新建平行身份表。

必须由数据库保证：

- 同租户只有一个有效 Owner。
- 邀请摘要唯一，明文邀请码不落库。
- Challenge 只能消费一次，`consumed_at` 更新必须带未消费条件。
- AuthTicket 只能交换一次并绑定 PKCE、state、nonce 和 target。
- 邀请、Challenge、手机号摘要和注册主体必须相关联。
- Operator 注册路径无法写入 Owner Role。
- 所有成员和授权查询受 Tenant/Scope/RLS 约束。

手机号应先按 E.164/中国大陆规则规范化，再使用环境隔离的 HMAC Key 生成检索摘要；可恢复展示值必须通过 KMS envelope encryption 保存。日志、Trace、错误消息和证据包不得包含原始手机号、验证码、邀请码、Ticket 或 Session Token。

### 11.5 事务与外部副作用

采用 Operation Lifecycle：

```text
prepare：规范化输入、必要的 KMS 加密/解密、构造发送意图
execute：serializable 数据库事务、锁、一次性消费、权限写入、Outbox
finalize：事务提交后的非关键响应整理
worker：短信发送、重试、回执和死信
discard：清理未提交的临时材料，不泄露敏感值
```

禁止在数据库事务中等待短信、HTTP Provider 或 KMS 网络调用。Provider 超时只能影响异步发送状态，不能留下“数据库已消费验证码但响应不确定”的半完成状态。

### 11.6 错误与响应规则

- 登录、注册 Challenge 使用统一反枚举响应。
- 邀请无效、过期、撤销、手机号不匹配对公众返回统一 `INVITE_INVALID`。
- 验证码错误、过期、重放分别进入内部审计，公开消息不得帮助撞库。
- 权限不足返回 403；未认证返回 401；版本冲突返回 409/412；限流返回 429。
- 所有错误码必须登记到 `packages/contract/definitions/errors.yml`，不得直接新增未登记字符串。

### 11.7 必须具备的自动化测试

1. Owner 密码登录、PKCE exchange、Ticket replay 失败。
2. 非 Owner 创建或撤销邀请返回 403。
3. Owner 创建的邀请只能显示一次明文，撤销后不可解析。
4. 邀请与手机号不匹配、过期、重复消费全部失败。
5. 注册验证码并发消费只有一个成功。
6. 登录验证码并发消费只有一个成功，且只创建一个 Session。
7. 新 Operator 可读自身 Session，但无 Owner 邀请权限。
8. Node 时钟落后或领先数据库时，使用同一 `evaluated_at` 的授权结果仍稳定。
9. 缺失/错误 CSRF 无法退出，正确 CSRF 可退出，旧 Session 立即失效。
10. Owner Step-Up 必须绑定原 Owner、原 Session、用途和有效期。
11. 跨租户邀请码、Membership、Scope 和 Session 全部 fail closed。
12. Fresh PostgreSQL migration replay、最小权限角色和 RLS Integration 通过。
13. 隔离 staging 完成 registration、login、stepup 三类真机短信和 replay 负例。
