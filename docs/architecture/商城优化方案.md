# 三、目标系统架构

推荐采用“模块化单体 + CQRS 读模型 + 事件驱动 Jobs + 隔离 Provider Worker”，而不是立即拆微服务。

原因是订单、库存、福利、卡券、财务之间存在强事务要求；当前容量目标为 API 5000 QPS、订单 300 TPS、支付回调 600 TPS，模块化单体配合横向扩展完全能够承载，同时比跨服务分布式事务更可靠、更易维护。

边界规则：

- 一个 Handler 对应一个 Operation。
- 一个业务表只有一个模块可写。
- 跨模块命令走 Public Write Port。
- 跨模块查询走 Public Read Port 或 Reporting Projection。
- 异步副作用走 Outbox；消费者使用 Inbox 去重。
- `Navigation` 只计算可见视图，不提供授权。
- `Reporting` 不跨 schema 联表拼报表。
- `Audit` 只追加。
- `Checkout`、`Channel` 是编排者，不拥有其他模块的业务状态。
- Provider 不能直接写 Catalog、Inventory、Finance 表。

正常下单流程中，storefront 不再自行调用一次 `payment.intents.create` 来“补支付”。订单提交必须返回完整支付状态：

- 全福利支付：`captured`。
- 外部支付：`pending` 和受控支付动作。
- Provider 暂时不可用：订单/预占仍可恢复，状态不得伪装为失败或成功。
- 相同幂等键和请求哈希必须返回相同结果；同键不同请求返回冲突。

固定锁顺序：

```text
Idempotency
→ Quote
→ Cart
→ Inventory，按SKU排序
→ Voucher，按Voucher ID排序
→ Benefit，按Account ID排序
→ Order
→ Payment
→ Finance
→ Audit
→ Outbox
```

# 七、数据所有权和核心不变量

| 模块          | 核心数据                                                      | 必须保持的不变量                                 |
| ------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| Identity      | Principal、Credential、Session、Invitation、FederatedIdentity | 外部身份唯一绑定；会话不可复用；凭证不可明文存储 |
| Organization  | Organization、UnitClosure、DirectoryBinding                   | 组织树无环；目录同步有来源和版本                 |
| Access        | Role、Grant、Ownership、Override、DecisionAudit               | 默认拒绝；权限、作用域、能力和认证强度同时满足   |
| Capability    | Capability、Dependency、Entitlement                           | Feature 开关不能绕过授权                         |
| Partner       | Partner、Agreement、Store、ServiceBinding                     | 无有效资质和协议不能交易                         |
| Member        | Profile、Address、Import                                      | 敏感数据加密；作用域内成员唯一                   |
| Qualification | PolicyVersion、Evidence、Decision                             | 决策绑定规则版本；历史决定不可覆盖               |
| Catalog       | Product、Sku、Pool、Listing、Category                         | SKU 业务键唯一；未发布内容不可进入 storefront    |
| Pricing       | PriceBook、Rule、Price、Quote                                 | 金额使用整数分；生效区间不重叠                   |
| Inventory     | StockItem、Reservation、Movement、Observation                 | 可售库存不得为负；释放、确认幂等                 |
| Experience    | Application、Version、Publication                             | 发布版本不可变；切换 Publication 原子化          |
| Marketing     | Campaign、Redemption                                          | 同一快照得到确定性优惠结果                       |
| Cart          | Cart、Item                                                    | 每用户每商城唯一活动购物车；版本并发控制         |
| Checkout      | Session、Evidence、Quote                                      | Quote 过期、Cart 变化或价格变化必须重新报价      |
| Order         | OrderRecord、Line、StateEvent、AfterSale、Receipt             | 商品、价格、地址、权益均是不可变下单快照         |
| Fulfillment   | FulfillmentOrder、Line、Milestone、Return                     | 履约数量不能超过订单数量                         |
| Verification  | Session、Attempt、Nonce、Device                               | 一次性凭证只能成功消费一次                       |
| Payment       | Intent、Attempt、Capture、Refund、Observation                 | 商户、币种、金额必须匹配；未知状态不得猜测       |
| Voucher       | Program、CardPool、Voucher、Hold、Redemption                  | 卡密唯一；状态迁移合法；核销只能成功一次         |
| Benefit       | Account、Lot、Reservation、Movement                           | 可用额度非负；返还关联原消费                     |
| Finance       | Journal、Entry、EconomicLeg、Settlement、Invoice              | 借贷平衡；账本只追加；修复通过冲正               |
| Extension     | Manifest、Installation、Registry、Health                      | 签名、合同、能力和配置缺一不可                   |
| Channel       | Connection、SyncRun、ExternalObject、WebhookInbox             | 先提交数据，后推进 Cursor                        |
| Referral      | Binding、Commission、Movement、Withdrawal                     | 首触绑定不可覆盖；退款等额冲正                   |
| Support       | Ticket、Conversation、Message、Assignment、SLA                | 关闭必须有解决结论和完整时间线                   |
| Notification  | Template、Dispatch、Attempt、Preference                       | 业务通知按幂等键去重                             |
| Reporting     | Fact、Metric、Projection、Watermark、Export                   | 展示数据水位；不得伪装实时                       |
| Risk          | PolicyVersion、Signal、Decision、Case                         | 高风险操作默认失败关闭                           |
| Audit         | Record、HashChain、Archive                                    | 只追加、不可业务修改、敏感字段脱敏               |
| Navigation    | 生成目录和授权后树                                            | 菜单显隐不能代替后端授权                         |

`ordering` schema 对应 Order 模块，`invoice` schema 由 Finance 拥有；应通过数据库所有权清单明确这种映射，禁止凭 schema 名猜测写权限。

# 十、数据一致性设计

## 一致性分级

| 场景          | 一致性   | 实现                                          |
| ------------- | -------- | --------------------------------------------- |
| Cart 更新     | 强一致   | Cart Version + Idempotency                    |
| Quote         | 快照一致 | Cart/Price/Qualification/Benefit Version      |
| 下单          | 强一致   | Serializable UoW + 固定锁顺序                 |
| 福利全额支付  | 强一致   | Order、Reservation、Benefit、Finance 同事务   |
| 外部支付      | Saga     | 本地意图先持久化，回调/主动查询恢复           |
| 库存          | 强一致   | Reservation 状态机和确定性锁顺序              |
| 卡券核销      | 强一致   | 唯一约束 + 行锁 + 状态机                      |
| 售后退款      | Saga     | Order、Fulfillment、Payment、Finance 事件编排 |
| Provider 同步 | 最终一致 | 分块事务，成功后推进 Cursor                   |
| 报表          | 最终一致 | Outbox→Inbox→Projection→Watermark             |
| 通知          | 最终一致 | Inbox 去重和重试                              |
| 缓存          | 最终一致 | Versioned Key + Event Invalidation            |
| 审计          | 强追加   | 同业务事务写不可变记录或 Outbox               |

## 状态机

```text
Order
created
→ awaitingpayment
→ paid
→ fulfilling
→ shipped
→ received
→ completed

created或awaitingpayment → cancelled
paid之后只能通过aftersale和refund处理
```

```text
Payment
created
→ preparing
→ pending
→ captured
→ partiallyrefunded
→ refunded

preparing或pending → failed
preparing或pending → expired
unknown → recovery，不得直接推断
```

```text
InventoryReservation
reserved
→ committed
→ released
→ expired
```

```text
Voucher
inactive
→ active
→ held
→ redeemed
→ reversed

active → disabled
active或disabled → void
active → expired
```

```text
AfterSale
applied
→ reviewing
→ approved
→ returning
→ received
→ refunding
→ resolved

reviewing → rejected
```

统一要求：

- 金额使用 `int64` 最小货币单位，禁止浮点。
- 比率使用整数基点或定点 Decimal。
- 时间统一 UTC，展示层转 `Asia/Shanghai`。
- 外部 ID 必须带 Provider 和 Tenant 范围。
- 所有可变 Aggregate 都有单调递增 `version`。
- 所有写操作都有幂等键、请求哈希和作用域。
- 同一幂等键重复请求返回首次结果；请求体不同返回冲突。
- Outbox 和业务状态同事务。
- Inbox 以 `provider + eventId` 或 `consumer + messageId` 唯一。
- 分配金额采用确定性的最大余数法；总和必须严格等于订单金额。
- 历史迁移不可重写；“抛弃兼容性”不意味着破坏迁移可回放性。

# 十二、安全设计

## 浏览器与身份

- 会话使用 `HttpOnly + Secure + SameSite` Host-only Cookie。
- 登录、邀请、Step-up、换手机、改密统一经过 Identity 和 Verification。
- CSRF Token 绑定 Session、Origin、Target 和过期时间。
- 登录回调和 Return Target 使用固定白名单。
- 登录、验证码、邀请码、联合身份回调都做速率限制和重放保护。
- 敏感操作要求 Step-up 和 Maker-checker。
- 退出时先使本地状态失效，再撤销服务器会话；撤销失败必须可见并可重试。

## 授权

授权顺序必须固定：

```text
Session
→ Membership Active
→ Credential Version
→ Access Version
→ Role Permission
→ Resource Scope
→ Capability
→ Assurance
→ Risk
→ Decision Audit
```

- 默认拒绝。
- RLS 是纵深防御，不是唯一授权。
- 每次请求的 Tenant、Membership、Scope 写入 DB Session Context。
- 缓存键必须包含 `membership + authzversion + capabilityversion`。
- Scope 切换必须清空前一商城的用户、商品、订单、购物车和导航缓存。

## 数据与供应链

- PII 字段使用 KMS Envelope Encryption；搜索字段单独保存不可逆指纹。
- 日志禁止出现 Authorization、Cookie、Password、OTP、Secret、Card Secret、Invite、Token Hash、Recipient 等字段。
- Webhook 校验证书、签名、时间窗、Nonce、商户和金额。
- 上传文件使用私有对象存储、短期签名 URL、MIME/尺寸校验、病毒扫描。
- CSP 默认拒绝，按真实资源逐项开放。
- 禁止在 `dangerouslySetInnerHTML` 中渲染未净化装修内容。
- CI 使用 OIDC；产物包含 SBOM、许可证报告、签名和 Provenance。
- 源码、Git 历史、日志、备份、退休产物全部进行秘密扫描。

# 十三、性能与高并发

沿用 [config/capacity.yml](/Users/changshengwang/Workspace/zhudatuan/config/capacity.yml) 和 [config/telemetry.yml](/Users/changshengwang/Workspace/zhudatuan/config/telemetry.yml) 的容量基线：

- 订单 300 TPS。

- 卡券批次 100 万。
- 年增长 80%。

SLO：

| 请求                 |     目标 |
| -------------------- | -------: |
| Catalog P95          |  ≤150 ms |
| 普通 Query P95       |  ≤300 ms |
| Detail P95           |  ≤500 ms |
| Command P95          |  ≤800 ms |
| Order P95            | ≤1500 ms |
| Webhook 持久接收 P99 |  ≤500 ms |
| Outbox P99           |   ≤30 秒 |
| 可用性               |  ≥99.95% |
| RPO                  |  ≤5 分钟 |
| RTO                  | ≤30 分钟 |

关键优化：

- storefront 初始 Gzip ≤110 KB；单个懒加载 feature ≤100 KB。
- Route 和大型页面按需加载。
- 图片使用多尺寸、WebP/AVIF、懒加载和 CDN。
- 商品列表使用游标分页和虚拟滚动。
- Bootstrap 和 Catalog 使用服务端组合，避免浏览器 6～10 次往返。
- 查询默认 50 行、最大 200 行、响应最大 2 MB。
- 数据库连接总预算 100，常态最多使用 70%；当前 Query 24、Command 20、Worker 24、Migration 1，总和 69。
- 热路径禁止 OFFSET、N+1、无界数组、无界 `Promise.all` 和全表导出。
- 所有外部调用使用 Deadline、Bulkhead、Retry、Circuit Breaker。
- Retry 只用于幂等操作，并增加抖动。
- Cache 只缓存可重建数据；Session、Access 不允许 Stale。
- Catalog、Experience 使用版本化缓存键。
- 报表导出全部异步，结果写对象存储。
- 大批量卡券、会员、商品导入使用分块、检查点、暂停和恢复。

# 十七、最终验收标准

只有同时满足以下条件，才可以称为完成。

## 需求

- 18 条 required MVP 全部为 `Released`。
- 4 条 nonblocking 明确记录“不阻塞”而非误删。
- 3 个阻塞定义全部签字。
- 11 个 P1 Provider 数量、ID、能力完全一致。
- 每条需求至少有一个真实 Journey Evidence。

## storefront

- 所有正式路由可深链接、刷新和前进后退。
- 不存在 mock、localStorage 业务状态和假成功。
- 不存在可点击但只提示“暂不可用”的入口。
- 游客、登录、无权限、会话过期、部分失败均有明确状态。
- 购物车选中结算、支付恢复、售后、卡券、安全、客服完整闭环。
- LI 的 8 个视口和交互契约全部通过。

## 架构

- 模块边界、所有权、调用图、重复逻辑、事务、分页门禁零违规。
- 前端 UI 不直接发网络请求。
- 跨模块不直接写表。
- 所有副作用通过事务或 Outbox。
- Provider 不进入领域内核。
- 没有兼容目录、旧 API Alias、双读或双写。

## 数据

- 空库 Migration Replay 成功。
- 生产快照迁移前后行数、金额、状态和哈希核对成功。
- 财务借贷平衡。
- 库存、卡券、福利账户不出现负数或重复消费。
- Outbox、Inbox、Job、Audit、Reporting 水位可核对。
- 支付和退款可通过 Provider 权威数据对账恢复。

## 性能和可用性

- 达到 5000 QPS、300 TPS 订单、600 TPS 回调目标。
- P95/P99、Outbox Lag 和 Bundle 预算达标。
- 任一 API Pod、Jobs Pod、Redis 副本或单可用区故障不中断核心交易。
- RPO≤5 分钟、RTO≤30 分钟恢复演练通过。
