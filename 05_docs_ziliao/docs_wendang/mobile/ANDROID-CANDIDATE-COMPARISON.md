# 智慧翼移动端两套候选项目对比报告

日期：2026-08-13

## 1. 结论

建议以 `smart-wing-benefit-mall小程序`（下称方案 A）作为智慧翼 Android 客户端主线；`智慧翼企业福利商城小程序`（下称方案 B）只作为优惠券、积分商城、会员卡片等局部视觉与交互参考，不适合直接继续扩建为主产品。

综合评分：

| 方案                             |       综合分 |   生产就绪度 | 定位判断                              |
| -------------------------------- | -----------: | -----------: | ------------------------------------- |
| A：smart-wing-benefit-mall小程序 | **73 / 100** | **28 / 100** | 方向正确的 Android 福利商城 MVP       |
| B：智慧翼企业福利商城小程序      | **41 / 100** | **14 / 100** | 餐饮会员小程序风格的 Android 视觉原型 |

两个目录虽然都叫“小程序”，实际都是 Kotlin + Jetpack Compose 的原生 Android 工程，不是微信小程序工程。两者都没有 `app.json`、`project.config.json`、WXML/WXSS，也没有 Taro/uni-app 工程结构。以后若要交付微信小程序，应新建独立客户端，并复用同一套 BFF、权限、会员、商品和订单接口，而不是把 Android 代码直接改名为小程序。

## 4. 方案 A 详细分析

### 优点

1. **业务方向最接近智慧翼。** 已有合作商、门店、城市专区、商品来源、履约方式、售后说明、限购、员工身份、企业范围和手机认证等概念。
2. **已有比较完整的演示闭环。** 能进行搜索、筛选、加入购物车、修改数量、按合作商拆分订单、分配福利余额和个人支付金额、生成订单与支付结果。
3. **VI 基础正确。** 主色使用 `#1F5EFF`，并配有 `#143A8F`、`#07182F`、`#10294D` 等智慧翼深色层级，方向与现有 Web 端一致。
4. **Android 导航合理。** 首页、分类、购物车、订单、我的五栏符合零售商城习惯，购物车有数量角标。
5. **为真实接口留出了入口。** 有 `SmartWingApi` 和 `MockSmartWingRepository` 的边界，比把全部状态写在页面中更容易替换。

### 主要问题

1. **目前仍是全量模拟数据。** `SmartWingApi` 只有占位地址，没有 Retrofit 接口、鉴权、刷新令牌、错误映射和远端 Repository，未连接智慧翼真实 BFF。
2. **网络商品图会直接失败。** 页面使用远程图片，但 Manifest 没有声明 `INTERNET` 权限；即使编译成功，图片也无法正常加载。图片也没有稳定 CDN、占位图和失败态。
3. **登录路由是假的。** 路由枚举中虽然有 `LOGIN`，实际渲染的仍是个人中心；应用启动即处于已登录状态，没有注册、登录、注销和会话恢复。
4. **金额使用 `Double`。** 福利余额、商品价格和支付分配不能使用浮点数，应统一改为分单位整数或高精度 Decimal，并由服务端最终裁决。
5. **部分按钮“说做了但没做”。** 例如“再来一单”只显示提示，没有真正重新加入购物车。
6. **Repository 过大。** 约 800 行模拟数据和业务操作集中在一个文件，后续应拆为认证、会员、商品、购物车、订单、支付、合作商等模块。
7. **品牌授权边界不严。** 数据中写入合作商品牌色和看似真实的门店地址；正式演示前应明确标记“演示数据”，未授权前不要表现为官方合作或使用对方视觉资产。
8. **会员码仍由客户端生成。** 正式场景必须由服务端签名、短时有效、防重放，并记录核销审计。

## 5. 方案 B 详细分析

### 可保留的优点

1. **局部组件较丰富。** 优惠券包、积分商城、会员中心、卡片式资产区等可以作为后续 UI 灵感。
2. **深色主题准备较多。** 如果未来确实需要夜间模式，可复用部分配色思路。
3. **组件数量较多。** 视觉拆分意识比单页堆叠更强，适合挑选少量卡片和空状态组件。

### 决定性问题

1. **产品定位偏离。** 核心仍是“点单、咖啡、奶茶、门店会员”，不是连接麦德龙、沃尔玛、山姆、大润发、永辉的企业福利商城。
2. **把微信小程序壳搬进 Android。** 代码中存在 rpx 换算、微信右上角胶囊安全区和类似小程序的导航设计；这既不是规范 Android，也不是真正的微信小程序。
3. **中央会员码按钮过重。** 巨大凸起按钮占据底部主导航核心位置，压过商品、购物车和订单，不符合综合福利商城的信息优先级。
4. **合作商模型缺失。** 没有统一合作商、门店授权、供应商来源、履约拆单、售后归属和接口适配器。
5. **会员资格过浅。** 没有手机认证状态、企业/部门/城市资格、商品可见与可买规则、限售模板和支付解锁条件。
6. **支付演示存在误导。** 提交订单后在客户端直接扣余额并生成“已完成”订单，没有服务端幂等、库存锁定、支付单、回调验签和失败恢复。
7. **图片资源没有落地。** 商品只保存诸如 `coffee_1` 的字符串键，工程中没有对应图片资源或真实加载链路，完成度停留在占位层。
8. **存在空按钮。** 分享、通知、关于等入口没有行为，演示时会出现“能点但无反应”。

## 6. 两者共同的生产阻断项

1. **没有真实注册、登录和会话安全体系。** 缺密码散列、短信验证、设备管理、刷新令牌、注销、找回密码与风控。
2. **没有连接智慧翼会员、权限、资格和订单服务。** 目前所有核心数据都在客户端内存中，重启即失效，也可被篡改。
3. **没有真实支付。** 缺支付下单、服务端签名、微信支付/支付宝回调、幂等、防重复扣款、退款和对账。
4. **没有真正的合作商连接器。** 麦德龙、沃尔玛、山姆、大润发、永辉需要各自授权、商品映射、库存价格、订单路由、售后和对账适配层。
5. **构建不可复现。** 两个目录都没有提交 Gradle Wrapper，本机也无法直接使用仓库自带命令完成一致构建。
6. **测试是失效模板。** 测试仍引用不存在的 `Greeting`，断言的应用名、包名也与当前项目不一致，测试套件不能作为质量证据。
7. **Android 安全配置不足。** 两者 Manifest 均允许应用备份；涉及账号和支付数据时应显式关闭或配置严格的数据提取规则。
8. **README 与项目不一致。** 文档仍要求配置 Gemini API Key，但实际客户端没有使用 Gemini；同时保留 AI Studio 模板发布说明，容易误导部署人员。

## 7. 合并建议

### 保留方案 A 的内容

- 智慧翼 VI 主色与深色层级
- Android 标准五栏导航
- 企业福利商城首页、分类、购物车、订单、个人中心
- 合作商、门店、城市专区和商品资格模型
- 合作商拆单、支付分配、订单详情与支付结果的流程骨架
- 手机未认证时限制支付的产品规则

### 从方案 B 选择性吸收

- 优惠券包和权益卡片的视觉组件
- 积分商城的页面结构
- 会员中心的资产摘要设计
- 优质空状态、卡片阴影和少量动效思路

### 明确不要吸收

- rpx、微信胶囊和假小程序安全区
- 巨大的中央会员码导航按钮
- “点单”作为一级导航
- 餐饮门店和咖啡奶茶作为核心商品模型
- 客户端直接扣余额和把订单设为“已完成”
- 客户端生成可核销会员码

## 8. 推荐落地路线

1. **先冻结方案 A 为 Android 主线。** 方案 B 标记为参考原型，停止平行扩建，避免两套界面和模型继续分叉。
2. **建立共享移动端设计令牌。** 将智慧翼颜色、字体、圆角、间距、图标和状态色输出为可生成 Android 与微信小程序资源的单一 JSON 源。
3. **先接真实账号与会员会话。** 注册、登录、注销、手机号状态、会员上下文和资格原因全部从 BFF 返回。
4. **接商品与资格查询。** 商品列表、详情、购物车和结算都必须使用同一服务端资格决策，明确显示“为什么不可见/不可买”。
5. **建立合作商连接器层。** 每家合作商使用统一内部模型和独立适配器，外部品牌、门店和价格信息只有在授权后启用。
6. **重做支付域。** 金额改为分单位整数；创建支付单、余额预占、第三方支付、回调验签、退款和对账都在服务端完成。
7. **另建微信小程序客户端。** 使用原生小程序或 Taro/uni-app，复用 BFF 与设计令牌，不复用 Compose UI 代码。
8. **补齐可重复构建和测试。** 提交 Gradle Wrapper，修复单元测试与截图测试，接入 CI，再开始内部 Android APK 验收。

## 9. 最终判断

方案 A 已经回答了“智慧翼移动端要卖什么、给谁卖、受什么资格限制、如何按合作商拆单”这些关键问题；方案 B 主要回答的是“一个餐饮会员小程序可以长什么样”。因此两者不是五五开的两个候选，而是**主产品骨架与视觉参考库**的关系。

选择 A 不等于它已经能上线。73 分代表方向和演示闭环较好；28 分的生产就绪度代表账号、会员、资格、支付、合作商接口、审计、构建和测试仍需正式工程化。正确策略是以 A 为主线补真实服务，把 B 的少量优质组件迁入，而不是继续维护两套独立产品。
