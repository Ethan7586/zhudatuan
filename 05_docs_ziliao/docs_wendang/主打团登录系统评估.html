Verdict

密码层

services/commerce/src/modules/identity/domain/policy/PasswordPolicy.ts

scrypt + 版本化存储格式优秀
scrypt$<VERSION>$<N>$<r>$<p>$<salt-base64url>$<hash-base64url>
  • scrypt——内存硬 KDF，抗 GPU/ASIC 暴力破解，不是 SHA-256 裸哈希
  • 每个密码 16 字节随机盐，64 字节输出
  • 参数编码进存储串（N/r/p）——将来调整成本参数可以无痛平滑迁移，旧记录仍可验证
  • timingSafeEqual 常量时间比较，不用 ===
反计时攻击：记录不存在也烧同等时间少见的细节

第 37 行，当凭证记录缺失时仍然执行一次 dummy scrypt：

await scrypt(password, Buffer.alloc(16), 64);

这让"用户不存在"和"密码错误"的响应时间一致，攻击者无法用计时差异枚举有效账号。多数生产系统不做这一步。

票据交换

这是整套系统最强的部分

单语句 CTE 完成三件事，全程原子PgAuthTicket.ts:26-37
with accepted as (
  select ... where ticket.token_hash=$1 and state_hash=$2
    and nonce_hash=$3 and pkce_challenge=$4
    and consumed_at is null and expires_at > clock_timestamp()
), consumed as (
  update identity.authticket set consumed_at=clock_timestamp() from accepted ...
), rotated as (
  update identity.session set token_hash=$6 from consumed
  where session.id=consumed.session_id and session.token_hash=$5
)
  • 四重匹配——token、state、nonce、PKCE challenge 必须同时命中，缺一不可
  • 一次性不可双花——consumed_at 在同一语句内写入，并发重放拿不到第二次
  • 绑定原会话——轮换要求出示当前 session token（$5）。偷到票据也无法在另一个会话里兑换
  • 全部哈希存储——ticket / state / nonce / session token 无一以明文落库
PKCE 是 S256，不是 plainAuthTransaction.ts:9,14,17
  • challenge 强制恰好 43 字符 = base64url(sha256(32B))，从长度上排除了 plain 方法
  • verifier 限制 43–128，符合 RFC 7636
  • 服务端重算 sha256(verifier) 与存储的 challenge 比对，而不是信任客户端声明
  • state / nonce 以 sha256 hex 存储，不留明文

会话与 CSRF

services/commerce/src/modules/identity/IdentitySecurity.ts:21-22

双 Cookie 分工正确设计对
shop_session=...; Path=/; Max-Age=..; Secure; HttpOnly; SameSite=Lax
shop_csrf=...;    Path=/; Max-Age=..; Secure;           SameSite=Strict
  • 会话 cookie HttpOnly——JS 读不到，XSS 偷不走
  • CSRF cookie 刻意不设 HttpOnly——前端必须读它放进请求头，这是标准 double-submit 模式，不是疏忽
  • 两者都 Secure，且不设 Domain= → host-only，不会泄漏到子域
缺 __Host- 前缀小、易补

当前配置已经满足 __Host- 的全部条件（Secure + Path=/ + 无 Domain），但没有用这个前缀。

加上之后，host-only 这个属性由浏览器强制，而不只是靠服务端自觉。任何一次配置疏忽（比如将来误加 Domain=）浏览器会直接拒绝写入，而不是静默降级。

__Host-shop_session=...; Path=/; Secure; HttpOnly; SameSite=Lax

今晚故障的真实性质

没有一个是设计缺陷

症状根因性质
Identity API 三项 false角色有 GRANT 但缺 RLS policy → 查询返回 0 行部署 ACL
bootstrap 事务回滚zhudatuanbootstrap 缺 access.membershiprole 读权限部署 ACL
邀请 one-shot 失败42P18 参数类型无法推断（PGlite 漏，真 PG 拒）SQL 类型
INTERNAL_ERROR 登录失败密码已验证通过，清理失败计数缺 DELETE 权限 → 整笔回滚部署 ACL

最后那个尤其能说明问题。IdentityOperations.ts:114：

delete from identity.loginattempt
where subject_hash = any($1::text[]) and client_hash in ($2,'account')

这是登录成功后清零失败计数的收尾动作。密码校验、会话创建全部正确，倒在最后一步的权限上，事务回滚，于是对外表现成"登录失败"。代码逻辑完全正确，缺的只是一行 GRANT。

顺带一提：subject_hash 和 client_hash——登录失败追踪也是哈希存储的，不留可关联的明文标识。

真正的弱点

按影响排序

ACL 缺口是逐个发现的，这个类没有被结构性关闭最高优先

今晚至少 4 次同类失败。模式是固定的：代码在超级用户或 PGlite 上下文里写就并通过测试，然后最小权限角色在生产上一个表一个表地撞。

Codex 已经为登录链路做了完整权限矩阵，但下一个碰新表的 operation 会重演同一出。

结构性解法：在 migration 重放之后，以每个最小权限角色的身份跑一遍该角色实际会执行的 SQL。项目里已经有现成材料——database-contracts.mjs 里刚加的 set local role 手法就是对的做法，只是目前只覆盖了 runtime.schemaversion 一张表。

LoginPage.tsx 1387 行全库最大文件

行预算是 299 行，超了 4.6 倍。登录、注册、OTP、多身份选择、锁定倒计时全挤在一个文件。

这是安全敏感 UI——审查面越大，漏掉一个状态处理错误的概率越高。后端那套精心设计的协议，前端如果在某个分支里把 CSRF token 忘了带，一样白搭。

三轨身份仍未合流架构债

canonical console 登录、canonical registration、smart-wing 兼容登录三条链路并存。auth.ts（520 行）与 canonicalIdentity.ts + canonicalRegistration.ts（452 行）是两套并行实现。

短期没问题，长期是双倍的安全审查成本——任何一条链路的疏漏都是整体的疏漏。

测试覆盖 6/19 ≈ 32%相对最好，绝对不够

identity 是 commerce 里覆盖最好的模块（finance 23%、payment 25%、order/checkout/cart 为 0）。但这是最该有覆盖的地方，而今晚暴露的所有问题——ACL、类型推断、RLS 可见性——现有测试一个都测不到，因为它们都是 mock 或 PGlite。
