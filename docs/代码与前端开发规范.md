# 智慧翼企业福利商城——代码与前端开发规范

版本：v1.0  
适用范围：`smart wing` 商城、Worker API、数据库变更与多端 Web 客户端。

## 1. 强制质量门禁

- 提交前必须运行 `npm run quality`；该命令检查格式、300 行约束、TypeScript、测试、生产构建和生产依赖审计。
- CI 使用同一命令。质量门禁未通过，不得合并或部署。
- 禁止提交密钥、访问码、供应商 token、支付证书、真实个人信息或数据库导出。
- 新功能必须同时包含成功、校验失败、权限拒绝和服务端失败的验收说明；资金类改动必须补自动化测试。

## 2. 代码组织与命名

- `src/screens` 仅编排页面；业务逻辑放入 `src/features`、`src/services` 或 `src/context`。
- `src/components` 只放跨页面展示组件，不直接调用数据库或持有资金状态。
- `worker/api` 负责 HTTP、认证、权限、输入校验与服务端编排；数据库写入只经受控 RPC。
- React 组件、类型和接口使用 PascalCase；变量、函数、路由参数使用 camelCase；数据库字段使用 snake_case。
- 一个可维护源码文件不得达到 300 行。超过时按职责拆分，历史迁移不因行数改写。
- 禁止新增无约束 `any`；外部输入先用 `unknown` 接收并校验后再转换。

## 3. 前端体验标准

- 颜色、间距、圆角和字体优先复用既有 Tailwind 语义类与商城主色，禁止为单个页面散落新的不透明色值。
- 每个异步页面或操作必须有加载、空态、错误态与重复提交防护；错误提示不得泄露密钥、堆栈或内部 SQL。
- PC、笔记本、平板、小程序视觉端与 Android 视觉端共用业务数据源，不复制订单、余额或支付规则。
- 演示、待联调、已上线能力必须显式区分；未接入的微信、小程序、供应商或支付能力不得伪装为已完成。
- 所有图片提供有意义的 `alt`；可点击元素使用 `button` 或具备键盘可达性。

## 4. API、身份与资金规则

- API 返回统一 JSON；错误必须包含稳定的 `code` 与 `requestId`。
- 所有写接口校验请求体、权限范围和租户/企业/商城/员工归属；不能信任浏览器传入的身份、金额或状态。
- 创建订单、支付、退款必须携带 `Idempotency-Key`，并以服务端请求哈希防止同键不同请求。
- 金额在服务端和数据库统一用整数分；前端仅用于展示金额，不能成为资金计算权威。
- 余额、订单、支付、退款、库存和审计以服务端 RPC/数据库事务为准；浏览器 `localStorage` 只能保存设备偏好或未登录演示状态。
- 收货人、电话和地址必须加密存储；日志中禁止记录完整 PII、访问码、会话 cookie 或支付凭据。

## 5. 数据库与迁移

- 新数据库变更必须新增迁移，严禁改写已经部署的历史迁移。
- 业务表启用 RLS；前端不持有 Supabase 管理密钥。
- 审计与账户流水仅追加，禁止更新和删除。库存、扣款、退款与订单状态转换必须在事务/RPC 中保证原子性。
- 迁移须提供回滚或补偿方案，并在预发布数据集上验证。

## 6. Git 与评审

- 每个提交只解决一个明确问题，提交信息采用 `type(scope): summary`，如 `fix(payment): reject duplicate allocation`。
- PR 描述必须写明：用户影响、数据/迁移影响、权限影响、测试证据、回滚方案和外部依赖。
- 涉及资金、身份、权限、PII、供应商回调的改动必须由第二位开发者或负责人复核。
- 不使用 `git reset --hard`、强制推送或改写已部署迁移处理问题。

## 7. 发布标准

- 生产环境只从 CI 通过的提交发布，且生产依赖审计无高危漏洞。
- 发布前完成：环境变量检查、数据库备份验证、健康检查、关键交易冒烟、日志/告警检查与回滚演练。
- 外部支付、企业 SSO、供应商 API 的密钥仅进入托管密钥库；真实接入需验签、幂等、重试、回调审计和对账验收。
