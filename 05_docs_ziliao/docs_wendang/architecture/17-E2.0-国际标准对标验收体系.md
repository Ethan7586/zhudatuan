# E2.0 国际标准对标验收体系

> **本版唯一可用结论：E2.0 尺子已补齐 E01—E12 并锁定判据；尚未据此完成 E01—E12 全量重测。**
>
> E2.0 是 `standards-aligned / tailored conformity profile`（标准对标及裁剪符合性配置），不是 ISO、IEEE、NIST、OWASP、PCI SSC 或任何第三方认证。不存在一项覆盖 SFL 全部能力的“世界标准”；SFL 的具体业务断言仍是项目自定义断言，外部标准只提供质量模型、测试过程、安全验证、开发证据或连续性参考。

## 1. 目的与不可变边界

E2.0 只负责测量、记录和报告。它把每项质量声明连接到业务风险、外部标准版本、项目测试、预锁定判据、独立 oracle、原始证据、执行环境、执行者、复核者、结果和缺口，使外部人员可以复核声明依据。

以下边界不可被本文件、schema、测试工具或报告覆盖：

1. E2.0 不是权限系统、运行时守卫或功能开关。
2. E2.0 不得接入应用启动、请求处理、登录、授权或数据访问路径。
3. E2.0 不得成为 GitHub required check、CI 合并门禁、发布门禁或部署前置条件。
4. `NOT MET`、`UNKNOWN` 或证据缺失不得禁用功能、阻止系统使用、自动回滚、停服或收窄权限。
5. 任何条目若要成为强制门禁，必须由 Ethan 针对该具体条目另行书面授权；本版本没有任何此类授权。
6. 本体系不新增安全约束、权限收窄或运行时校验，只测量现状。

机器文件中的 `non_gating` 必须恒为 `true`；任何把它改为 `false` 的派生物都不属于 E2.0。

## 3. 对标含义与版权边界

每条外部映射必须声明以下四种类型之一：

- `QUALITY_MODEL_ALIGNMENT`：标准提供质量分类，具体 SFL 判据由项目定义。
- `PROCESS_ALIGNMENT`：标准提供测试过程、文档、oracle 或独立性思想，未声称逐条符合。
- `EXACT_OPEN_REQUIREMENT_MAPPING`：仅用于可合法读取并准确定位的开放标准要求，例如 ASVS 5.0.0 的要求 ID。
- `PROJECT_CUSTOM`：没有外部条款直接规定该 SFL 行为；必须显式标注，不能伪装成国际条款。

ISO 公开摘要不足以支撑 ISO/IEC/IEEE 29119 的正式符合性声明。若未来要作此声明，必须先合法取得并按授权使用相关标准全文，由合格人员逐条记录适用性、裁剪理由、证据和结论。ISO 标准受版权保护，本仓库只保存标准编号、官方公开描述的项目摘要、项目解释、测试和证据链接。

[ISO 官方认证说明](https://www.iso.org/certification.html)明确区分标准制定与外部认证。第三方认证必须由适格外部机构执行；E2.0 的内部或外部复核都不自动等于认证。

## 4. 术语与结果模型

### 4.1 四个独立维度

一个结论必须同时给出四个维度，禁止只写 `PASS`：

| 维度 | 允许值 | 含义 |
| --- | --- | --- |
| 声明结论 | `MET` / `NOT MET` / `UNKNOWN` / `NOT APPLICABLE` | 判据已满足、已违反、证据不足/矛盾、经批准不适用 |
| 环境保证 | `DEV VERIFIED` / `STAGING VERIFIED` / `PRODUCTION OBSERVED` / `NOT ESTABLISHED` | 结论在哪一类环境获得；低层结果不得自动升级 |
| 复核保证 | `NOT REVIEWED` / `INTERNAL PEER REVIEWED` / `INDEPENDENTLY REVIEWED` | 谁与设计/执行保持何种责任分离 |
| 对标深度 | 上节四种 mapping type | 标准提供的是模型、过程、开放要求还是项目自定义判据 |

`PRODUCTION OBSERVED` 只说明在生产观测到指定事实，不等于已执行破坏性负向实验，也不等于 `STAGING VERIFIED` 或 `INDEPENDENTLY REVIEWED`。`INDEPENDENTLY REVIEWED` 只能由未设计、未执行该测试且披露利益关系的复核者签署，并保留复核输入和重算结果。

### 4.2 环境定义

- `DEV VERIFIED`：本地、一次性数据库、临时容器、模拟器或开发者控制的隔离环境。
- `STAGING VERIFIED`：有稳定身份、配置管理、与生产架构的差异清单、独立凭据/数据和可重复部署记录的真实 staging。把本地目录或临时容器命名为 staging 不足以获得此等级。
- `PRODUCTION OBSERVED`：真实生产环境的只读或已明确授权观测；必须记录生产对象、时间窗和影响。未经授权不得执行写入、故障注入或回滚实验。

### 4.3 评级组合闭合规则

三份 schema 对相关字段实施同一组约束，不再允许文字规则与机器记录相互矛盾：

| 组合 | 机器规则 |
| --- | --- |
| `MET` / `NOT MET` | 必须有非空原始证据引用，环境保证不得为 `NOT ESTABLISHED` |
| `NOT APPLICABLE` | 环境保证必须为 `NOT ESTABLISHED`，且必须引用裁剪/适用性决定；追踪矩阵中的适用性与结论必须一致 |
| DEV / STAGING / PRODUCTION 证据 | 只能对应 `DEV VERIFIED` / `STAGING VERIFIED` / `PRODUCTION OBSERVED`，或保持 `NOT ESTABLISHED`；任一已建立环境等级都必须有证据引用 |
| `NOT REVIEWED` | 复核者、时间、独立性声明和复核证据引用必须为空 |
| `INTERNAL PEER REVIEWED` | 必须有复核者、时间、重算证据和关系披露；复核者不得是执行者或测试设计者 |
| `INDEPENDENTLY REVIEWED` | 在内部同行复核条件上，还必须明确与交付团队外部独立且已披露利益冲突 |

JSON Schema 无法跨字段比较两个任意字符串是否相等，因此证据合同同时强制记录 `same_as_executor=false`、`same_as_test_designer=false`、外部性和冲突披露；发布校验再对已记录的 actor ID 做语义复核。任一条不成立，高复核等级无效。

## 5. 治理、角色与测试独立性

| 角色 | 职责 | 不得替代 |
| --- | --- | --- |
| Profile Owner | 批准范围、项目判据、裁剪和版本；当前为 Ethan | 外部认证机构 |
| Claim Owner | 说明业务风险和被测声明 | 执行证据本身 |
| Test Designer | 在执行前锁定输入、正负用例、判据和结果穷举表 | 事后改尺者 |
| Executor | 运行测试并保存原始观测 | 默认独立复核者 |
| Oracle Evaluator | 不读取测试程序的汇总 `PASS`，从原始事实独立重算 | 测试程序自报结果 |
| Reviewer | 核对范围、判据锁定时间、证据链、oracle 和缺口 | 未披露关系的签名 |

同一人可以承担多个角色，但必须如实记录，此时不得标为 `INDEPENDENTLY REVIEWED`。工具不是复核者；工具生成的 `PASS` 不是独立 oracle。

## 6. 执行前锁尺与穷举判定

每次执行前必须形成不可含糊的 criteria 记录并计算 SHA-256，至少锁定：声明、风险、适用性、测试基础、环境、输入、样本、正向用例、负向用例、阈值、独立 oracle、必需证据和以下结果表。执行后只能新增观测，不能改写判据；确需改尺时创建新 criteria ID 和新版本，旧记录保留。

本版追踪矩阵的 `criteria_lock.status` 为 `LOCKED`；其锁定身份是“包含该矩阵的 Git 提交”，不在文件内回填会导致循环变化的自身 SHA。E2.0-RC1 候选基线 `72ab307ffc0dffff424d929c003fbe06b1386457` 永久保留为前件；本版任一范围、判据、schema 或结果枚举变更都必须另起版本。

| 预先列明的情形 | 声明结论 |
| --- | --- |
| 全部必需证据可读、哈希匹配、oracle 所有强制条件满足 | `MET`，并附实际环境保证 |
| 任一强制条件被原始观测明确违反 | `NOT MET`，不得因其他条件通过而抵销 |
| 缺少必需证据、环境身份不成立、观测冲突、oracle 无法独立重算 | `UNKNOWN` |
| 有明确范围决定、理由、批准者和复核触发条件 | `NOT APPLICABLE` |

禁止事后新增第五种结果，禁止把 `UNKNOWN` 当作 `MET`，禁止用较高环境的存在替代该环境的实际证据。

## 8. E v1 冻结与迁移规则

自本基线起，旧 E01—E12 冻结为 **“E v1 内部架构验证标准”**。历史文件、原始结果和当时环境标签原样保留，不追溯改写；E2.0 只增加新的解释层。旧 `PASS` 不自动转换成 E2.0 的 `MET`，更不能自动升级为 staging、production 或独立复核等级。

本版已将 E01—E12 每项且仅一次映射到 E2.0，没有裁掉 E01—E04：

- 节点模型与拓扑：E01、E02；分别衡量三个同级节点的共享模型/横向隔离，以及 L0—L11 统一纵链/关系版本/边界。
- 授权交集与身份隔离：E03、E04；分别保留 32 行五维真值表与同凭据三 Realm 身份/会话切换隔离。E03 不从 E12 继承真值表，E04 不从 E12 继承凭据发现或会话迁移证据。
- 发布与规模：E05、E06、E10、E11；分别保留 Hosted 零扇出、Sovereign 单节点切换、跨表面共享变更、规模曲线，不重复计分。
- 节点升级连续性：E07。
- 交易完整性与恢复：E08、E09；分别衡量业务守恒和执行幂等/恢复，不重复计分。
- 多租户隔离：E12。

## 9. E06 校准结论

E06 的旧 `PASS` 被保留在 E v1 原报告中。依据 E2.0 独立读取现有六份原始 JSON 后，本次只能给出：

> 声明结论 `MET`；环境保证 **`DEV VERIFIED`**；复核保证 **`NOT REVIEWED`**。

理由：三个节点均为临时 Docker 隔离进程，网络为 `none`，没有生产部署、生产指针、真实客户记录或支付调用。原始收据支持在该开发机制环境中观察到 S-B 的 A→B→A、S-A/S-C 零变化、同一 B 制品身份和历史摘要零变化；但“disposable Docker staging”这个自定义名称不满足 E2.0 的真实 staging 定义，也没有外部独立复核签名。

完整判据和证据记录见 [E06 校准判据](./evidence/e2.0/E2.0-E06-校准判据.json)与 [E06 校准样例](./evidence/e2.0/E2.0-E06-校准样例.json)。补证路线依次是：真实 staging 身份与差异清单 → 同 SHA 在真实 staging 重放并保存独立观测 → 经另行授权的生产只读观测 → 与设计/执行责任分离的外部复核。四层互不替代。

## 10. 版本与变更管理

1. 任何标准版本、公开状态、范围、判据、schema 或结果枚举变化都提升 E2.x 版本，并保留旧配置。
2. 原始证据不可覆盖；更正采用新 evidence ID，并通过 `supersedes` 指向旧记录。
3. 标准链接每次发布时复核；链接可访问不等于拥有标准全文许可。
4. 结果只对记录的 Git SHA、配置摘要、环境和时间窗有效。
5. E2.0 文档或工具失败只形成 `UNKNOWN` 或报告缺口，不影响应用、合并、发布和部署。

## 11. 允许与禁止的对外表述

允许：

- “E2.0 正式尺子已锁定，覆盖 E01—E12；全量重测尚未执行。”
- “本项目建立了基于公开国际标准来源的裁剪对标配置和可复核证据格式。”
- “E06 在临时 Docker 开发机制环境达到 `DEV VERIFIED`，尚未达到真实 staging、生产或独立复核等级。”

禁止：

- “已获全球认证”“通过 ISO/IEC 25010 认证”“通过 ISO/IEC/IEEE 29119 认证/正式符合”“已获 OWASP 认证”。
- 在未确认适用范围和完成规定验证前声称“PCI DSS 合规”或“PCI DSS 不适用”。
- 把 ISO 22301 参考映射称为 BCMS 符合或认证。
- 只写 `PASS`，隐去环境、复核等级、适用性、裁剪和缺口。

外部审计材料和复现顺序见 [E2.0 外部审计交接清单](./18-E2.0-外部审计交接清单.md)。
