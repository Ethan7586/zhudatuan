# 智慧翼企业福利商城——生产型 MVP 开发说明

技术服务方：雍彻科技（YONGCHE TECH）

更新日期：2026-07-24

## 1. 本阶段结论

项目已从“纯前端演示原型”进入“生产型 MVP 底座”建设。现有商城界面继续用于甲方确认交互和视觉；新增的服务端、Supabase PostgreSQL 数据库、权限、订单、内部账户支付、审计等模块，作为后续真实业务的权威数据源。

正式数据库部署在 Supabase 东京区域 `ap-northeast-1`。浏览器不持有数据库管理密钥，前端只访问商城服务端 API；服务端通过 Supabase Data API 调用受控的 PostgreSQL 函数。

已登录的 MVP 验收会话不再把浏览器 `localStorage` 中的余额、订单、流水或库存视为正式数据；这些数据全部以服务端和数据库为准。未登录页面保留少量只读演示兼容数据，便于需求评审。

## 2. 已落地的生产能力

### 2.1 四层业务隔离

数据模型按以下四层建立：

1. 平台/集团租户（tenant）
2. 企业（enterprise）
3. 商城（mall）
4. 员工用户（user）

所有商品、库存、账户、订单、支付、售后和审计查询均带租户及商城范围；员工订单额外校验企业和本人用户 ID，避免只靠前端切换造成串库。

### 2.2 核心数据域

已建立 27 张生产/安全业务表：

- 组织与身份：租户、企业、商城、部门、用户
- 权限：角色、权限、角色权限、用户角色
- 商品供应链：供应商、SPU、SKU、库存
- 福利资金：福利/餐卡账户、不可变账户流水
- 交易：购物车、购物车明细、主订单、供应商子订单、订单明细
- 支付售后：支付单、支付分摊、退款、售后
- 治理：审计日志、幂等记录
- 安全：登录失败计数与限时封禁

金额统一以“分”为单位存储，禁止使用浮点数作为资金字段。

### 2.3 数据库级风险控制

- 库存采用带可售条件的原子更新，预占失败会回滚整个下单事务。
- 福利卡与餐卡在行锁内扣减，任何账户余额不足都会回滚整个支付事务。
- 两个账户的扣款合计必须严格等于订单应付金额，订单只能从待支付状态支付一次。
- 账户流水和审计日志禁止更新、禁止删除。
- 创建订单和支付均要求 `Idempotency-Key`，同一幂等键不能提交不同内容。
- 下单时按供应商自动拆分子订单。
- 收货人姓名、电话和地址使用 AES-256-GCM 加密后入库；未配置密钥时禁止创建订单。
- 27 张业务表全部启用 Row Level Security；`anon` 与普通 `authenticated` 角色没有直接表权限。
- MVP 访问码换取 8 小时、`HttpOnly + Secure + SameSite=Lax` 的签名会话；连续失败 5 次后按来源限时封禁 15 分钟。
- 售后申请校验订单归属、订单状态、实付上限和重复处理中工单，并写入审计日志。

### 2.4 已实现的 API

| 方法 | 地址                                    | 用途                                   |
| ---- | --------------------------------------- | -------------------------------------- |
| GET  | `/api/health`                           | 快速存活检查，不访问远程数据库         |
| GET  | `/api/ready`                            | 数据库、认证和加密配置深度就绪检查     |
| GET  | `/api/v1/products`                      | 按商城、分类分页查询商品和实时可售库存 |
| POST | `/api/v1/auth/login`                    | 使用阶段访问码建立安全验收会话         |
| POST | `/api/v1/auth/logout`                   | 销毁验收会话                           |
| GET  | `/api/v1/auth/session`                  | 查询当前会话状态                       |
| GET  | `/api/v1/bootstrap`                     | 返回当前员工、权限和商城范围           |
| GET  | `/api/v1/accounts`                      | 查询本人福利卡、餐卡余额               |
| GET  | `/api/v1/account-ledgers`               | 查询本人真实账户流水                   |
| GET  | `/api/v1/orders`                        | 查询本人订单                           |
| POST | `/api/v1/orders`                        | 加密收货信息、预占库存、创建主子订单   |
| POST | `/api/v1/orders/{id}/payments/internal` | 福利卡和餐卡组合支付                   |
| GET  | `/api/v1/after-sales`                   | 查询本人售后工单                       |
| POST | `/api/v1/after-sales`                   | 提交本人订单售后申请                   |

正式环境的业务接口默认拒绝匿名请求。开发身份头仅在 `APP_ENV=development` 且 `AUTH_MODE=development` 两项同时成立时启用。

前端已接入生产商品目录、会话、账户余额、账户流水、订单创建、内部账户支付、本人订单和售后申请。登录后首页、分类、详情、结算、订单、余额和售后读取同一套权威数据。`MVP验收台`用于检查环境和核心流程，不等同于正式运营管理后台。

## 3. 当前刻意未开放的能力

以下事项必须取得甲方的真实资质、账号或业务规则后才能安全接入：

- 企业 SSO、微信小程序登录或手机号认证
- 微信支付/支付宝/银联商户号及回调证书
- 阿里权益及其他供应商商品、库存、订单、发货、退款接口
- 企业组织架构和员工同步数据
- 正式商城、企业、部门和员工初始化数据
- 短信、邮件和企业微信通知通道
- 客服系统、工单 SLA 和人工退款审批规则
- 发票、结算周期、供应商对账及财务科目

在上述信息未到位前，系统采取“安全失败”：允许公开查看测试商品，但不允许匿名下单或扣款。

## 4. 从演示数据切换到生产数据

切换分三步执行：

1. 甲方确认身份方案，完成签名验证与账号绑定。
2. 导入正式租户、企业、商城、员工、商品、SKU、库存和账户期初余额。
3. 将卡券、收藏和购物车从当前设备级兼容实现迁移至服务端，完成多设备一致性验收。

切换后 `localStorage` 只保留主题、提示关闭状态等设备偏好，不再保存余额、订单、卡券或库存。
