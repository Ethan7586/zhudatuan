# 一、实施前必须锁死的架构决策

## 1. `zhudatuan` 是唯一主线

只从 `/Users/changshengwang/Workspace/zhudatuan-li` 提取以下设计语义：

- 邀请成功后一次性展示邀请码。
- 客服三栏工作台。
- 消息气泡、发送区、上下文面板。
- 工单队列选择、移动端返回、错误重试。
- 弹窗、加载、空状态、无权限提示等 UX。

禁止复制：

- `zhudatuan-li/services/commerce-api`。
- `routerSupport.ts`。
- 旧数据库 migration。
- 旧权限体系。
- 手写 Fetch 协议层。
- Mock、showcase、临时代理接口。
- 旧新版开关和兼容 DTO。

## 2. `groupconsole`、`mallconsole` 不能成为新的 wire target

架构文档中的 `groupconsole`、`mallconsole` 是产品视角，不应扩展当前底层目标枚举。

正式映射为：

| 产品入口 | `X-Client-Target` | 权限范围 |
|---|---|---|
| 集团控制台客服 | `console` | `scope.kind=enterprise` |
| 商城控制台客服 | `console` | `scope.kind=mall` |
| 员工商城客服 | `storefront` | 当前商城与 `self` |
| 控制台邀请管理 | `console` | 当前 enterprise/mall scope |
| 员工邀请码注册 | `storefront` | 邀请绑定 organization |

因此不修改 `OPERATION_TARGETS=['console','storefront']`，避免把新概念扩散到认证、CSRF、会话、导航和全部 SDK。

## 3. 邀请码只能有一条兑换路径

当前存在两个行为：

- `identity.invitations.resolve` 只返回邀请元数据。
- `identity.sessions.create(method='invitation')` 实际执行锁定、Claim、PreAuth、OTP、Session。

最终必须硬切为：

```text
identity.invitations.resolve
    = 唯一的邀请码提交、锁定、Claim、PreAuth、OTP/Session 路径

identity.sessions.create
    = 仅保留 password、otp 等已有身份登录
```

不能让两个 operation 同时具备邀请码兑换能力，否则会产生安全策略、速率限制、审计和并发语义重复。

## 4. 普通员工邀请允许 AAL2，高风险邀请要求 AAL3

当前 `identity.invitation.issue` 的 `minimumAssurance` 是 3，导致普通员工邀请也必须 AAL3，与方案不符。

最终规则：

- `enrollment + storefront + 单员工`：AAL2。
- `campaign`：AAL3。
- `signin`：AAL3。
- 撤销邀请：AAL3。
- 创建 UI 根据当前 assurance 决定显示、禁用或触发 Step-up。
- 后端根据 `kind` 再做动态检查，不能只依赖前端。

## 5. `expectedVersion` 只保留一份

架构文档示例把 `expectedVersion` 写在 body 中，但当前主线已经将其统一建模为：

```text
SDK context.expectedVersion
→ If-Match
→ OperationInput.expectedVersion
```

落地时不得再在业务 body 中复制 `expectedVersion`。否则会出现 body 与 `If-Match` 不一致的双真相。

## 6. SSE 事件只传轻量事实

SSE 中不传消息正文、手机号、邀请码、对象存储引用。

示例：

```ts
interface SupportEvent {
  id: string
  type:
    | 'message.sent'
    | 'ticket.updated'
    | 'ticket.assigned'
    | 'ticket.closed'
    | 'ticket.reopened'
    | 'readstate.updated'
    | 'attachment.ready'
    | 'attachment.rejected'
  scopeId: string
  ticketId: string
  conversationId: string
  sequence?: number
  version?: number
  occurredAt: string
}
```

客户端收到后按 ID、Sequence、Version 增量拉取权威数据。

## 7. 外部 I/O 不进入数据库事务

必须放在 Durable Handler 的 `prepare/finalize`：

- KMS 加密、解密。
- 对象存储签名。
- Secret Store 查询。
- 外部账号连通性验证。
- Redis 阻塞读取。

事务内只执行数据库状态变更、历史、Outbox。

```text
UI 选择文件

→ support.attachments.create
→ 服务端生成不可猜测 object key
→ 返回签名 PUT
→ 浏览器直传 Object Store
→ supportscan Job Inspect
→ Hash/MIME/魔数/恶意内容检查
→ clean/rejected
→ Outbox
→ SSE
→ UI 更新状态
```

当前 `SupportMessageActions.createAttachment()` 中以下逻辑删除：

- Base64 正文上传。
- 1MB body 内嵌。
- API 进程读取完整文件。
- 上传后直接标记 clean。

`supportscan` 增强：

- Inspect 对象存在性。
- SHA256。
- Size。
- Content-Type。
- 文件魔数。
- 病毒扫描结果。
- 文件名清洗。
- 扫描失败原因。
- 幂等状态迁移。
- ready/rejected 事件。
