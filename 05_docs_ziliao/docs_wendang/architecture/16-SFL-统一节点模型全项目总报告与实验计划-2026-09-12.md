## 3. 最终目标定稿：一套模型、一套内核、一次构建、多节点数据驱动

最终目标只有一个版本：

1. 所有 L0—L11、横向和纵向节点使用同一节点模型、同一商城内核和同一业务代码。
2. 一次共享代码修改只形成一次构建和一个不可变制品。节点不得复制源码、创建长期节点专属业务分支或节点专属构建。
3. 服务端先解析 `NodeContext`，再绑定当前活动身份和 `Membership`，随后计算 `Permission ∩ Scope ∩ CapabilitySet/NodeProfile ∩ 资源就绪状态`，据此决定页面、API、任务和服务是否可用。
4. 横向与纵向只改变 `operating_line_id/line_id`、`parent_node_id`、`signed_level`、关系版本和 Scope 数据，不改变节点类型或代码生成方式。
5. Hosted 节点是共享宿主内的数据行；共享内核变更对 Hosted 节点的逐节点操作扇出为零。
6. Sovereign 节点使用同源不可变制品，但保留独立发布指针，可以渐进升级、暂时版本不同和单节点回滚；“同模型”不等于“同时切换”。

这不是 `NodeCloneRequest`、`NodeBlueprint` 或“复制某个现有节点作为模板”的方案。当前主轴全仓精确检索没有发现 `NodeCloneRequest` 或 `NodeBlueprint` 定义。第十三、十四批的 `CloneCompanyTemplate` 是公司业务引导器：它创建独立 Realm、商城、经营线、Hosted L0、Membership、应用和待绑定配置，明确不复制源码、运行实例或历史订单；它不能被提升为统一节点模型本身。

## 5. 最终架构

### 5.1 决策链

```text
同一共享商城内核 / 同一公共契约 / 同源不可变制品
                    ↓
Host 或入口精确解析服务端 NodeContext（未知 Host 不回退）
                    ↓
Credential → Principal → 当前 Realm Session → 单一活动 Membership
                    ↓
Operation + Permission + AccessVersion + Scope
                    ↓
Membership 可用 Operation（CapabilitySet）+ NodeProfile + 资源就绪
                    ↓
页面可见性 / API 可调用性 / 任务可执行性 / Provider 与服务可运行性
```

当前可定位的实际调用点：

- [`SflNodeKernel.ts`](../../../01_core_hexin/packages/config/src/SflNodeKernel.ts) 定义 `NodeContext`、`NodeRecord`、`NodeRelationRecord`、`NodeProfile`、`SovereigntyTier`、Manifest 和 `ReleasePointerRef`，并按 Host 精确解析上下文；未知或歧义 Host 均抛错。
- [`PgAccessResolvers.ts`](../../../01_core_hexin/services/commerce/src/foundation/security/PgAccessResolvers.ts) 用入口 Host 解析 Session，绑定 Realm 与活动节点；Membership、Scope 和可用 Operation 均来自数据库权威函数。
- [`AccessPipeline.ts`](../../../01_core_hexin/services/commerce/src/foundation/security/AccessPipeline.ts) 依次检查 Audience、Membership、Permission、AccessVersion、Scope、Capability、Assurance 和 Risk，然后才放行业务 Operation。
- [`AuthoritativeNodeContextResolver.ts`](../../../01_core_hexin/services/commerce/src/foundation/security/AuthoritativeNodeContextResolver.ts) 从节点事实和当前关系解析 self／ancestors／descendants／subtree。
- [`ExtensionRegistry.ts`](../../../01_core_hexin/services/commerce/src/bootstrap/ExtensionRegistry.ts) 以 provider + scope + capability 选择已安装适配器并检查健康状态，承接资源就绪维度。

当前代码没有一个名为 `CapabilitySet` 的统一类型；服务端用 `capability.membership_operations(membership_id)` 返回 Operation 列表，并装入 `AccessContext.capabilities`。这在行为上承担 CapabilitySet，但名称和跨页面／任务／服务的一致投影仍应由 E03、E10 验证。

### 5.2 Hosted 路径

Hosted 节点由 `organization.node + organization.noderelation + Realm/Membership/Scope/Capability` 等数据事实表达。创建、启停、授权、关系换版和 Hosted 开店都应只产生数据库写入、审计和 Outbox，不生成 Node Manifest、进程、端口或发布指针。共享代码形成新制品后，Hosted 节点随宿主共享内核生效，不做逐节点部署或逐节点构建。

第七批和第十四批数据库证据均记录 `infrastructure_action_count = 0`；第十四批本次复跑结果为 4 个公司引导记录、16 个待绑定项、4 个 Outbox 事件、基础设施动作总数 0。

### 5.3 Sovereign 路径

Sovereign 节点拥有独立入口、资源绑定、运行实例、Manifest 和发布指针。它与其他节点使用同源制品，但每个节点可以把自己的指针从制品 A 推进到制品 B，也可以只回滚目标节点；其他节点的指针和运行状态必须保持不变。

这意味着一次共享代码变更的正确扇出是：

- 构建侧：一次源码版本 → 一次构建身份 → 一个不可变制品身份；
- Hosted 运行侧：宿主切换后覆盖其承载节点，逐 Hosted 节点操作数为 0；
- Sovereign 运行侧：多个独立指针可以在不同时间引用同源制品，允许渐进升级和单节点回滚；
- 禁止项：节点源码副本、节点专属业务分支、节点专属构建和长期代码分叉。

当前 Node Manifest 候选 fixture 可证明多个节点引用同一 `source_sha/build_id/immutable_artifact_digest` 且 `build_count=1`；AutoNode 本地测试也声明 `source_tree_copy_count=0`、`node_specific_build_count=0`。但通用发布引擎仍使用一个 package set 中的多个 target artifact，最新 CI 也描述“重建全部运行制品”。是否已收口成任务要求的“全项目一个不可变制品”尚无生产收据，故生产层保持 `UNKNOWN`，由 E10/E11 直接验证。

## 6. 横向与纵向如何统一

横向和纵向不是两套生成器：

- 横向三个同级节点：同一 `operating_line_id` 下使用同一父节点和相同 `signed_level`，仅 `operating_node_id`、Membership、Scope、Mall 或资源绑定不同；若位于不同经营线，则各线有自己的 L0，仍使用同一行模型。
- 纵向 L0—L11：同一经营线内每个节点把上一节点作为 `parent_node_id`，`relation_version/effective_at/superseded_at` 记录当前与历史父边，`signed_level` 记录线内相对位置。
- 换父或换线：写入新的版本化关系事实，保留原父边和历史交易路径；不重算已成交路径。
- 权限：级号本身不授权。管理员是独立身份；会员与管理员都经 Permission、Scope 和 Capability 判定。

数据库底座 [`20260911200000_create_sfl_node_sovereignty.sql`](../../../02_platform_pingtai/database/supabase/migrations/20260911200000_create_sfl_node_sovereignty.sql) 用一套 `node/noderelation` 表达主权、画像、Realm、父边、级号和关系版本；[`20260912010000_create_sfl_node_context_scope.sql`](../../../02_platform_pingtai/database/supabase/migrations/20260912010000_create_sfl_node_context_scope.sql) 用同一闭包与解析函数覆盖 self、祖先、后代和子树。因此横向／纵向的差别已经是关系数据差别，而不是源码差别。

## 10. 真实剩余项、非阻塞后续与风险

### 10.1 已知实现差距

1. `NodeContext` 缺 `lineage_digest`；千万级后代下的常数级失效语义未证明。
2. Cross-Node Grant 和授权型跨节点 Worker 未形成可验收闭环。
3. Domain Binding 目前只有 `candidate/active/rolled_back`，未实现历史验收所需 `primary/draining/retired` 完整语义。
4. 第十批机器矩阵缺逐 Operation 的请求 Schema、响应 Schema 和 Scope Resolver 显式引用。
5. 当前通用发布引擎以 package set 包含多个 target artifact；是否满足“全项目一个不可变制品”的最终目标需实验直接判定。

### 10.2 节点特例与中立性风险

共享节点模型文件本身没有品牌或域名写死，但更广的应用／运行层仍可定位到：

- `commerce-api` 的固定 `zhudatuan.com` Origin、Cookie 名、支付回调和图片 Host；
- `auth-web` 的 `node:hbbtzn:l1` 品牌分支和固定入口策略；
- Console 的固定租户或品牌展示；
- `ApiBootstrap`、Catalog 和 Web Business Runtime 对 L0 的特殊注册表／Scope 选择；
- `PgSessionResolver` 在数据库缺新投影列时回退旧 Session 投影；
- 注册业务对 L0—L5、L6—L11、L11 截止的显式判断。最后一项属于现行产品语义，前五项需要区分“产品品牌层允许的适配”与“共享运行内核中的节点特例”。

这不证明已经串线，但证明“所有页面、API、任务和服务完全由统一上下文动态决定”尚不能判定为生产完成。

### 10.3 生产与证据 UNKNOWN

- AutoNode C1 的三个真实 L1、同源制品、27/27 服务、单节点真实回滚与部署收据：仓库内没有可读收据，本报告不宣称 PASS。
- 每个启用支付节点的真实渠道 7/7。
- 两个以上真实 Sovereign 节点的同源制品渐进升级、单节点回滚和其他节点不变。
- DNS → Tunnel → gateway → process 的真实停链隔离。
- 逐节点 artifact／Manifest／binding／pointer／runtime 一致性机器包。
- 浏览器视觉、完整四入口 Login Intent 负向矩阵和真实恢复。

### 10.4 非阻塞后续

E01—E12 是实验计划，不是新标准，不自动阻塞已有业务。可先在本地和 staging 运行 E01—E05、E07—E09、E11—E12；E06、E10 需要 staging 的真实 Sovereign 指针与一次构建制品。生产证据只在另行授权真实生产实验后形成。

## 11. 商业与组织价值

- **规模**：新增 Hosted 节点的主要成本从“复制项目和部署服务”降为“写入节点、关系、身份、范围和能力事实”；E11 将量化代码量、构建次数和 Hosted 操作数是否保持常数。
- **隔离**：同凭据可以发现多个 Realm 身份，但活动 Membership、Scope、权益和交易不合并，降低串号和跨商城泄漏风险。
- **开店与升级**：会员开店升级原节点，不丢血缘和历史；业务成熟后可显式升级 Sovereign，获得独立入口、资源和发布节奏。
- **组织治理**：管理员不占用 L 级，管理段和会员段通过独立 Operation/Permission/Scope 表达，避免“上级天然拥有下级数据”。
- **供应商网络**：一个商城可形成多个供应商经济腿，供应关系、合同、履约和结算责任独立可追踪。
- **四流与售后**：订单、商品、现金、财务各守权威事实；部分退款按原商品行和原路径逆向回放，关系换版不重算历史。
- **发布效率**：Hosted 零逐节点扇出，Sovereign 独立指针渐进发布；若 E10/E11 证明单制品目标，将把节点增长与构建成本彻底解耦。

## 13. 结论

SFL 已经完成最难的一步：把“节点”从代码副本和部署模板，提升为共享内核中的业务事实；把级号、能力、身份、权限、范围和主权拆成正交维度；再把商城、供应商和四流放回同一可追踪模型。第五至第十四批使这套模型从架构文字进入数据库合同、服务入口、执行内核和真实 PostgreSQL 业务验证。

但项目尚不能宣布“全部完成”。最准确的结论是：**产品模型完成，候选实现与主轴集成高度完成，生产全覆盖未完成。** 下一阶段不需要再发明另一套节点模板，而需要用 E01—E12 把横纵统一、全真值授权、Hosted 零扇出、Sovereign 同源渐进发布、一次构建一个制品和规模不增长逐项变成可复核证据，并对仍存在的应用特例与历史兼容路径完成边界收口。
