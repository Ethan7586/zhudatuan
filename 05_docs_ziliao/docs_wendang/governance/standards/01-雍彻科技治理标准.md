# 雍彻科技治理标准 v1.0.0

本标准由根 [`LAW.md`](../../../../LAW.md) 启用后生效。它只能管理“规则如何成为标准”，不能自行启用自己，也不能替 Ethan 创造决定。

## 1. 唯一职责

本标准负责：标准的制定、标识、版本、状态、作用范围、Owner、职责、冲突、替代和废止；工作区写入归属；外部状态变更授权；有限“须 Ethan 授权操作”的登记方法；公共契约单一权威源原则。

本标准不负责：定义节点、会员、交易或产品语义；指定数据库表、框架、脚本、发布工具、测试数量或报告版式；把运行事实登记成永久规范。

## 2. 标准资格与元数据

一份文件只有同时满足以下条件，才有资格被 LAW 登记为标准：

1. 具有 `standard_id / 中文名称 / version / status / scope / effective_at / supersedes / authority / responsibility / explicit_non_responsibilities`；
2. 只有一个明确责任域，并写出不负责事项；
3. 每条强制规则登记规则 ID、Owner、职责范围、真实损失、触发条件、执行点、例外或退出方式、来源证据；
4. 不把测试、报告、证据、脚本、历史资料或当前运行状态当成规范来源；
5. 在 LAW 的有效标准登记区写明精确版本并标为 `ACTIVE`。

缺少第 5 项时，文件最多是 `REFERENCE`；文件正文写着“正式”“强制”或 `ACTIVE` 也不能自我启用。

## 3. 标识、版本与状态

- `standard_id` 永久稳定，不随文件名或路径改变。
- `version` 使用 `主版本.次版本.修订号`。改变责任域、权威语义或强制规则时提升主版本；新增向后兼容条款时提升次版本；不改变语义的澄清提升修订号。
- 现行权威状态只认 LAW 的 `ACTIVE` 登记；`REFERENCE / HISTORY / CANDIDATE_DELETE / UNKNOWN` 含义以 LAW 为准。
- 新版本生效时，`supersedes` 明确上一版本；旧版转为 `HISTORY`，不得同时保留两个相互冲突的 `ACTIVE` 版本。
- 标准废止必须有 Ethan 明确决定和替代／退出说明。删除文件不是废止标准的合法方法。

## 4. 制定、冲突、替代与废止

1. 提案先写责任域、损失和来源，再写规则；证据只能支持提案，不能批准提案。
2. 启用、停用、改变权威或修改 LAW，只能来自 Ethan 的明确决定。
3. 冲突按 `Ethan 当前明确决定 > LAW > LAW 登记的上级标准 > 下级标准 > 运行政策 > 参考资料` 裁定。
4. 同级标准冲突时，双方均不得越权覆盖；由 Ethan 明确裁定，随后分别升版或收窄范围。
5. 标准替代必须保留 `旧版本 → 新版本 → 生效时间 → 迁移／退出事项`，不改写历史验收和运行记录。
6. 物理删除标准、证据、分支、工作树或运行资源必须单独确认目标及保留位置；状态登记本身不是删除授权。

## 5. 有限“须 Ethan 授权操作”

“高风险”不是授权类别。某操作只有出现在已由 LAW 启用标准的“受保护操作登记”中，才属于须 Ethan 明确授权的操作。每一项必须包含：

```text
protected_operation_id
精确动作与精确对象范围
触发条件
不授权会避免的真实损失
可接受的授权语句
授权有效期或单次边界
执行后事实记录
退出或移除方式
来源：Ethan 的明确决定
```

没有登记项时默认放行；AI 不得按金额、环境、主机、账号、不可逆性或主观风险自行补充类别。v1.0.0 不新增任何受保护操作；后续登记必须由 Ethan 明确增加并升版相应标准。

## 6. 单一契约源原则

1. 同一公共操作的请求、响应、错误、版本与边界语义只能有一个权威契约源。
2. 前端类型、后端边界、Schema、SDK、文档和测试应由该源生成或共同引用；长期并存的平行手写公共响应模型不合规。
3. `strictObject` 不是错误。每个边界是严格拒绝额外字段，还是允许兼容扩展，必须由共享契约逐边界明确；实现方不得统一猜测。
4. 生成器、文件位置和迁移方案不是本标准的永久条款，由后续契约实施批次决定。
5. 契约冻结期间不得借治理标准修改现有契约代码；本条只建立未来接管原则。
