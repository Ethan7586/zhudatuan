# AU-453｜财务账本、对账、结算与提现生命周期

## 范围与方法

- 主审文件：`02_platform_pingtai/database/supabase/migrations/20260821043000_finance_lifecycle.sql`（405 行）。
- 人工审阅迁移的资金表、历史数据承接、账本保护、RLS、接口/事件注册和断言；反查 Finance API、结算 Worker、死信与事件订阅。
- 本轮为静态审阅；未执行迁移、付款、对账、数据库验证或线上查询。

## 真实运行关系

对账任务从渠道账单与内部资金事实比对；仅当对账已批准、差异为零且证据冻结时，`SettlementJobProcessor` 建立结算、冻结规则和行快照。结算审批/调整、提款申请/审批/恢复和发票请求经 Finance API 操作处理器进入数据库；提现使用带 idempotency key 的付款网关。`reconciliation`、`settlement`、`invoice` Worker 由统一任务目录注册，具有队列、超时、租约、重试与死信。

迁移将 journal 的幂等范围从全局改为 `(scope_id, reference_type, reference_id)`，建立对账明细、结算行与调整、分账、提现、期间关闭、发票行/快照和财务 backfill 证据。账户、账本、结算行和发票事实使用拒绝更新/删除的触发器保护；行级权限按 scope 限制应用会话，后台 job 身份专用于异步处理。

## 失败与恢复边界

- 提现的任务死信把 `processing` 改为 `uncertain` 并发布 `finance.withdrawal.uncertain`，避免在未知渠道状态下自动二次付款。
- 对账任务失败改为 `difference` 并保存死信证据；结算建立时复核账单哈希、可结算项目、排除迟到款项、冻结规则、行总额和重放一致性。
- 迁移登记对账差异、结算审批/调整、提现付款/不确定等运行事件，事件地图将其交给通知与投影消费者。

## 高风险迁移边界

迁移把财务、结算和发票的运行数据迁移到范围化、追加式且受 RLS 保护的模型，并创建历史 backfill 的哈希/笔数/金额证据。它是资金与税务的基础切换边界，登记为 **GX-0012**；不能以“旧迁移”或“无普通源码入口”认定无用。

## 评审结论

- **G0**：对账、结算、提现、发票、死信和事件消费者对这些表、函数和约束存在实际运行依赖。
- **GX-0012**：涉及历史财务、付款和不可变账本；禁止删除、改写、单独重放或与功能修复混合，需独立资金/数据/权限复核。
- 未发现本迁移新增且可直接证实的 P0–P3。尚未验证目标库的历史金额/笔数一致性、渠道支付状态和恢复演练结果。

## 后续验证与回滚边界

- 任何独立后续工作应从最新 `zdt-next` 建分支，验证多 scope journal 幂等、对账差异、结算冻结/审批、提款未知状态恢复、期间关闭、发票红冲与 RLS。
- 迁移或恢复必须先以 scope、币种、账本笔数/金额和渠道侧状态对账，并使用经演练的备份；不得在审计分支执行。
