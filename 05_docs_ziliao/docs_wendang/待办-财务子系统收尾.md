# 待办：财务子系统收尾

本文登记已有 schema 与集成规格、但生产路径尚未接入的财务能力。对应测试只做暂缓，断言体完整保留；实现完成后应逐项恢复为 `it` 并用全新 PostgreSQL/Redis 按 `replay:postgres → test:integration → test:adapters` 验收。

## FinanceReconciliation.test.ts

建议实现主入口：`01_core_hexin/services/commerce/src/modules/finance/03_application_yingyong/command/ReconcileStatement.ts` 的 `ReconcileStatement.execute`、`match` 与差异项投影逻辑。

### 对账-权威收款与部分退款

- 暂缓测试：`reconciles the captured external tender and only the succeeded partial refund leg`
- 业务规则：payment 只按已捕获的外部 tender 对账，refund 只按成功退款腿对账，并把权威来源、tender 金额和 allocation 数写入 evidence。
- 当前缺口：`match` 只按外部引用选单一 payment/refund 记录，没有从权威 tender/refund allocation 形成候选 evidence；查询中的 scope 参数也缺少足以兼容 PGlite 的显式类型。
- 建议位置：在 `ReconcileStatement.ts::match` 建立 payment/refund 候选 CTE，显式定型 scope 参数，并统一生成 candidates evidence。

### 对账-双向差异

- 暂缓测试：`creates both external-without-internal and internal-without-external differences idempotently`
- 业务规则：同一轮同时投影 provider-only 与 internal-only 差异，重复执行不得产生重复项，parent 汇总必须覆盖两侧净额。
- 当前缺口：现有 `match` 仅从 statementline 向内部事实匹配，不反向扫描权威内部 tender/refund；也没有内部差异项的幂等 upsert 与 evidence。
- 建议位置：在 `ReconcileStatement.ts::match` 增加 internal-only 候选与 reconciliationitem upsert，并由 `execute` 按完整差异集汇总 parent。

### 对账-重试投影合并

- 暂缓测试：`merges retry projections when an authoritative provider reference arrives later`
- 业务规则：权威引用后到达时，将先前两条缺失投影合并为一条 matched item，并保留 `REFERENCE_BECAME_AUTHORITATIVE` 证据。
- 当前缺口：现有冲突处理只按 `statement_line_id` 更新，无法识别并合并先前 internal-only 项，也不记录 retryMerge evidence。
- 建议位置：在 `ReconcileStatement.ts::match` 的 upsert/清理阶段按 reconciliation、kind 和 internal fact 合并重试投影。

### 对账-journal-反转与更正

- 暂缓测试：`fails closed when the source journal has a posted reversal_of relation`
- 暂缓测试：`fails closed when the source journal has a posted correction_of relation`
- 业务规则：来源 journal 存在已过账反转或更正关系时不得结算；分别生成 `INTERNAL_JOURNAL_REVERSED`、`INTERNAL_JOURNAL_CORRECTED`，并记录关系 journal 与 `settlementEligible=false`。
- 当前缺口：journal 候选只聚合 entry 金额，不读取 `reversal_of`、`correction_of` 或关系 journal，因而会错误匹配。
- 建议位置：扩展 `ReconcileStatement.ts::match` 的 journal candidates 与 reason/evidence 决策。

### 对账-多对一歧义

- 暂缓测试：`fails closed instead of allocating one provider line across multiple payment allocations`
- 业务规则：单个 provider line 对应多个 payment allocation 时必须以 `MANY_TO_ONE_UNSUPPORTED` fail closed，不得任取一个内部事实。
- 当前缺口：`matched` 使用 `distinct on` 直接选择首个候选，没有候选数量、allocationCount 或歧义分支。
- 建议位置：在 `ReconcileStatement.ts::match` 先聚合候选数量和 allocation evidence，再决定 matched/difference。

### 对账-仅内部权威事实

- 暂缓测试：`detects an authoritative captured tender even when both its journal and provider statement line are missing`
- 业务规则：即使 journal 与 provider statementline 都不存在，已捕获权威 tender 仍需形成 internal-only difference，parent credit/difference 同步更新。
- 当前缺口：匹配入口完全由 statementline 驱动，空 statement 不会扫描 payment tender，也不会生成 `INTERNAL_JOURNAL_MISSING` 项。
- 建议位置：在 `ReconcileStatement.ts::match` 增加权威内部事实反向扫描，并在 `execute` 汇总 internal-only 金额。

### 对账-late-journal-evidence

- 暂缓测试：`preserves late capture/refund journal types as non-settleable reconciliation evidence`
- 业务规则：late capture/refund 即使金额匹配，也必须保留 journal reference type，并标记 `settlementEligible=false`。
- 当前缺口：当前 evidence 只包含 statement 基础字段，没有传播 `payment.late.detected`、`payment.late.refunded` 等 journalReferenceType。
- 建议位置：在 `ReconcileStatement.ts::match` 的 journal/payment/refund candidates 中投影 reference_type 与结算资格。

### 对账-差异审批版本

- 暂缓测试：`requires itemVersion, advances the parent version and enforces a different item approver`
- 业务规则：差异项提议/审批使用 itemVersion 乐观锁，parent version 同步推进，并禁止提议人自批。
- 当前缺口：该流程依赖完整 difference item，但当前匹配在进入 resolver 前即因候选 SQL 参数未定型失败，无法形成可审批投影。
- 建议位置：先在 `ReconcileStatement.ts::match` 完成显式参数定型和差异投影，再核对 `ResolveDifference.ts` 的 item/parent 版本联动。

### 对账-重复-provider-reference

- 暂缓测试：`represents ambiguous provider references without selecting an arbitrary internal fact`
- 业务规则：相同 provider reference 命中多个内部事实时，provider 侧与每个内部侧都应形成 `MANY_TO_ONE_UNSUPPORTED` 差异，不得任取候选。
- 当前缺口：refund join 可返回多候选，但 `distinct on` 会任取一个，且缺少 provider-side/internal-side 的歧义投影。
- 建议位置：在 `ReconcileStatement.ts::match` 按 line_id 聚合候选并为歧义两侧分别 upsert reconciliationitem。

## InvoiceIssueIntegrity.test.ts

### 开票-不可变-owner-快照查询

- 暂缓测试：`reads requests through the immutable owner snapshot rather than the live profile owner`
- 业务规则：发票请求可见范围由审批时不可变 `invoice.requestprofile.owner_id` 决定，不随 live profile owner 漂移。
- 当前缺口：`GetInvoices.ts::invoice.requests.read` 通过 live `invoice.profile` 过滤 owner，未使用 requestprofile snapshot。
- 建议位置：`01_core_hexin/services/commerce/src/modules/finance/03_application_yingyong/query/GetInvoices.ts` 的 `invoice.requests.read` 查询。

### 开票-完整签发生命周期

- 暂缓测试：`validates one sealed snapshot, persists the receipt atomically and skips a completed replay`
- 业务规则：一次 claim 对应一次密封快照、artifact 与 finalize；完成后的 job 重放不得再次调用 provider。
- 当前缺口：`InvoiceJobProcessor.issue` 直接把 request 改成 issuing、调用 provider、写 document/outbox，未调用数据库已有的 claim/register artifact/finalize 函数，且相关 SQL 参数未完整定型。
- 建议位置：`01_core_hexin/services/commerce/src/modules/finance/05_interface_jieru/job/InvoiceJob.ts` 的 `InvoiceJobProcessor.issue`。

### 开票-签发前完整性校验

- 暂缓测试：`fails closed before decrypting or calling the provider when amount or source hash is invalid`
- 业务规则：request amount 与冻结行合计、source hash 必须在解密及 provider 调用前校验，分别抛出精确错误。
- 当前缺口：job 未读取/验证密封 requestline 与 source hash，先进入解密/provider 路径，issuer 无结果时表现为 `contentType` 未定义。
- 建议位置：`InvoiceJob.ts::InvoiceJobProcessor.issue`，claim 后、KMS 解密前。

### 开票-审批快照一致性

- 暂缓测试：`rejects approval-era line mutation and detects a legacy requestline/rendered-line mismatch before issue`
- 业务规则：审批时的 requestline 与签发渲染行必须一致；历史脏数据也应在 provider 调用前 fail closed。
- 当前缺口：job 直接读取 `invoice.line`，未比较不可变 requestline 快照、rendered line 与 sealed hash。
- 建议位置：`InvoiceJob.ts::InvoiceJobProcessor.issue` 的签发前快照验证阶段。

### 开票-红票签发

- 暂缓测试：`issues one immutable red document linked to the original and replays without a second provider call`
- 业务规则：红票文档不可变并关联原票 document，重复 job 不得二次签发。
- 当前缺口：现有直接 document upsert 绕过 claim/artifact/finalize，不能可靠保证不可变关联及 provider 后幂等。
- 建议位置：`InvoiceJob.ts::InvoiceJobProcessor.issue`，通过 `invoice.claim_issue`、`invoice.register_issue_artifact`、`invoice.finalize_issue` 完成红票路径。

### 开票-红票失败绑定

- 暂缓测试：`keeps a failed post-provider red attempt bound to its original invoice`
- 业务规则：provider 已响应但后续持久化失败时，红票尝试仍绑定原票，且不得产生重复红票请求。
- 当前缺口：失败后的 artifact/original binding 没有通过受控函数持久化，deadletter 也只处理 issuing 状态。
- 建议位置：`InvoiceJob.ts::InvoiceJobProcessor.issue` 的 artifact 注册/失败释放路径，并与 `FinanceDeadletter.ts::record` 协同。

### 开票-outbox-冲突回滚

- 暂缓测试：`rolls back document and status changes when an outbox id has conflicting evidence`
- 业务规则：固定 outbox id 已存在冲突证据时，document/status 应原子回滚，上传 artifact 标记 orphan。
- 当前缺口：job 对 outbox 使用 `on conflict do nothing`，不验证既有 evidence；document、状态和 artifact 也未统一走 finalize 事务。
- 建议位置：`InvoiceJob.ts::InvoiceJobProcessor.issue`，以 `invoice.finalize_issue` 承担冲突检查与原子提交。

### 开票-worker-scope

- 暂缓测试：`rejects a cross-scope invoice worker before decrypt or provider access`
- 业务规则：job scope 必须与不可变 request owner scope 一致，校验应早于 KMS/provider。
- 当前缺口：`InvoiceJobProcessor.process` 只读取 request id，没有把 `job.scope_id` 带入 claim/owner 校验。
- 建议位置：`InvoiceJob.ts::process/issue`，claim 后立即比较 job scope 与 requestprofile owner。

### 开票-deadletter-approved

- 暂缓测试：`moves a terminal pre-claim failure to audited failed state through the deadletter path`
- 业务规则：claim 前的终态错误也要把 approved request 转为 failed，并追加 statusevent 与 deadletter evidence。
- 当前缺口：`FinanceDeadletter.record` 只允许 `state='issuing'` 更新，且没有写 invoice.statusevent，因此 approved 保持不变。
- 建议位置：`01_core_hexin/services/commerce/src/modules/finance/05_interface_jieru/job/FinanceDeadletter.ts` 的 invoice 分支，或新增受控数据库函数后由该分支调用。
