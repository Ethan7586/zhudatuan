## 1. 本阶段结论

1. 本阶段只建立台账，没有改变任何业务、契约、数据库、CI、发布链路、GitHub 设置或生产状态。
2. 旧体系尚未真正失去指挥权：根规则文本彼此冲突，Actions 仍启用，生产机还有启用中的发布生命周期定时器与路径触发器。
3. GitHub 当前有 24 条远程分支，`zdt-next` 是默认分支，但 `protected=false`；仓库没有 GitHub Environment。`CODEOWNERS` 非空，但当前没有主轴保护机制证明它会强制 Ethan 审批。
4. `04_tools/scripts/check/` 确有 49 个物理文件：42 个顶层文件、7 个 `callgraph/` 子模块。7 个子模块全部可从 `check:calls` 间接到达，不是死文件。
5. `sfl-hosted-node-provisioning.pg17-fixture.mjs` 没有发现 package、workflow 或代码调用入口；只在验收资料中发现人工命令，因此维持“疑似废弃／可能是人工夹具”，不删除。
6. 当前没有 `05_docs_ziliao/docs_wendang/zdt.md`。现有 SFL 架构文档、提示词、历史报告都只能作为资料，不能自动补成新体系权威。
7. 阶段二必须先安装新权威，再让旧体系失去指挥权；物理删除只能放在新体系接管并验收之后。

## 2. 本台账的判定口径

### 2.1 状态词

| 状态 | 含义 |
| --- | --- |
| 生效 | 当前会被 agent、GitHub、脚本或生产控制面实际读取或执行 |
| 可调用 | 有明确入口，但不会在当前默认流水线自动运行 |
| 资料 | 只能提供历史、设计或取证信息，不得作为执行命令 |
| 冲突 | 与另一条当前可见规则给出相反指令，不能靠文件自称的优先级解决 |
| 未知 | 本阶段没有直接证据，禁止推断补齐 |

### 2.2 强制规则资格

新体系中的每条强制规则必须同时具备：明确作用域、责任人、真实损失、触发条件、执行机制和退出／例外方式。只有命名偏好、固定数量、固定格式、固定时间或证据排版，而没有真实损失的，最多进入参考层。

### 5.2 Actions 的真实调用链

```text
PR / push(zdt-next) / workflow_dispatch
  -> Affected Delivery.plan
  -> release-engine plan
  -> lane != A3 且 deployRequired=true
       -> related tests -> typecheck -> build -> package
       -> push(zdt-next) 或显式 stage_candidate 时上传阿里云候选

workflow_dispatch(Deploy)
  -> 查找同 SHA 的绿色 Affected Delivery
  -> 下载候选
  -> release-engine deploy --environment production
```
