## 2. P0：不清零不得碰真实资金

### P0-1 库存只占不放（最严重）

**证据**：`database/supabase/migrations/20260724070000_production_mvp.sql:560`

全仓 69 个迁移里，`inventory` 的数量字段只有这一处变更：`reserved_qty = reserved_qty + quantity`。
没有任何一处减少 `reserved_qty`，也没有任何一处改动 `available_qty`。

因此：

- 下单即永久占用库存，取消/超时**从不释放**
- 支付成功**不扣减** `available_qty`，卖出去的货在账上还在
- 库存数字在任何一次下单流程之后即失去意义

| ID  | 内容                                                                                                                    | 验收                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| B1  | 新增迁移：`api_commit_inventory(order_id)`，支付成功时 `available_qty -= q` 且 `reserved_qty -= q`，用 `version` 乐观锁 | SQL 契约测试：支付后两字段同步下降                              |
| B2  | `api_release_inventory(order_id, reason)`：取消/超时/支付失败时 `reserved_qty -= q`                                     | 契约测试：释放后 `available_qty - reserved_qty` 回到下单前      |
| B3  | 订单超时任务：`pending_payment` 超过 N 分钟自动取消并调 B2                                                              | 集成测试：伪造过期订单，跑一次任务后库存归还                    |
| B4  | 幂等：B1/B2 重复调用不得重复扣减                                                                                        | 同一 `order_id` 调两次，第二次返回 `already_applied` 且数量不变 |
| B5  | 并发：同一 SKU 并发下单不得超卖                                                                                         | 并发测试：20 并发抢 5 件，成功恰好 5 单                         |

**依赖**：B1 必须由 P0-2 的 Outbox 消费者调用，否则支付成功仍不扣减。

### P0-2 Outbox 无消费者：支付后一切下游都不发生

**证据**：

- `20260814130000_wechat_order_payment_compliance.sql:934` 定义 `api_claim_wechat_payment_outbox`（`for update skip locked`、worker 租约、2 分钟超时重投）
- 同文件 `:967` 定义 `api_complete_wechat_payment_outbox`
- `20260819120000_client_error_reports.sql:152` 另有一套
- **`services/` 与 `apps/` 下没有任何文件出现 `outbox` 字样** —— 三个 claim 函数从未被调用

支付成功时（同文件 `:686`）只更新 `public.orders` 的 `paid_cents` 与 `status`，其余通过 `order.payment_succeeded` 主题投递。该事件无人消费，所以履约、结算、通知、子订单状态全部停在原地。

| ID  | 内容                                                                           | 验收                                           |
| --- | ------------------------------------------------------------------------------ | ---------------------------------------------- |
| C1  | 新增 `services/paymentworker`：claim → 处理 → complete 循环，含退避与死信      | 单测覆盖租约过期重投、超次数进死信             |
| C2  | 消费 `order.payment_succeeded`：调 B1 提交库存、写履约单、写结算意图           | 端到端：模拟支付回调后库存/履约/结算三处一致   |
| C3  | 消费 `order.payment_reconciliation_required`：进人工对账队列，**不得自动平账** | 金额冲突订单进队列且 `status='refund_pending'` |
| C4  | 子订单状态传播：父单 `paid` → 各子单按供应商推进                               | 多供应商订单支付后每个子单状态正确             |
| C5  | worker 纳入 `ecosystem.config.cjs` 与 `deploy.sh`                              | PM2 进程列表含 worker，重启后自动拉起          |

### P0-3 微信退款通道不存在

**证据**：`20260725014000_payment_refund_reconciliation.sql:101` —— 只要订单存在非 `welfare`/`meal` 通道的成功支付，就抛 `REFUND_CHANNEL_UNSUPPORTED`。

好消息：它**失败关闭**，不会错退。坏消息：真实付款订单无法退款。

| ID  | 内容                                                     | 验收                                 |
| --- | -------------------------------------------------------- | ------------------------------------ |
| D1  | 接入微信退款 API，复用 `wechatPayCrypto.ts` 的签名与证书 | 沙箱完成一笔退款并收到退款结果通知   |
| D2  | 退款结果通知路由 + 验签 + 幂等落库                       | 重复通知只记一次                     |
| D3  | 混合支付订单按通道分别退款（福利余额 + 微信）            | 契约测试：两通道金额之和等于退款总额 |

### P0-4 售后可绕过审核直接退款

**证据**：同文件 `:96` —— 允许的状态是 `submitted` / `reviewing` / `approved`。
`submitted` 即申请人自己提交后、无需任何人审批即可退款。

| ID  | 内容                                                                  | 验收                                                |
| --- | --------------------------------------------------------------------- | --------------------------------------------------- |
| D4  | 收紧为仅 `approved` 可退款                                            | 用 `submitted` 调退款返回 `AFTER_SALE_NOT_APPROVED` |
| D5  | 补齐状态机迁移：`submitted → reviewing → approved/rejected`，禁止跳跃 | 契约测试覆盖全部非法迁移                            |
| D6  | 审批动作要求 `order.refund.approve` 权限 + 二次认证                   | 无权限身份收到 403 且不触库                         |

### P0-5 财务对账台是前端伪造

**证据**：`apps/admin-web/src/components/workstations/FinancialReconciliationWorkstation.tsx:28-40`

平账动作是一次纯前端 `discrepancies.map()`，把行状态改成 `RESOLVED`、写上「平账成功！调账凭证已存」，再 `alert("调账凭证已自动生成，差额 ¥X 抹平！")`。**全程不调用任何接口。**
数据来自 `apps/admin-web/src/data/mockData.ts:1050` 的 `INITIAL_FINANCE_DISCREPANCIES`。

操作员会看到「平账成功」和「调账凭证已生成」，而账上什么都没发生。

| ID  | 内容                                                                   | 验收                         |
| --- | ---------------------------------------------------------------------- | ---------------------------- |
| E1  | **立即**在真实环境隐藏该工作台，直到 E2 完成                           | 生产构建中该菜单不可达       |
| E2  | 后端对账：`api_finance_discrepancies` 三方勾稽（订单/支付流水/结算单） | 差异行来自真实数据           |
| E3  | 平账写路径：`api_reconcile_discrepancy`，落调账凭证 + 审计 + 幂等键    | 平账后凭证可查、可追溯操作人 |
| E4  | 前端改接真实接口，移除 `alert` 与前端状态改写                          | 断网时显示错误而非「成功」   |

### P0-6 后台仍有 5 个切片是永久 mock

## 5. 全程适用的工程约束

- DDD 分层：`domain`（零 IO）→ `application` → `interface`；`infrastructure` 实现 `port`。跨模块只经 port 或领域事件。
- 一个文件一个主要公共概念，超 299 行必须先按职责拆分（`npm run check:lines` 是硬门禁）。
- 命名：目录单数小写英文；类/组件 PascalCase；函数/变量 camelCase；常量 UPPERCASE。除 cli、代码审计、配置、SQL 迁移与测试外，不得出现下划线、连字符、空格或无意义缩写（`V1` 这类版本后缀已清理，不要再引入）。
- **金额一律整数分，禁止浮点。**
- 禁止重复逻辑与重复配置；禁止调用点断裂。
- 彻底移除演示态与兼容层，不保留转发别名。
- 任何「看起来缺失/重复/架构不对」的现象，先 `git show 77b0500:<文件>` 查基线再动手——本仓库曾因目录复制式合并丢失 28 个文件、64 个导出符号、约 1816 行。
