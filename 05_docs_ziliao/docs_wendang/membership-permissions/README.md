# Smart Wing 会员权限系统

这套系统以福利商城 MVP 的真实业务范围为权限目录，以 HS 的 Owner 保护、授权留痕和管理体验为安全基线，并吸收 Discord 的两个核心思想：多个角色可以叠加，明确禁止永远优先。

## 一句话模型

一次授权决定由四部分组成：会员身份 × 允许做什么 × 可以操作哪些数据 × 是否满足风险条件。

菜单隐藏只改善体验，最终决定必须由服务端根据数据库中的会员、角色、权限、数据范围和授权版本重新判断。

## 已搭建的 MVP

- 会员身份列表：有效、暂停、移除等生命周期。
- 角色模板：角色权限可叠加，未来可增加自定义角色。
- 数据范围：当前启用安全租户、集团、商城、供应商、部门、本人；全局平台已经具备祖先判定能力，但只允许通过后续专用授权仪式授予；分销商、品牌、门店继续默认拒绝。
- 最小披露：会员列表默认不返回邮箱和手机，只有 `member.pii.read` 才能读取敏感字段。
- 明确禁止：会员级 `deny` 覆盖任意角色的 `allow`。
- Owner 保护：每租户唯一；日常后台不能授予、撤销、暂停或修改 Owner。
- 防止误锁与提权：不能修改自己的角色、范围或状态。
- 防止向上授权：委派管理员不能授予自己没有的权限，也不能授予超出自身管理范围的数据。
- 立即失效：会员角色、范围、状态、例外以及角色内部权限变化都会提升相关 `authz_version`，旧会话随即失效。
- 高风险二次验证：退款、角色授权、范围授权、支付配置、密钥和导出等由风险目录统一标记。
- 审计：变更原因、操作者会员、授权证据和结果写入不可修改审计日志。

## 刻意保留的扩展点

- `permissions` 表保存展示分类、风险级别和 MVP 标识；新增业务功能只需登记权限，不改授权引擎。
- `roles` 表保留系统角色与自定义角色；后续可以增加角色复制、版本、审批和有效期。
- 严格组织层级采用 `org_units + org_unit_closure`，旧 tenant/enterprise/mall/department 字段继续兼容；详细边界见 [四类边界模型](./00-BOUNDARY-MODELS.md)。
- 分销商属于组织层级；品牌和门店属于商业资源关系，不能只靠增加 scope 枚举完成。
- `membership_permission_overrides` 同时支持 allow/deny；当前后台只开放 deny，避免一开始形成难以解释的个人特权。
- 权益套餐与人员权限保持分离：套餐决定企业买了什么，角色决定某人能操作什么。
- Owner 转移不属于日常权限页，后续单独设计带二次验证、双人确认、冷静期和恢复码的流程。

## 下一阶段

1. 接入真实密码、手机、验证码和会话设备管理。
2. 开放自定义角色的创建、复制与权限矩阵编辑。
3. 补齐会员邀请、批量导入、部门同步和离职流程。
4. 给高风险操作增加双人审批与职责分离。
5. 接入分销商、品牌、门店资源表后启用对应范围校验。
6. 建立权限回归矩阵，确保每个接口、导出、敏感字段都在服务端复核。
