状态：待实施

架构形态：模块化单体、异步作业、事件驱动投影
兼容策略：一次性切换，不保留旧接口、旧读模型、双写或兼容适配层

## 2. 结论

现有系统已经具备卡券核心运行能力：方案版本、卡号池、批量发行、单券状态、余额、绑定、核销、冲正、异步任务、幂等、KMS、Outbox 和财务端口。现状缺失的是甲方要求的 B2B 运营模型与完整管理工作台。

本次升级不重写基础设施，也不复制甲方静态 HTML。目标是在现有基础上建立一条唯一、完整、可恢复的业务链：

```text
企业客户 + 卡券产品 + 卡密凭证
              ↓
          备券申请
              ↓
          多级审批
              ↓
        卡券销售订单
              ↓
          异步发行
              ↓
      激活 / 绑定 / 核销
              ↓
      状态历史 / 财务事实
```

## 3. MVP 决策

以下决策作为实施默认值。若甲方改变口径，只修改本节并同步受影响的领域规则，不在代码中增加兼容分支。

1. MVP 产品类型只实现储值券。
2. 积分券、专用积分和兑换礼包不进入 MVP，但通过卡券类型注册表保留正式扩展点。
3. 审批引擎支持任意多级节点；初始模板预置“商城管理员提交 → 子机构管理员审批 → 机构管理员审批”。
4. 审批模板可以停用。未绑定有效模板的产品按无需审批处理，不维护额外全局布尔开关。
5. 实体券先生成凭证库存，再由备券审批占用，发行时转换成可使用卡券。
6. 电子券不预生成物理卡号；备券只占用数量额度，发行作业生成券密。
7. 实体券备券必须明确 `medium=physical`，电子券备券必须明确 `medium=electronic`。不允许在卡券中心临时改变介质。
8. “仅输入券密”和“输入券号及券密”是兑换方式，不与“系统生成/文件导入”混为同一个字段。
9. 卡券面值、销售单价、销售总额分开建模。销售总额等于销售单价乘数量；面值来自产品版本快照。
10. 客户默认付款条件属于客户；收款状态属于每一张卡券销售订单。
11. 一张备券申请允许创建多张销售订单，剩余数量在订单提交时扣减，而不是在后台任务完成后扣减。
12. 激活、绑定、兑换、作废不是四个可任意组合的布尔值。当前状态由卡券状态机决定，时间字段与历史事件用于查询展示。
13. 所有重任务均异步执行：批量生成、文件导入、卡券发行、批量状态操作、到期处理和导出。
14. API 接收命令后返回稳定回执；客户端通过批次查询获得进度，不维持长连接等待大批次结束。
15. 不保留旧卡券 API、旧四页只读治理台或旧字段别名。切换后只有新模型是事实来源。
16. 卡券 Console 以 Smart Wing VI 1.2 为唯一视觉基础；只通过 `@shop/design` 公共导出消费组件和 Token，不复制组件、不反向修改 Design 包。

## 4. MVP 功能范围

### 4.1 卡号库

- 创建实体券凭证池。
- 选择兑换方式。
- 批量生成 NO 编号、QH 券号和 QM 券密。
- 导入外部凭证文件。
- 查询生成或导入进度和逐行错误。
- 按编号、券号、状态、创建人和时间搜索。
- 导出凭证数据。
- 查看凭证从生成、占用到发行、作废的历史。

### 4.2 客户管理

- 企业客户新增、编辑、详情、启停和搜索。
- 客户类型、行业、规模、标签、销售负责人和默认付款条件。
- 多联系人增删改查。
- 客户电话、地址、联系人手机和邮箱由 Partner 模块统一维护。
- 已被历史订单引用的客户不物理删除，只改变状态。

### 4.3 产品档案

- 储值券产品新增、版本化编辑、详情和启停。
- 适用商城、面值、默认有效期、兑换方式和审批模板。
- 已发行版本保持不可变；新规则产生新版本。
- 停用产品不能创建新备券，既有卡券仍按发行时版本运行。

### 4.4 备券中心

- 创建草稿、编辑、提交、取消和详情。
- 关联客户、产品版本、商城、介质、兑换方式和申请数量。
- 提交时冻结一份业务快照。
- 审批通过后，实体券占用具体凭证；电子券确认数量额度。
- 支持多张发行订单分次消耗。
- 展示申请、承诺、已发行和剩余数量。

### 4.5 卡券审批

- 审批模板新增、版本化修改、启停和详情。
- 配置申请人规则、审批节点顺序、审批人规则和任一/全部通过模式。
- 每次备券提交创建独立审批实例并快照模板版本。
- 审批决定不可修改；重新提交创建新的审批实例。
- 展示当前待办、执行人、意见、时间与完整历史。

### 4.6 卡券中心

- 实体券和电子券分栏查询。
- 三步创建：选择类型、填写规则、确认凭证或券码计划。
- 维护券名称、封面、有效期、销售价格、跳转目标和备注。
- 提交后创建订单和发行批次。
- 支持批次失败重试，不重复生成卡券或记账。
- 展示订单、发行批次、数量、卡号范围和销售快照。

### 4.7 券操作

- 激活、禁用、恢复、延期和作废。
- 选择单券、券号段或发行批次。
- 提交时冻结目标集合，后台逐券执行。
- 展示每张券的操作前状态、操作后状态、时间和失败原因。

### 4.8 卡券查询

- 以单张卡券为行的统一搜索。
- 支持甲方原型中的全部筛选条件。
- 查看卡券详情、余额、客户、产品、订单、凭证、会员和时间字段。
- 查看生成、占用、发行、激活、绑定、核销、退款、禁用、延期、作废和到期时间线。
- 异步导出当前筛选结果。

### 4.9 会员端与核销

- 仅券密激活。
- 券号加券密激活。
- 激活时绑定当前会员，或由授权运营操作单独绑定。
- 下单时预占、支付后核销、失败或取消后释放。
- 门店核销支持一次性使用全部余额。
- 订单退款支持部分冲正，多次冲正累计不得超过原核销金额。

## 5. 明确不做

- 不直接复用甲方 HTML 的硬编码数据或内联 JavaScript。
- 不维护新旧两套数据表、接口和页面。
- 不把客户复制到 Voucher 模块。
- 不把商城、商品或会员资料复制进卡券主表。
- 不把审批人硬编码在 TypeScript 或 SQL 中。
- 不把四个查询状态保存为互不约束的布尔列。
- 不在 HTTP 请求内同步生成大量券密、批量更新数万张券或导出大文件。
- 不为积分券和礼包预先实现未确认的业务规则。
- 不拆分独立微服务；当前事务边界和规模更适合模块化单体。

## 6. 统一术语

| 中文 | 代码名 | 含义 |
|---|---|---|
| 企业客户 | `Customer` | 采购或使用卡券的 B2B 主体，属于 Partner 上下文 |
| 产品档案 | `VoucherProduct` | 稳定产品身份 |
| 产品版本 | `ProductVersion` | 不可变面值、有效期和规则快照 |
| 卡号库 | `CredentialPool` | 实体券凭证批次容器 |
| 卡密凭证 | `Credential` | NO/QH/QM 或电子券密 |
| 备券申请 | `StockRequest` | 经审批取得可发行数量或实体凭证的申请 |
| 审批模板 | `ApprovalTemplate` | 可版本化审批定义 |
| 审批实例 | `ApprovalInstance` | 一次备券提交对应的执行快照 |
| 卡券订单 | `IssueOrder` | B2B 销售及发行指令 |
| 发行批次 | `IssueBatch` | 异步生成单张卡券的执行单元 |
| 单张卡券 | `Voucher` | 最终可激活、绑定和核销的价值载体 |
| 临时预占 | `TenderHold` | 会员结算时短期冻结卡券余额 |
| 核销 | `Redemption` | 消耗卡券余额的事实 |
| 冲正 | `Reversal` | 恢复一次核销的部分或全部金额 |
| 券操作批次 | `ActionBatch` | 对冻结目标集合执行状态变更的批次 |

## 8. 设计原则

1. 一个业务事实只有一个写入所有者。
2. 聚合只维护自己的不变量，不跨模块直接写表。
3. 跨模块同步读取走最小端口，异步通知走版本化事件。
4. 领域层不依赖 HTTP、PostgreSQL、KMS、ObjectStore 或 React。
5. 命令和查询分离；复杂查询不通过聚合仓储拼装。
6. 大批量操作先冻结目标，再异步逐项执行。
7. 金额统一使用安全整数最小货币单位和 `Money`。
8. 所有写命令具备幂等键；并发修改使用版本或行锁。
9. 所有历史快照不可变；当前指针和运行状态可以改变。
10. 扩展产品类型通过注册表和策略对象，不在核心流程堆叠条件分支。
11. 界面字段、API 字段和领域术语保持一一映射。
12. 不为未进入 MVP 的需求增加表、接口或空页面。

## 9. 验收总则

只有同时满足以下条件才算完成升级：

- 八个甲方工作台均连接真实服务端数据。
- 客户、产品、凭证、备券、审批、订单、发行、操作、查询形成端到端闭环。
- 实体券与电子券的凭证生命周期不混淆。
- 一张备券可以安全并发创建多张订单且绝不超量。
- 批量任务中断后可以继续，不重复发券、扣量或记账。
- 单张券详情和时间线能解释其所有状态变化。
- 核销、部分退款、作废和到期后的余额与财务事实一致。
- 浏览器、API、数据库、作业和财务的真实端到端测试通过。
- 旧页面、旧接口、旧表名和旧兼容代码已从最终运行路径移除。
